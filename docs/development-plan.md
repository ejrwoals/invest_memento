# Investment Memento — 개발 계획 문서

## 0. 한 줄 요약

> 영화 <메멘토>처럼, 과거의 나(투자 판단의 근거와 가설)를 잊지 않도록 기록하고
> 주기적으로 리마인드하며, AI가 그 가설에 영향을 줄 새로운 정보를 계속 조사해주는
> **투자 판단 보조 노트 앱**.

---

## 1. 배경 및 문제의식

- 개인 투자자는 과거에 스스로 세웠던 분석/가설/전제를 시간이 지나면서 잊어버린다.
- 그 결과 눈앞의 뉴스, 단기 변동성, 감정에 휩쓸려 과거의 논리와 모순되는 판단을 반복한다.
- "내가 왜 이 종목/자산을 샀는지", "그 판단의 전제 조건이 아직 유효한지"를 스스로
  추적하지 못하는 것이 어리석은 투자 판단의 핵심 원인 중 하나다.
- 필요한 것은 단순한 메모장이 아니라, **과거의 가설을 잊지 않게 강제로 리마인드**하고
  **그 가설이 여전히 유효한지 판단할 근거(뉴스/데이터)를 계속 모아주는 보조 장치**다.

## 2. 핵심 컨셉

### 2.1 메멘토 원칙

영화 속 주인공이 문신과 메모로 기억을 대체하듯, 이 앱은 사용자의 "과거 투자 관점"을
잃어버리지 않도록 구조화해서 저장하고, 시간이 지남에 따라 사용자에게 능동적으로
다시 보여준다.

1. **기록(Record)**: 판단 당시의 근거, 조사 자료, 관점을 시나리오·시점과 함께 구조화하여 저장한다.
2. **리마인드(Remind)**: 주기적으로 과거 기록을 다시 보여줘서 현재 판단이 과거 논리와
   일관적인지 스스로 점검하게 한다.
3. **추적(Track)**: AI가 각 가설/시나리오와 관련된 새 뉴스·데이터를 지속적으로 조사해서
   요약해준다.
4. **재평가(Re-evaluate)**: 시간이 지나며 어떤 시나리오의 발생 확률이 올라가고, 어떤
   시나리오는 이제 접어도 되는지 사용자가 판단하도록 돕는다.

### 2.2 가설-시나리오 중심 설계

이 앱에서 "노트"는 단순 텍스트가 아니라 **검증 가능한 구조**를 가진다.

- 하나의 투자 노트(Note)는 하나의 투자 대상(종목/자산/테마)에 대한 **핵심 가설(Thesis)**을 가진다.
- 하나의 가설은 여러 개의 **시나리오(Scenario)**로 분기된다. (예: 낙관/중립/비관, 또는 사건 발생/미발생 등)
- 각 시나리오는 다음을 반드시 포함해야 한다.
  - 시나리오 설명 (구체적으로, 무엇이 어떻게 되면 이 시나리오인지)
  - **예상 시점(Target Timeframe)** — "언제까지 이 일이 일어나거나 판가름 나는지"
  - **근거 항목** — 내 논리가 참이라면 먼저 일어나야 하는 일. 수치화하지 않고 서술로 (§2.3)
  - **결과 지표(Indicator)** — 결과를 객관적으로 확인할 수 있는 수치 조건. 선택 사항이며
    노트 저장 후 2단계에서 따로 설정한다 (§2.3, §3.1)
  - 최초 추정 확률(선택), 그리고 시간에 따라 갱신되는 확률
- 시점을 명시하기 때문에, 그 시점이 다가오거나 지나면 앱이 "이 시나리오 재검토 시점입니다"라고
  능동적으로 알릴 수 있다.

### 2.3 반증 가능성 — 결과는 숫자로, 논리는 회고로

"유동성이 풀린다" 같은 가설은 '풀린다'의 기준이 모호해서 나중에 맞았는지 틀렸는지 판정할 수
없다. **판정할 수 없는 가설은 복기할 수 없고, 복기가 불가능하면 이 앱은 그냥 일기장이 된다.**

따라서 시나리오를 만들 때 **그것이 맞았는지 확인할 수 있는 조건을 함께 정한다.**

#### 결과는 숫자로 판정하고, 논리는 회고로 검증한다

이 앱이 답해야 할 질문은 사실 두 개이고, 서로 성질이 다르다.

| 질문 | 검증 방법 | 시점 |
|---|---|---|
| **내가 예상한 일이 일어났는가?** | 수치 지표 자동 판정 | 판단 시점 도래 시 |
| **그게 내가 생각한 이유 때문이었는가?** | AI 자료조사 + 사용자 서술 | 판정 후 회고록(§3.6) |

두 번째 질문을 수치 지표로 풀려는 시도는 현실적으로 실패한다. "DRAM 현물가", "HBM 매출 비중"
같은 진짜 중요한 중간 고리들은 유료 산업 데이터라 무료 API로 가져올 수 없다. 억지로
가져올 수 있는 것만 쓰면 지표가 다시 결과 지표(주가·지수)로 수렴해 동어반복이 된다.

그래서 **자동 판정은 결과 지표만 담당하고, 논리 검증은 회고 단계로 넘긴다.**

#### 지표는 두 종류로 기록하되 역할이 다르다

| 종류 | 의미 | 자동 추적 | 쓰임 |
|---|---|---|---|
| **결과 지표** | 내가 기대하는 최종 결말 (주가, 지수, 금리, 환율, CPI 등) | ✔ 가능 | 판정 트리거 + 객관적 결과 확인 |
| **근거 항목** | 내 논리가 참이라면 **먼저 일어나야 하는 일** | 대부분 불가 | 회고 때 AI가 조사할 대상 |

- **근거 항목은 수치로 가져올 수 없어도 반드시 적어둔다.** 자동 추적이 목적이 아니라,
  "내가 무엇을 전제로 이 판단을 했는가"를 남기는 것이 목적이다. 시간이 지나면 사람은
  자기가 어떤 논리로 샀는지조차 잊고 결과만 기억한다. 그 논리 자체가 기록되어야
  나중에 검증할 대상이 생긴다.
- 근거 항목은 **회고 시 AI 자료조사의 검색 키워드**가 된다. "HBM 매출 비중이 실제로
  올랐는가"를 AI가 뉴스·공시·실적 발표에서 찾아 근거와 함께 정리한다.
- 근거 항목 중 마침 API로 가져올 수 있는 것(금리, 환율, 수출 증가율 등 FRED·ECOS가 커버하는
  거시 계열)은 결과 지표와 동일하게 자동 추적한다. 가능하면 하고, 안 되면 회고로 넘긴다.

#### 지표의 구성 요소

```
지표 = 데이터 출처 + 대상 + 비교 방식 + 목표값 + 관측 규칙
예) FRED · 미국 기준금리 · 이하 · 3.5% · 종가 기준 1회라도
    KIS  · 삼성전자    · 이상 · 95,000원 · 5거래일 연속 종가
```

- **비교 방식**: 이상 / 이하 / 범위 안 / 변화율(기준일 대비 ±N%) — 사용자가 고른다.
- **관측 규칙**: **사용자가 고르지 않는다. 시스템이 하나로 고정한다.**

#### 관측 규칙은 하나로 못 박는다

> **판단 시점까지 기간 중 한 번이라도 목표에 닿으면 달성. 장중에 스친 것도 인정한다.**

"장중 터치를 인정할지", "종가로 며칠 연속이어야 하는지"를 사용자에게 물으면, 모든 사용자가
지표를 만들 때마다 **자기가 답할 준비가 안 된 질문** 앞에 선다. 대부분은 그 차이를 생각해본
적이 없고, 고민하다 설정 자체를 포기한다.

관대한 쪽으로 고정해도 잃는 것이 없다. **앱은 어차피 판정하지 않고 제안만 하기 때문이다.**
기준이 관대하다는 건 "앱이 더 일찍 묻는다"는 뜻일 뿐이고, 장중에 잠깐 스친 것을 적중으로
볼지는 결과 확인 화면에서 사용자가 정한다. 오히려 엄격한 기준은 **닿았는데도 앱이 아무 말을
안 하는** 상황을 만들어 더 나쁘다.

- 거시 지표에는 장중이라는 개념이 없다. 발표된 값 하나가 그날의 값이고, 같은 규칙이
  그대로 적용된다.
- 이 규칙은 화면에 **설정 항목이 아니라 안내 문장**으로 한 번 적는다.

#### 여러 지표를 묶는 방식

지표가 여러 개일 때 **전부 달성(AND)만 강요하지 않는다.** 현실의 가설은 대부분 OR이거나
"몇 개 이상"이다. AND만 있으면 거의 모든 가설이 실패로 끝나 사용자가 지표 설정을 회피하게 된다.

- 전부 달성 (AND)
- 하나라도 달성 (OR)
- N개 중 M개 이상

#### 결과 자체가 숫자가 아닌 경우는 사건형 지표로

규제 승인, M&A 성사처럼 결과 자체가 숫자가 아닌 경우도 있다. 이런 것은 **사건형 지표**
(예/아니오)로 두고 사용자가 직접 표시한다. 자동 수집은 안 되지만 판정 시점을 명확히 하는
효과는 동일하다.

(내 논리의 중간 고리를 적어두는 **근거 항목**과는 다른 것이다. 사건형 지표는 결과 축이고,
근거 항목은 논리 축이다.)

#### 자동 판정은 하지 않는다 — 제안까지만

**지표가 전부 달성되어도 앱이 "맞았다"고 확정하지 않는다.** 지표는 내 논리와 무관한 이유로도
달성될 수 있고, 그걸 앱이 적중으로 처리해버리면 사용자는 틀린 논리를 옳다고 학습한다.
이 앱의 목적과 정면으로 어긋난다.

- 지표 달성 시: "지표가 전부 달성됐습니다. 어떻게 보시겠습니까?" → 사용자가 판단
- 기한 경과 + 지표 미달성 시: 자동 실패 처리가 아니라 `결과 확인 필요` 상태로 전환
- 결과 확인 선택지는 세 가지다.
  `그대로 되었다` / `틀렸다` / `방향은 맞지만 시기를 다시 본다`

  여기서 묻는 것은 **"예상한 일이 일어났는가"뿐이다.** "그게 내 논리 때문이었는가"는
  자료를 조사해봐야 알 수 있으므로 이 자리에서 물으면 사용자가 답할 수 없다.
  그 질문은 회고록(§3.6)이 담당한다.

#### 지표를 나중에 고치면 이력이 남는다

지표를 사후에 유리하게 낮추면 이 기능 전체가 무의미해진다. 수정 자체는 허용하되,
**"처음엔 3,200이었는데 2,900으로 낮춤" 같은 변경 이력이 복기 화면에 반드시 남는다.**
원본 대화를 고치지 않는 원칙(§3.1)의 연장이다.

### 2.4 AI의 역할

AI는 판단에 필요한 정보를 모으고 정리해서 사용자가 더 나은 판단을 하도록 돕는
보조자이면서, 동시에 **적극적으로 의견을 개진하는 어드바이저**이기도 하다.

- **리서치 보조**: 노트/가설/시나리오와 관련된 최신 뉴스, 공시, 데이터를 조사해서 읽기 쉽게 요약.
- **관련성 판단**: 수집한 정보가 어떤 시나리오를 뒷받침하는지, 어긋나는지 표시.
- **리마인드 큐레이션**: 언제, 어떤 노트를, 어떤 맥락과 함께 다시 보여줄지 결정.
- **확률 갱신 제안**: 새 정보 기반으로 시나리오 확률 조정을 "제안"하되, 최종 확정은 사용자가 함.
- **소크라테스식 질문**: 사용자가 놓친 반대 시나리오나 리스크를 질문 형태로 환기.
- **직접적인 매수/매도 의견 제시**: AI 프롬프트 단에서는 매수/매도 추천, 목표가, 타이밍 의견 등을
  자유롭게 낼 수 있도록 제한을 두지 않는다. "투자 판단과 그 책임은 전적으로 사용자 본인에게
  있다"는 고지를 UI 레벨(예: 앱 전역 푸터, 리서치/추천 카드마다, 온보딩 등)에서 상시 노출하는
  것으로 책임 소재를 명확히 하고, 그 대신 AI는 판단을 흐리지 않고 소신 있게 의견을 낸다.
  즉 **면책은 UI의 책임, 유용하고 직접적인 조언은 AI의 책임**으로 역할을 분리한다.

## 3. 핵심 기능 명세

### 3.1 투자 노트 작성 — AI와의 대화 기반

노트는 폼 입력이 아니라 **AI와의 대화**로 만들어진다. 사용자는 생각나는 대로 말하고,
AI가 대화를 통해 필요한 구조를 끌어낸 뒤 노트를 작성한다. 폼을 강제하면 작성이 귀찮아져
기록 자체가 쌓이지 않고, 기록이 없으면 이 앱의 가치는 0이 되기 때문이다.

#### 작성은 두 단계로 나눈다

한 번의 대화에서 논리와 수치 설정을 모두 받으면 대화가 길어져 사용자가 이탈한다.
시나리오 2개에 지표까지 물으면 질문이 열 번을 넘고, 이는 **작성 진입장벽을 최소화한다**는
원칙(UX §P6)과 정면으로 충돌한다. 그래서 성질이 다른 두 작업을 분리한다.

> **논리는 대화로, 수치 설정은 폼으로.**
> 대화는 "왜"를 끌어내는 데 강하고, 폼은 "얼마"를 받는 데 강하다.

| | 1단계 — 대화 | 2단계 — 지표 설정 |
|---|---|---|
| 성격 | 사고를 끌어내는 일 | 기계적인 설정 작업 |
| 형식 | AI와의 자유 대화 | AI가 후보를 채워둔 폼 |
| 필수 여부 | 필수 | 건너뛸 수 있음 |
| 다루는 것 | 대상, 가설, 시나리오, 판단 시점, 근거 항목 | 결과 지표의 목표값·관측 규칙 |

#### 1단계 — 대화에서 확보할 항목

| 항목 | 필수 | 비고 |
|---|---|---|
| 투자 대상(티커/자산/테마) | 필수 | |
| 핵심 가설 | 필수 | |
| 시나리오 2개 이상 | 필수 | 긍정/부정 등 대칭적 사고 유도 |
| 각 시나리오의 **판단 시점** | 필수 | 특정 날짜 또는 범위 ("2026 Q4까지") |
| 각 시나리오의 **근거 항목** | 필수 | 내 논리의 중간 고리. 수치화하지 않는다 |
| 반증 조건 | 권장 | |
| 근거 자료 | 선택 | 사용자가 링크를 붙이면 수집 |

- AI는 **판단 시점과 근거 항목**에 대해서만 끈질기게 확보를 시도한다. 시점이 없으면
  리마인드가 불가능하고, 근거 항목이 없으면 회고 때 검증할 대상이 없어진다.
  강요하지는 않고 막연하면 범위로라도 받아낸다.
- **근거 항목은 반드시 1단계에 남긴다.** 2단계로 미루면 안 된다. 논리는 사용자가
  자기 생각을 말하는 흐름 속에서 받아야 진짜가 나온다. 나중에 폼으로 따로 물으면
  이미 정리된 결론에 맞춰 사후 합리화된 답만 돌아온다.
  숫자를 묻지 않으므로 한 턴이면 끝나 대화 길이에도 부담이 적다.
- 근거 항목을 끌어내는 질문: "그렇게 되려면 그 전에 무슨 일이 먼저 일어나야 할까요?"
  **수치나 데이터 출처는 묻지 않는다.** 사용자가 말로 설명한 그대로 받는다.
  ("HBM 공급이 계속 부족해야 하고, 삼성이 퀄 통과를 해야 하고")
- 대화 종료 시 AI가 노트 초안을 생성 → 사용자가 미리보기에서 확인·수정 후 저장
  (무엇을 어떻게 채우는지는 아래 '노트 생성 계약' 참조)
- **원본 대화 전문은 노트에 영구 첨부되며 수정·삭제할 수 없다.** AI가 노트를 쓰는 구조에서
  "과거의 나의 관점"이 AI의 문장이 되는 문제를 방지하는 장치로, 사용자는 언제든
  자신이 실제로 무슨 말을 했는지 원문으로 확인할 수 있다.


#### 노트 생성 계약 — AI는 자유 형식으로 쓰지 않는다

AI는 빈 문서에 글을 쓰는 것이 아니라 **정해진 스키마의 칸을 채운다.**

완전 자유 형식이면 이 앱의 나머지가 전부 무너진다. 프로그램이 시나리오를 읽지 못하면
판단 시점 리마인드도, 지표 연결도, 확률 조정도, 회고 자동 조사도 불가능하다.
반대로 문장까지 템플릿으로 고정하면 AI가 할 일이 없다. 그래서 이렇게 나눈다.

> **구조는 스키마가 강제하고, 문장은 AI가 쓴다.**

**출력 형식**: AI는 산문이 아니라 아래 구조를 반환한다. 화면 렌더링은 클라이언트가 한다.

| 칸 | 누가 채우나 | 규칙 |
|---|---|---|
| `target` | AI | 대화에서 종목·자산·테마를 뽑아 정규화 (`삼성전자` / `005930`) |
| `thesis_summary` | AI | **한 문장.** 목록·검색·알림에 쓰이므로 40자 내외로 압축 |
| `thesis_detail` | AI | 사용자의 논리를 재구성. 3~5문장 |
| 대표 인용 | **사용자 발화 그대로** | 대화에서 가장 핵심적인 한 마디를 원문 그대로 1개. `[사용자]` 표기 |
| `scenario.name` | AI | 한 문장. 무엇이 일어나는지가 드러나게 |
| `scenario.description` | AI | 2~3문장 |
| `scenario.target_timeframe` | AI가 파싱 | "올해 안" → `2026-12-31`. **해석한 결과를 사용자에게 보여주고 확인받는다** |
| `premise.statement` | **사용자 말 그대로** | 다듬지 않는다. 이건 나중에 검증할 대상이므로 원형이 중요하다 |
| `probability` | 사용자 | AI는 초기값을 제안하지 않는다 |

#### 지켜야 할 것 넷

1. **대화에 없는 내용을 쓰지 않는다.** 이게 가장 중요하다. AI가 그럴듯한 근거를 지어내
   채워 넣으면, 사용자가 몇 달 뒤 되돌아볼 "과거의 나"가 **하지도 않은 생각**이 된다.
   이 앱의 존재 이유가 통째로 무너진다. 빈 칸은 빈 채로 두고 미완성으로 표시한다.
2. **근거 항목은 사용자의 말에 가장 가깝게 둔다.** 시나리오 이름은 AI가 다듬어도 되지만,
   논리의 고리는 사용자 것이어야 한다. 회고 때 "내가 이렇게 생각했었나"에서 어긋나면 안 된다.
3. **해석한 것은 보여주고 확인받는다.** "내년 상반기" → `2027-06-30`처럼 AI가 판단한
   값은 미리보기에서 그대로 드러내고, 사용자가 고칠 수 있게 한다.
4. **저장 후에는 재생성하지 않는다.** 미리보기 단계에서만 `다시 만들기`를 허용하고,
   그때도 사용자가 이미 손댄 블록은 보존한다. 저장된 노트를 다시 생성하면 과거 기록이
   바뀌는 것이므로 금지다.

#### 2단계 — 결과 지표 설정 (건너뛸 수 있음)

노트 저장 직후 "이어서 지표를 정하시겠어요?"로 자연스럽게 이어지되, **나중에 해도 되고
안 해도 된다.**

- **AI가 후보를 미리 채워둔 폼으로 제시한다.** 빈 폼이 아니다. 대화 내용에서 종목·지수·
  거시 계열을 추출해 데이터 소스와 함께 후보로 올리고, 대화에 숫자가 언급됐으면 목표값도
  채워 둔다. 사용자는 확인하고 고치기만 하면 된다.
- 여기서 받는 것: **목표값, 비교 방식(이상/이하/범위/변화율), 여러 지표의 결합 방식**
  (전부/하나라도/N개 중 M개). 이 셋뿐이다.
- **관측 규칙은 묻지 않는다.** 시스템이 `한 번이라도 닿으면 달성 · 장중 포함`으로 고정하고,
  화면에는 안내 문장 한 줄만 둔다. 사용자가 답할 준비가 안 된 질문을 폼에 놓으면
  거기서 이탈한다.
- 근거 항목 중 마침 FRED·ECOS로 추적 가능한 것이 있으면 이 화면에서 지표 후보로 함께
  올라온다. 사용자가 원하면 추가하고, 아니면 넘긴다.

#### 지표가 없는 노트도 정상 동작한다

지표는 필수가 아니므로, 없어도 앱의 핵심 루프는 그대로 돌아간다.

| 빠진 것 | 결과 |
|---|---|
| 판단 시점 | **미완성 노트.** 리마인드 대상에서 제외되고 상단에 안내가 붙는다 |
| 결과 지표 | 정상 노트. 시점 기반 리마인드·회고록 모두 작동하고, **자동 판정만 없다.** 결과 확인 시 사용자가 직접 판단한다 |

지표가 없으면 노트 상세에 `지표를 정하면 자동으로 확인해 드립니다`라는 안내가 조용히
붙는다. 차단이 아니라 안내다. 압박하지 않는다(UX §P5).

> 화면 구성과 인터랙션 상세는 [`ux-design.md`](./ux-design.md) 참조.

### 3.2 리마인드 시스템
- 예약된 리마인드: 노트 작성 후 N일/주/월 후 자동 리마인드 (사용자 설정 가능, 기본값 제공)
- 시점 기반 리마인드: 시나리오의 예상 시점이 임박하거나 도래하면 알림
- 이벤트 기반 리마인드: AI가 수집한 뉴스가 특정 시나리오와 강하게 연관되면 즉시 알림
- 리마인드 화면 구성: "과거의 나는 이렇게 생각했다"(원문 그대로) + "그동안 이런 일이 있었다"(AI 요약)
  + "지금은 어떻게 보시나요?"(다시 판단하도록 유도)

### 3.3 AI 리서치 & 뉴스 모니터링
- 노트/가설/시나리오 단위로 관련 키워드·엔티티 자동 추출
- 주기적으로 (또는 온디맨드로) 관련 뉴스/공시/데이터 검색
- 검색 결과를 다음 기준으로 정리:
  - 어느 노트/시나리오와 관련 있는지
  - 해당 시나리오를 뒷받침하는지 / 어긋나는지 / 관련만 있는지
    (내부 값 `supports` / `contradicts` / `neutral`, 화면 표기는 UX 문서 §7.4 대응표를 따른다)
  - 한 줄 요약 + 원문 링크
- 사용자는 각 리서치 결과에 대해 "반영함/무시" 피드백 → AI 리서치 품질 개선에 활용

### 3.4 시나리오 트래킹 보드
- 노트별로 시나리오들을 보드 형태로 시각화, 홈에서는 전체 노트의 판단 시점을 세로 타임라인으로 표시
  (축 하나에 판단 시점을 점으로 찍고 카드를 연결한다. 항목이 늘어도 스크롤로 감당된다)
- 시간 경과에 따른 확률 변화 이력
- 시나리오 상태 (화면 표기 / 내부 값): 지켜보는 중 `active` / 결과 확인 필요 `pending_judgment` /
  그대로 됨 `confirmed` / 틀렸음 `rejected`
  - **앱이 알아서 "틀렸다"고 정리하는 경우는 없다.** 시점이 지나면 `결과 확인 필요`가 되어
    리마인드가 뜨고, 결론은 반드시 사용자가 낸다.
  - 선택지는 세 가지: `그대로 되었다` / `틀렸다` / `방향은 맞지만 시기를 다시 본다`
    - 여기서 묻는 것은 **"예상한 일이 일어났는가"뿐이다.** "내 논리 때문이었는가"는
      자료를 조사해봐야 알 수 있으므로 회고록(§3.6)에서 따로 묻는다.
    - 세 번째를 같은 비중으로 두는 이유: 현실에서 가장 흔한 경우가 "방향은 맞았는데 시기를
      잘못 봤다"인데, 틀렸다만 고를 수 있게 하면 사용자가 확인 자체를 피하고 방치하게 된다.
    - 시점 재설정 시 `active`로 복귀하며, 재설정 이력은 회고용으로 보존한다.
  - `그대로 됨` 또는 `틀렸음`으로 확정되면 **회고록이 열린다**(§3.6). 여기서 비로소
    "제대로 맞춘 것인가, 소 뒷걸음질인가"를 가린다.
  - 시나리오 카드에는 항상 **지표 달성 현황**이 함께 표시된다 (예: `지표 3개 중 2개 달성`).
    부분 달성은 그 자체로 강한 신호이므로 최종 판정 전에도 계속 보여준다.
  - 결과를 정할 때 이유를 한 줄 남기도록 권한다(선택). 이것이 가장 값진 회고 자료가 된다.
- 한 갈래 안의 시나리오들은 **동시에 일어날 수 없는 경우로 보고, 확률 합을 항상 100%로** 맞춘다.
  하나를 올리면 다른 것이 줄어드는 제약이 있어야 트레이드오프 사고가 강제된다.
- 갈래의 구성비는 **도넛**으로, 개별 시나리오의 확률 변화는 **눈금 막대**로 보여준다.
  전자는 "다 합치면 하나"를, 후자는 "지난번 대비 얼마나 움직였나"를 답한다.
  조각 경계를 그라데이션으로 그려 확률이 어림임을 형식에 담는다.
- 모든 노트에 지울 수 없는 **`그 외 예상 못한 전개`** 항목을 자동으로 만들고 최소 5%를 남긴다.
  "내가 생각한 경우가 전부"라는 착각을 구조적으로 막기 위함.

### 3.5 지표 수집 & 평가

- 사용자가 설정한 지표를 **하루 1회 배치로 수집**하고 달성 여부를 평가한다.
- 이 앱은 **실시간 시세가 필요 없다.** 지표는 종가·일별 값 기준으로 판정하고, 거시 통계는
  월·분기 단위로 갱신된다. 실시간을 전제하면 비용·라이선스·복잡도가 모두 불필요하게 올라간다.

#### 무엇을 저장하는가 — 종가와 고가·저가

| 데이터 종류 | 저장 값 | 이유 |
|---|---|---|
| 주식·지수 (KIS) | 종가 + 고가 + 저가 | 종가는 판정과 차트의 기준, 고가·저가는 `장중 터치 인정` 규칙 판정과 차트의 띠에 쓰인다 |
| 거시 지표 (FRED·ECOS) | 값 하나 | 장중이라는 개념이 없다. 설정 화면에서 장중 옵션을 노출하지 않는다 |

- **배치는 각 시장 마감 후 실행한다.** 한국장과 미국장은 따로 돈다.
- **아직 마감하지 않은 당일은 저장하지도, 그리지도 않는다.** 차트의 마지막 점은 언제나
  확정된 마지막 종가다. 장중 값을 보여주기 시작하면 그 순간 시세 앱이 되고, 사용자는
  하루에 몇 번씩 앱을 열게 된다 — 이 앱이 막으려는 행동이 정확히 그것이다.
- 해외 지표는 **현지 거래일 기준**으로 찍는다. 한국 시간으로 환산하지 않는다.
- **지표 값은 사용자별이 아니라 전역으로 캐시한다.** 삼성전자 종가는 모든 사용자에게 같은
  값이므로, 외부 API 호출량은 사용자 수가 아니라 **서로 다른 지표의 개수**에 비례한다.
  노트 10개 내외 × 사용자 수천 명이어도 실제 호출은 수백 건 수준에 머문다.
- 평가 결과는 `IndicatorSnapshot`으로 날짜별 보존한다. "그때 실제로 얼마였는지"가 남아야
  나중에 복기가 가능하다. 이 스냅샷이 곧 **지표 추이 차트**의 원천 데이터가 된다.
- 화면에서는 **기록 시점 값 · 목표값 · 그 사이 거리 · 오늘까지의 추이 · 남은 기간**을
  한 그림에 담는다. 캔들·이동평균·보조지표는 붙이지 않는다. 기술적 분석을 부르는 순간
  이 앱이 막으려던 충동적 판단이 되돌아온다. (UX 문서 §7)
- 기간은 언제나 `기록 시점 → 판단 시점`으로 고정한다. 사용자가 기간을 바꾸기 시작하면
  트레이딩 앱이 된다.
- 달성/미달성이 바뀌는 순간은 리마인드 트리거가 된다 (§3.2의 이벤트 기반 리마인드).

### 3.6 회고록 — 이 앱의 최종 산출물

시나리오의 결과가 정해지면 **회고록**이 열린다. 여기서 답하는 질문은 하나다.

> **제대로 맞춘 것인가, 소 뒷걸음질 치다 맞춘 것인가.**

결과가 맞았다는 사실만으로는 아무것도 배울 수 없다. 틀린 논리로 운 좋게 맞은 것을
실력으로 착각하면, 다음에 같은 논리로 더 큰 돈을 넣고 크게 잃는다. **이 앱의 존재 이유가
바로 이 구분에 있다.** 지표도, 리마인드도, 원본 대화 보존도 전부 이 순간을 위한 준비다.

#### 결과 × 논리의 2×2

|  | **논리가 맞았다** | **논리가 틀렸다** |
|---|---|---|
| **결과가 맞았다** | 제대로 맞춤 | **소 뒷걸음질** — 가장 위험한 성공 |
| **결과가 틀렸다** | 논리는 옳았으나 시기·경로가 어긋남 — **가장 배울 게 많은 실패** | 완전히 빗나감 |

- 판정(결과)은 §3.4에서, 논리 평가는 회고록에서 정한다. 두 축은 독립이다.
- 오른쪽 위 칸이 이 앱이 잡아내려는 핵심이다. 다른 앱은 이걸 "적중"으로만 기록한다.
- 왼쪽 아래 칸도 중요하다. 논리가 옳았는데 시기를 잘못 봤다면 그 논리는 버릴 게 아니라
  다시 쓸 자산이다.

#### AI가 초안을 먼저 만든다

빈 화면에 "회고를 쓰세요"라고 두면 아무도 쓰지 않는다. **AI가 자료조사를 마친 초안을
먼저 제시하고, 사용자는 거기에 최종 판단을 얹는다.**

AI 회고 리서치의 동작:

1. 노트에 기록된 **근거 항목**들을 꺼낸다 (수치화되지 않은 것 포함)
2. 각 항목이 해당 기간에 실제로 일어났는지 뉴스·공시·실적 발표에서 조사한다
3. 항목별로 `실제로 일어남` / `일어나지 않음` / `확인 불가`로 분류하고 출처를 붙인다
4. 결과 지표가 달성됐다면, **그 결과의 실제 원인으로 지목되는 설명들**을 따로 수집한다
   (시장 전체 상승, 다른 재료, 수급 등 — 내 논리와 무관한 원인일 수 있다)
5. 초안 서술을 생성한다

```
AI 회고 초안 예시

  당시 세우신 논리는 이랬습니다.
    HBM 공급 부족 지속 → 삼성전자가 후발주자로 점유율 확보 → 주가 상승

  조사 결과:
    · "HBM 공급 부족 지속"     → 일어나지 않음
      SK하이닉스 HBM4 양산이 앞당겨지며 2026년 하반기부터 공급이 풀렸습니다. (출처 2건)
    · "삼성전자 점유율 확보"   → 확인 불가
      삼성의 HBM 점유율을 공개한 자료를 찾지 못했습니다.
    · 결과 지표(주가 95,000원) → 달성 (2026.11.18)

  다만 같은 기간 코스피가 18% 올랐고, 반도체 업종 전체가 21% 올랐습니다.
  삼성전자의 상승률은 15%로 업종 평균을 밑돕니다.

  전제였던 공급 부족은 실제로는 해소되었는데 주가는 올랐습니다.
  시장 전체 상승에 따라 움직였을 가능성을 검토해 보시기 바랍니다.
```

- **AI는 초안까지만 쓴다.** "이건 운이었습니다"라고 확정하지 않는다. 판단은 사용자가 한다.
- 위 예시의 마지막 두 문단이 회고 리서치의 핵심이다. **결과 지표를 벤치마크(지수·업종)와
  대비**시키는 것만으로도 "그냥 시장이 올라서 오른 것"을 상당 부분 걸러낼 수 있다.
  이건 무료 API로 충분히 가능하다.

#### 사용자가 쓰는 부분

- 논리 평가: `논리대로 맞았다` / `결과만 맞았다` / `논리는 맞았는데 결과가 안 나왔다` /
  `둘 다 틀렸다`
- 서술: 무엇을 놓쳤는지, 다음에 같은 상황이면 무엇을 다르게 볼 것인지 (자유 서술)
- 이 서술은 `[사용자]` 저작으로 표기되며, 이후 회고 리포트(§3.9)의 원재료가 된다

#### 회고록을 강요하지 않는다

- 판정 직후 자동으로 초안이 생성되지만, **바로 쓰라고 요구하지 않는다.**
- 안 쓴 회고록이 쌓여도 개수를 세거나 배지를 띄우지 않는다. (P5)
- 대신 같은 대상으로 **새 노트를 만들 때** 조용히 꺼내 보여준다.
  "이 종목으로 지난번에 이렇게 판단하셨습니다" — 회고록이 가장 필요한 순간은
  같은 실수를 반복하려는 바로 그때다.
- 회고록이 비어 있어도 AI 초안과 지표 기록은 그대로 남으므로, 나중에 언제든 쓸 수 있다.

### 3.7 AI 어드바이저
- 노트 상세 화면에서 "지금 어떻게 해야 할까?"를 AI에게 직접 물어볼 수 있다.
- AI는 현재 가설, 시나리오별 확률, 최근 수집된 정보를 근거로 **매수/홀드/매도 등 구체적인 스탠스**를
  명확히 제시한다. 애매한 원론적 답변이나 "전문가와 상담하세요" 같은 회피는 하지 않는다.
- 제시된 의견은 노트에 `AdvisorOpinion`으로 기록되어, 이후 리마인드 시점에 "그때 AI는 이렇게 말했고,
  나는 이렇게 판단했다"를 함께 되돌아볼 수 있다. (AI 의견의 적중률도 함께 축적됨)

### 3.8 면책 고지 UI
- 앱 전역에 "모든 투자 판단과 그 결과에 대한 책임은 사용자 본인에게 있습니다"를 상시 노출한다.
  - 온보딩 시 1회 명시적 동의
  - AI 의견/리서치 카드 하단에 고정 문구
  - 앱 전역 푸터 또는 설정 화면
- 이 UI 레이어가 면책을 전담하므로, AI 프롬프트에는 면책·회피 관련 제약을 넣지 않는다.

### 3.9 회고 리포트 & 학습 (장기 로드맵)
- 회고록이 쌓이면 개인의 판단 패턴을 분석한다.
- "결과가 맞은 8건 중 3건은 논리가 틀렸다", "나는 늘 6개월 빠르게 예상한다" 같은 인사이트.
- 적중률만 보여주는 것은 금지한다. 적중률은 운을 실력으로 포장하는 지표다.
  **논리 정확도와 결과 정확도를 항상 분리해서 보여준다.**

## 4. 사용자 플로우 (핵심 시나리오)

1. 사용자가 관심 종목에 대해 투자 노트를 작성 — 가설 + 시나리오(시점 포함) 입력
2. AI가 초기 리서치를 수행해 참고할 만한 배경 자료를 정리해서 첨부
3. 시스템이 리마인드 일정을 자동 생성
4. 시간이 지나며 AI가 지속적으로 관련 뉴스를 모니터링, 유의미한 소식은 즉시 카드로 정리해 노트에 첨부
5. 리마인드 시점이 되면 알림 → 사용자는 "과거 나의 관점 + 그동안의 새 정보"를 한 화면에서 확인
6. 사용자는 시나리오 확률을 조정하거나, 시나리오의 결과를 정하거나, 새 시나리오를 추가
7. 필요하면 AI 어드바이저에게 "지금 어떻게 해야 할까?"를 물어 구체적인 매수/홀드/매도 의견과
   근거·철회 조건을 받고, 그 의견을 노트에 기록
8. 판단 시점이 되거나 지표가 달성되면 결과를 확인한다 — 예상한 일이 일어났는가
9. 결과가 확정되면 **회고록**이 열린다. AI가 근거 항목을 사후 조사하고 벤치마크와 대비한
   초안을 만들어 두면, 사용자가 "제대로 맞춘 것인지 소 뒷걸음질인지"를 판단해 서술한다
10. 같은 대상으로 새 노트를 만들 때 과거 회고록이 조용히 소환된다

```

     ├─ thesis_detail: text

     ├─ sources: [Source]  (사용자가 첨부한 근거 자료)

     ├─ remind_schedule: ReminderRule
     ├─ research_items: [ResearchItem]  (AI가 수집)
     ├─ advisor_opinions: [AdvisorOpinion]  (AI가 제시한 액션 의견)
     ├─ conversation: Conversation  (노트를 만들어낸 원본 대화, 수정·삭제 불가)
     ├─ color: string  (홈 타임라인에서 노트를 식별하는 고정 색상)

Conversation (원본 대화 — 수정·삭제 불가)
 ├─ note_id
 └─ messages: [{ role: user|assistant, content, created_at }]

ContentBlock (노트 본문을 구성하는 블록)
 ├─ note_id, section: thesis|scenario|...
 ├─ content: text
 ├─ authorship: ai|user          ← user일 때만 UI에 [사용자] 표기
 ├─ quoted_from: message_id (nullable, 사용자 발화 직접 인용 시)
 └─ derived: boolean             AI가 해석해서 만든 값인지 (예: "내년 상반기" → 날짜)

Scenario
 ├─ note_id
 ├─ name, description
 ├─ target_timeframe: { type: date|range, value }
 ├─ trigger_conditions: text

 ├─ status: active|pending_judgment|confirmed|rejected
 ├─ status_reason (결과를 그렇게 정한 이유)
 ├─ is_residual: boolean  (`그 외 예상 못한 전개`. 삭제 불가, 최소 5%)
 ├─ indicators: [Indicator]        (결과 지표 — 자동 추적)
 ├─ premises: [Premise]            (근거 항목 — 회고 때 검증)
 ├─ indicator_logic: all|any|at_least   (기본 all)
 ├─ indicator_threshold: int            (at_least일 때 M)
 └─ review: Review (nullable)      (결과 확정 후 생성)
 └─ timeframe_reset_history: [{ from, to, reset_at, reason }]
      (시점을 다시 잡은 기록 — 회고용. 카드나 홈에는 드러내지 않음)

Indicator (판단 지표)
 ├─ scenario_id
 ├─ type: numeric|event          (수치형 / 사건형)
 ├─ series: { provider: fred|ecos|kis|manual, code, label }
 │     예) { provider:"fred", code:"DFF",        label:"미국 기준금리" }
 │         { provider:"kis",  code:"005930.KS",  label:"삼성전자" }
 ├─ comparator: gte|lte|between|change_pct   (numeric일 때)
 ├─ target_value / target_range / baseline_date
 │   ※ 관측 규칙은 필드가 아니다. 시스템 전체가 `기간 중 한 번이라도 닿으면 달성,
 │     장중 포함`으로 고정이므로 지표마다 저장할 것이 없다.
 ├─ status: not_met|met
 ├─ met_at: date (nullable)
 ├─ progress: float  (목표까지 얼마나 왔는지 0~1. 부분 달성 표시용)
 └─ edit_history: [{ field, from, to, edited_at, reason }]
       (사후에 목표값을 유리하게 낮추는 것을 막기 위한 이력. 복기 화면에 노출된다)

Premise (근거 항목 — 내 논리의 중간 고리)
 ├─ scenario_id
 ├─ statement: text        사용자가 말한 그대로. 수치화하지 않는다
 │     예) "HBM 공급 부족이 2026년 내내 이어진다"
 ├─ order: int             논리 사슬에서의 순서 (A → B → C)
 ├─ linked_indicator_id: (nullable)
 │     마침 FRED/ECOS로 추적 가능한 경우에만 연결된다. 대부분 null이다
 └─ verification: (회고 시 AI가 채운다)
      ├─ verdict: happened|did_not_happen|unverifiable
      ├─ summary: text
      └─ sources: [{ title, url, published_at }]

Review (회고록 — 이 앱의 최종 산출물)
 ├─ scenario_id
 ├─ outcome: confirmed|rejected        §3.4의 판정 결과 (결과 축)
 ├─ logic_verdict: (사용자가 정함 — 논리 축)
 │     logic_held        논리대로 맞았다
 │     outcome_only      결과만 맞았다 (소 뒷걸음질)
 │     logic_only        논리는 맞았는데 결과가 안 나왔다
 │     both_wrong        둘 다 틀렸다
 ├─ ai_draft: text                     AI가 자료조사 후 생성한 초안
 ├─ benchmark_comparison: {            "그냥 시장이 올라서" 여부 판별용
 │     scenario_return, index_return, sector_return, period
 │   }
 ├─ user_narrative: text               [사용자] 저작. 무엇을 놓쳤고 다음엔 무엇을 다르게 볼지
 ├─ drafted_at / written_at (nullable) 초안 생성 시점 / 사용자가 쓴 시점
 └─ status: draft_ready|written        안 쓴 채로 남아 있어도 압박하지 않는다

IndicatorSnapshot (일별 관측값 — 전역 캐시)
 ├─ provider, code, date        ← (provider, code, date)가 유니크 키
 ├─ close: number          판정과 차트의 기준
 ├─ high / low: number     (nullable) 장중 터치 판정과 차트의 띠에 쓰임. 거시 지표는 null
 └─ fetched_at
   ※ 사용자별로 저장하지 않는다. 같은 종목·지표는 모든 사용자가 공유한다.

Source (사용자 첨부)
 ├─ type: link|text|file|image
 ├─ content / url
 └─ created_at

ResearchItem (AI 수집)
 ├─ note_id, scenario_id (nullable, 노트 전체와 연관될 수도 있음)

 ├─ relation: supports|contradicts|neutral
 ├─ relevance_score
 └─ user_feedback: adopted|dismissed|none

AdvisorOpinion (AI의 액션 의견)
 ├─ note_id

 ├─ referenced_research: [research_item_id]

 ├─ type: interval|scenario_deadline|pending_judgment|event_triggered

 └─ current_interval_weeks: int  (연속 미열람 시 2배씩 증가, 최대 12주)
```

```
   ├─ Reminder Curation Agent    ├─ 상태 전이 시 리마인드 트리거
   ├─ Thesis Builder Agent       └─ 지표 카탈로그 검색
   │    └─ 대화 → 지표 후보 제안       (사용자 표현 → 실제 계열 코드 매핑)
   ├─ Review Agent
   │    ├─ 근거 항목 사후 조사
   │    └─ 벤치마크 대비 수익률 계산
   └─ Advisor Agent
        │                              │
        ▼                              ▼
[Data Store]
   ├─ RDB (Notes, Scenarios, Indicators, Premises, Reviews, IndicatorSnapshot, Users)
   ├─ Vector DB (노트/뉴스 임베딩 → 유사도 기반 관련 뉴스 매칭, 향후)
   └─ Object Storage (첨부 파일/이미지)
        │
        ▼
[External Integrations]
   ├─ 뉴스/검색 API
   ├─ 시세·거시지표 API (FRED / 한국은행 ECOS / 한국투자증권)
   └─ 알림 (Push / Email)
```

**Indicator Service를 별도 축으로 두는 이유**: AI 리서치와 완전히 다른 성질의 작업이다.
리서치는 비결정적이고 온디맨드이며 비용이 LLM 호출에 비례하지만, 지표 수집은 결정적이고
스케줄 기반이며 비용이 외부 API 쿼터에 걸린다. 실패 시 재시도 전략도 다르다.
(지표는 하루치를 놓쳐도 다음 배치에서 소급 수집하면 되지만, 리서치는 그렇지 않다.)

### 외부 데이터 소스 선정

> 아래 수치는 2026년 8월 기준 확인값이다. 무료 티어 정책은 자주 바뀌므로 착수 시 재확인할 것.

**채택**

| 소스 | 범위 | 조건 | 비고 |
|---|---|---|---|
| **FRED** | 미국·글로벌 거시 (금리, CPI, 실업률, GDP) | 무료, API 키 발급 | 공공 데이터, 상용 이용 제약 없음 |
| **한국은행 ECOS** | 한국 거시 (기준금리, 물가, 환율, 수출입) | 무료, API 키 발급 | 공공 데이터 |
| **한국투자증권 Open API** | 국내·해외 주식 및 지수 시세 | 이용료 없음, 계좌 개설 필요 | REST + WebSocket, 초당 20건 제한, 리눅스 서버에서 동작 |

**배제 — 이유가 각기 다르다**

| 소스 | 배제 사유 |
|---|---|
| **yfinance** | Yahoo의 비공식 엔드포인트를 긁는 방식이고, Yahoo API 약관은 수익을 얻는 용도의 사용을 금지한다. 개인 학습·프로토타입용이며 이 앱이 유료화되는 순간 쓸 수 없다. 엔드포인트가 예고 없이 바뀌어 깨지는 문제도 있다. |
| **Alpha Vantage** | 무료 티어가 **하루 25요청**(분당 5요청)으로 축소되어 실사용이 불가능하다. 지표 수십 개를 매일 수집하는 이 앱의 요구를 충족할 수 없다. |
| **Finnhub** | 무료 티어(분당 60요청)가 **비상업 용도로 제한**된다. 유료화 시 사용 불가라 yfinance와 같은 문제를 안는다. |
| **Polygon.io** | 무료 플랜이 분당 5요청 + 장 마감/15분 지연 데이터로 좁고, 무료 티어 유지 여부에 대한 정보가 엇갈린다. 유료 전환 시 후보로 재검토. |
| **키움증권 Open API** | Windows 32bit COM 객체 방식이라 리눅스 백엔드에서 쓸 수 없다. |

**프로토타입 단계의 예외**: 개발 초기에 `yfinance`로 빠르게 데이터 파이프라인을 검증하는 것은
가능하다. 단 **출시 전 반드시 교체한다는 전제**로만 쓰고, 데이터 소스 인터페이스를 추상화해
교체 비용을 낮춰 둔다. 프로토타입 코드가 그대로 상용에 남는 것이 가장 흔한 사고다.

**설계상 유리한 점**: 이 앱은 **실시간 시세가 필요 없다.** 지표는 종가 기준으로 하루 1회
평가하면 충분하고, 거시 통계는 월·분기 단위로 갱신된다. 실시간 요구가 없으면 위 무료 소스만으로
충분히 상용 서비스를 운영할 수 있다. 이것이 이 기능의 비용 구조를 결정한다.

## 7. AI 기능 상세 설계

### 7.1 Research Agent
- **입력**: 노트의 target, thesis_summary, 각 시나리오의 description/trigger_conditions
- **동작**:
  1. 키워드/엔티티 추출
  2. 웹/뉴스 검색 실행
  3. 검색 결과 중 관련성 높은 것만 필터링 (relevance_score 산출)
  4. 각 결과를 요약하고, 어떤 시나리오를 지지/반박하는지 분류
  5. 노트에 ResearchItem으로 저장, 유의미도가 높으면 즉시 알림 트리거
- **실행 주기**: 기본 주기(예: 매일 1회) + 사용자 온디맨드 요청

### 7.2 Reminder Curation Agent
- 여러 경로에서 발생한 리마인드(정기/시점/새 정보)를 모아 우선순위를 정하고 한 번에 묶어 보내,
  알림이 과도해지지 않게 한다
- 리마인드 시 "과거 관점 요약 + 새 정보 요약 + 재평가 유도 질문" 형태로 콘텐츠 구성

### 7.3 Thesis Builder Agent (대화형 노트 작성)
노트 작성의 보조가 아니라 **작성 수단 그 자체**다. 대화를 통해 필수 항목을 확보하고
노트를 작성한다.

- **대화 단계**: 대상 파악 → 관심 이유 → 핵심 가설 → 반대 시나리오 → 판단 시점 → 확인 지표
- **질문 예시**
  - "반대로 흘러간다면 어떤 모습일까요?"
  - "이건 언제쯤 판가름 날까요?" (시점 확보 — 가장 집요하게)
  - "무엇을 보면 그렇게 되고 있다는 걸 알 수 있을까요?"
  - "이 판단이 틀렸다는 건 뭘로 알 수 있을까요?" (반증 가능성)
- **턴 수 목표: 5~8턴.** 심문처럼 느껴지면 작성을 포기하게 되므로 길이 관리가 중요하다.
- **노트 생성**: 산문이 아니라 **구조화된 객체**를 반환한다. 렌더링은 클라이언트가 한다.
  채우는 칸과 각 칸의 규칙은 §3.1 '노트 생성 계약'에 정의되어 있다.
  - 대화에 없는 내용을 채워 넣지 않는다. 빈 칸은 비운 채로 반환한다.
  - 근거 항목(`premise.statement`)은 사용자의 말을 다듬지 않고 그대로 옮긴다.
  - 시점 문자열("내년 상반기")을 날짜로 해석했으면 해석 결과를 함께 반환해
    미리보기에서 확인받는다.
- **스키마 위반 처리**: 시나리오가 1개만 나왔거나 시점을 못 뽑았으면 **지어내지 않고**
  해당 칸을 비운 채 반환한다. 미완성 노트로 저장되고 화면에 무엇이 비었는지 표시된다.
- **원본 대화 보존**: 대화 전문을 수정·삭제 불가로 저장. AI가 노트를 쓰는 구조이므로,
  "실제로 내가 한 말"에 대한 접근 경로가 반드시 유지되어야 한다.

### 7.4 Review Agent (회고 초안 작성)

시나리오 결과가 확정되면 실행된다. **이 앱의 최종 산출물을 만드는 에이전트**다.

- **입력**: 시나리오의 근거 항목(`Premise`) 목록, 결과 지표 판정 결과, 대상 종목, 검증 기간
- **동작**:
  1. 각 근거 항목을 검색 질의로 변환해 해당 기간의 뉴스·공시·실적 발표를 조사
  2. 항목별로 `실제로 일어남` / `일어나지 않음` / `확인 불가`로 분류하고 출처를 붙인다
  3. **벤치마크 대비 수익률을 계산**한다 — 대상 종목 / 시장 지수 / 업종 지수를 같은 기간으로
     비교. 종목이 20% 올랐어도 업종이 25% 올랐다면 내 논리와 무관하게 움직인 것이다.
     이 계산만으로도 "그냥 시장이 올라서"를 상당 부분 걸러낼 수 있고, 무료 API로 가능하다.
  4. 결과 지표가 달성됐다면 그 결과의 **실제 원인으로 지목되는 다른 설명들**을 수집한다
  5. 초안 서술 생성
- **원칙**: **"이건 운이었습니다"라고 확정하지 않는다.** 사실과 대비만 제시하고 판단은
  사용자에게 넘긴다. AI가 논리의 옳고 그름을 선언하면 사용자는 스스로 생각하지 않게 되고,
  그러면 이 앱은 판단력을 기르는 도구가 아니라 대신 판단해주는 도구가 된다.
- `확인 불가`를 숨기지 않는다. 자료를 못 찾았으면 못 찾았다고 말한다.

### 7.5 Advisor Agent (직접 의견 제시)
- 사용자가 요청하면(또는 리마인드/리서치 결과와 함께) 현재 가설·시나리오·최신 정보를 종합해
  **명확한 액션 의견**을 제시한다.
  - 매수 / 추가매수 / 홀드 / 일부익절 / 전량매도 등 구체적 스탠스
  - 근거가 되는 시나리오와 정보, 목표 가격대·기간(가능한 경우)
  - 이 의견이 틀렸다고 판단할 조건(손절/철회 트리거)
- **프롬프트 원칙**: "투자 조언을 할 수 없다", "전문가와 상담하라" 류의 회피성 문구를 넣지 않는다.
  근거가 부족하면 회피하는 대신 "무엇을 더 알면 판단이 명확해지는지"를 말한다.
- **일관성 체크**: 사용자의 과거 가설과 현재 제시하는 의견이 상충하면 그 사실을 명시적으로 지적한다.
  (메멘토 컨셉의 핵심 — 과거의 나와 지금의 판단을 대조)
- 면책 문구는 AI 응답 본문이 아니라 UI 레이어에서 일괄 처리한다. (AI 출력에 매번 면책을 섞으면
  가독성과 신뢰도가 떨어지므로)

## 8. MVP 범위

투자 판단 보조라는 핵심 가치를 가장 빠르게 검증할 수 있는 범위로 제한한다.

**MVP 포함:**
- 홈: 가까운 미래 판단 시점 타임라인 + 리마인드 피드
- 대화형 노트 작성 (Thesis Builder Agent) → 노트 초안 생성 → 미리보기·수정 → 저장
- 원본 대화 전문 보존 및 열람
- 노트 상세: 좌(나의 관점) / 우(새 정보) 분리 레이아웃, 시나리오 보드
- 시나리오별 확률 입력(합 100%, `그 외 예상 못한 전개` 포함) 및 변경 이력 조회(리스트)
- 시나리오 상태 변화 및 네 가지 선택지
- 결과 지표 설정 (노트 저장 후 2단계 폼, 건너뛰기 가능), 일 1회 수집·평가, 달성 현황 표시
- 지표 추이 차트 (노트 상세 축약형 + 결과 확인 전체형)
- 근거 항목 기록 (수치화 없이 서술로)
- 회고록: AI 초안(근거 항목 사후 조사 + 벤치마크 대비) + 사용자 서술
- 지표 데이터 소스: FRED + ECOS + 한국투자증권
- 리마인드 상세 3단 화면 (과거의 나 → 그동안의 일 → 지금은?)
- 기본 주기 리마인드 + 시점 기반 리마인드, 이메일 알림
- AI 리서치: 온디맨드 실행 (노트 상세 화면 "지금 다시 조사하기") — 자동 주기 실행은 이후 단계
- 수집한 정보에 뒷받침/어긋남 표시, 사용자 피드백(반영/무시)
- AI 어드바이저: 온디맨드로 매수/홀드/매도 스탠스와 근거를 받아보고 `AdvisorOpinion`으로 기록
- `[사용자]` 저작 표기
- 면책 고지 UI (온보딩 동의 + 전역 상시 노출)
- 반응형 웹 (데스크톱 전체 → 모바일 리마인드 확인 플로우 순으로 구현)

**MVP 제외 (이후 단계로 이연):**
- 자동 주기적 백그라운드 리서치 크롤링, 이벤트 기반 즉시 알림
- 벡터 검색 기반 정교한 관련성 매칭
- 확률 변화 그래프 시각화 (MVP는 이력 리스트로 대체)
- 회고/패턴 분석 리포트
- PWA 푸시 알림, 네이티브 모바일 앱, 소셜/공유 기능
- 시세 연동, 포트폴리오 관리 기능 (보유 수량·단가 등 실제 포지션 입력 일체)

| Phase 2 | AI 리서치 자동화 | 주기적 뉴스 모니터링, 이벤트 기반 알림, 관련성 판단 고도화, PWA 푸시 |
| Phase 3 | 인사이트 강화 | 시나리오 확률 히스토리 시각화, 지표 추이 차트, 회고 리포트(논리 정확도 vs 결과 정확도), 노트 간 거시 변수 연결 |
| Phase 4 | 확장 | 네이티브 모바일 앱, 시세/공시 연동, 개인화 학습(판단 패턴 분석) |

## 10. 리스크 및 고려사항

- **투자자문 규제 리스크**: AI 프롬프트 자체는 매수/매도 의견을 자유롭게 낼 수 있도록 열어두는 대신,
  "최종 투자 판단과 그 책임은 사용자 본인에게 있다"는 면책 고지를 UI 전반(온보딩, 노트/리서치
  화면, 추천 카드 등)에 상시 노출한다. 다만 이는 제품 방향에 대한 결정이며, 실제 서비스 지역/약관에
  따라 투자자문업 관련 법적 리스크가 있을 수 있으므로 정식 출시 전 법률 검토가 필요하다.
- **정보 신뢰성**: AI가 수집한 뉴스/요약의 출처를 항상 함께 제공하여 사용자가 검증 가능하게 함.
- **알림 피로 / 죄책감**: 리마인드가 과도하거나 부채감을 주면 앱 자체를 안 열게 된다.
  미룬 횟수·달성률·스트릭·배지 카운트 같은 압박 장치는 제품 차원에서 금지하고, 반복해서 열리지
  않는 리마인드는 벌 대신 노출 빈도를 자동으로 낮춘다. (UX 설계 원칙 P5)
- **데이터 프라이버시**: 개인의 투자 관점/포지션은 민감 정보이므로 저장/전송 시 보안 설계 필요.
- **AI 비용**: 리서치 에이전트의 실행 빈도가 늘어날수록 API 비용 증가 → 사용자별/노트별 실행 정책 필요.
- **지표 데이터 소스 의존**: 무료 API의 티어 정책은 예고 없이 축소된다(Alpha Vantage가 하루
  500요청에서 25요청으로 줄어든 것이 실례다). 데이터 소스를 추상화 계층 뒤에 두어 교체 가능하게
  설계하고, 특정 제공자에 종속되는 코드를 만들지 않는다.
- **회고 리서치의 품질**: 근거 항목이 산업 특화 내용일수록 AI가 자료를 못 찾을 가능성이 높다.
  `확인 불가`가 대부분인 회고록은 가치가 없다. 벤치마크 대비 수익률은 언제나 계산 가능하므로,
  최소한 그것만이라도 항상 제공되도록 설계한다.
- **근거 항목이 비는 문제**: 사용자가 논리 없이 "느낌"으로 산 경우 근거 항목을 못 적는다.
  이 경우 회고할 대상 자체가 없다. AI가 대화에서 이를 확보하지 못하면 회고 기능 전체가
  형식만 남는다. 대화 설계의 품질이 곧 이 기능의 품질이다.
- **2단계 지표 설정의 이탈률**: 건너뛸 수 있게 만든 대가로 대부분의 사용자가 지표를 영영
  설정하지 않을 수 있다. 그래도 앱은 동작하지만 자동 판정이라는 차별점이 사라진다.
  2단계 진입률과 완료율을 초기 지표로 측정하고, 낮으면 1단계 말미에 최소 1개만 받는
  절충안을 검토한다.
- **지표 사후 조작**: 목표값을 나중에 유리하게 낮추면 복기가 무의미해진다. 수정 이력을 반드시
  보존하고 복기 화면에 노출한다.

## 11. 확정된 결정 사항

UX 설계 과정에서 확정된 항목들. 상세 근거는 [`ux-design.md`](./ux-design.md) 참조.

| 항목 | 결정 |
|---|---|
| 플랫폼 | 반응형 웹. 데스크톱 전체 → 모바일 리마인드 확인 플로우 순으로 구현 |
| 홈 화면 | 리마인드 피드(우선순위 순) 위, 세로 타임라인(시간 순) 아래. 노트 목록은 별도 탭 |
| 타임라인 축 | 데스크톱·모바일 모두 세로. 화면 폭에 따라 여백만 달라진다 |
| 노트 작성 | AI와의 대화 → AI가 노트 작성. 폼 입력 방식은 쓰지 않음 |
| 동시 관리 노트 수 | 10개 내외 전제. 폴더/태그 없이 단순 리스트 + 검색 |
| 리마인드 강제성 | 없음. 미룸 횟수 기록·노출 금지, 스트릭/달성률 금지 |
| 누가 쓴 글인지 | AI가 쓴 글은 표시 없음, 사용자가 쓴 부분에만 `[사용자]` 표기 |
| 내 사고 ↔ 외부 정보 | 공간적으로 분리. 리마인드 화면에서만 의도적으로 대비 |
| 포지션 입력 | MVP 제외 (관점 기록과 자산 관리는 별개 제품으로 봄) |
| 확률 표현 | 갈래 안에서 합 100%, 5% 단위로만 조정. 구성비는 도넛, 변화는 막대 |
| AI 의견 강도 | "적극 제안" 고정. 매수/매도 의견에 제약 없음 |
| 반증 가능성 | 모든 시나리오에 수치 조건(판단 지표)을 필수로 붙인다 |
| 결과 vs 논리 | 결과는 수치 지표로 자동 판정, 논리는 회고록에서 AI 조사 + 사용자 서술로 검증 |
| 근거 항목 | 수치화 불가해도 서술로 반드시 기록. 회고 때 AI 조사의 대상이 된다 |
| 회고록 | 판정 확정 시 AI 초안 자동 생성. 작성 강요·미작성 카운트 없음 |
| 작성 단계 | 1단계 대화(논리) + 2단계 폼(수치 설정)으로 분리. 2단계는 건너뛸 수 있음 |
| 근거 항목 수집 시점 | 반드시 1단계 대화 중. 나중에 물으면 사후 합리화된 답만 나온다 |
| 지표 결합 | 전부(AND) / 하나라도(OR) / N개 중 M개 — AND 강요하지 않음 |
| 지표 판정 | 앱은 제안만 한다. 자동으로 적중/실패를 확정하지 않는다 |
| 운/실력 구분 | AI는 사실과 벤치마크 대비만 제시하고, 운이었는지는 사용자가 판단한다 |
| 시세 데이터 | 실시간 불필요. 일 1회 종가 기준 배치 + 전역 캐시. 미마감 당일은 저장·표시 안 함 |
| 지표 시각화 | 기록선·목표선·그 사이 띠·추이·남은 기간을 한 그림에. 기간 고정, 기술 지표 없음 |
| 관측 규칙 | 사용자가 고르지 않음. `한 번이라도 닿으면 달성 · 장중 포함`으로 시스템 고정 |

## 12. 오픈 이슈 (추후 논의 필요)

- 어떤 자산군까지 지원할지 (주식/코인/부동산/거시경제 테마 등)
- 지표 카탈로그를 어디까지 미리 등록할지. 사용자가 말한 표현("유동성")을 실제 계열로 매핑하는
  일이 이 기능의 사용성을 좌우하는데, 전부 AI에 맡길지 사전 사전(辭典)을 만들지 미정
- 암호화폐 지표를 넣을 경우의 데이터 소스 (현재 채택한 셋으로는 커버되지 않음)
- 지표 달성 알림을 이벤트 기반 즉시 알림으로 볼지, 일일 배칭에 포함할지
- 벤치마크를 무엇으로 잡을지 (코스피/코스닥/S&P500은 쉬우나 업종 지수는 매핑이 필요)
- 회고록을 안 쓴 채로 오래 두면 AI 초안의 자료 링크가 만료될 수 있다. 초안 생성 시점에
  본문을 스냅샷으로 보관할지 검토
- 뉴스/데이터 소스 API 선정
- 무료/유료 정책 (AI 리서치 실행 횟수 제한 등)
- 노트 작성 대화의 적정 턴 수 (목표 5~8턴, 실측 필요)
- 타임라인 구간 경계값(`이번 주 / ~1개월 / ~3개월 / ~6개월 / 그 이후`)의 실사용 적합성
- 노트 간 거시 변수 연결을 언제 도입할지 (가치는 크나 내비게이션 단순성과 충돌)
- AI 의견 강도를 사용자가 조절 가능하게 할지
