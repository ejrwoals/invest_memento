# Investment Memento — 개발 계획 문서

## 0. 한 줄 요약

> 영화 <메멘토>처럼, 과거의 나(투자 판단의 근거와 가설)를 잊지 않도록 기록하고
> 주기적으로 리마인드하며, AI가 그 가설에 영향을 줄 새로운 정보를 계속 조사해주는
> **투자 판단 보조 노트 앱**.

---

## 1. 배경 및 문제의식

- 개인 투자자는 과거에 스스로 세웠던 분석/가설/전제를 시간이 지나면서 잊어버린다.
- 그 결과 눈앞의 뉴스, 단기 변동성, 감정에 휩쓸려 과거의 논리와 모순되는 판단을 반복한다.
- "내가 왜 이 종목/자산을 샀는지", "그 판단의 전제 조건이 아직 유효한지"를 스스로
  추적하지 못하는 것이 어리석은 투자 판단의 핵심 원인 중 하나다.
- 필요한 것은 단순한 메모장이 아니라, **과거의 가설을 잊지 않게 강제로 리마인드**하고
  **그 가설이 여전히 유효한지 판단할 근거(뉴스/데이터)를 계속 모아주는 보조 장치**다.

## 2. 핵심 컨셉

### 2.1 메멘토 원칙

영화 속 주인공이 문신과 메모로 기억을 대체하듯, 이 앱은 사용자의 "과거 투자 관점"을
잃어버리지 않도록 구조화해서 저장하고, 시간이 지남에 따라 사용자에게 능동적으로
다시 보여준다.

1. **기록(Record)**: 판단 당시의 근거, 조사 자료, 관점을 시나리오·시점과 함께 구조화하여 저장한다.
2. **리마인드(Remind)**: 주기적으로 과거 기록을 다시 보여줘서 현재 판단이 과거 논리와
   일관적인지 스스로 점검하게 한다.
3. **추적(Track)**: AI가 각 가설/시나리오와 관련된 새 뉴스·데이터를 지속적으로 조사해서
   요약해준다.
4. **재평가(Re-evaluate)**: 시간이 지나며 어떤 시나리오의 발생 확률이 올라가고, 어떤
   시나리오는 이제 접어도 되는지 사용자가 판단하도록 돕는다.

### 2.2 가설-시나리오 중심 설계

이 앱에서 "노트"는 단순 텍스트가 아니라 **검증 가능한 구조**를 가진다.

- 하나의 투자 노트(Note)는 하나의 투자 대상(종목/자산/테마)에 대한 **핵심 가설(Thesis)**을 가진다.
- 하나의 가설은 여러 개의 **시나리오(Scenario)**로 분기된다. (예: 낙관/중립/비관, 또는 사건 발생/미발생 등)
- 하나의 가설은 하나 이상의 **갈래(Galae)**로 검증된다. 갈래는 질문 하나이고,
  **시나리오(Scenario)**는 그 질문에 대한 배타적인 답들이다.
- 갈래는 다음을 가진다.
  - **질문** — 시나리오들이 무엇을 놓고 갈리는지
  - **판단 시점** — 언제 답이 나오는지. 갈래에 하나뿐이다 (§3.4)
- 각 시나리오는 다음을 가진다.
  - 답 (결과로 쓴다) + 설명 (그렇게 되는 경로와 이유)
  - **판정 방법** — `auto`(공개 수치로 확인) / `manual`(사람이 확인) /
    `complement`(나머지가 아니면 이 답). 검증할 수 있는 명제는 전부 시나리오이고,
    수치 조건은 시나리오 아래 딸린 별개의 것이 아니다 (§2.3)
  - 최초 추정 확률(선택), 그리고 시간에 따라 갱신되는 확률
- **근거 항목**은 갈래가 아니라 노트(가설)에 붙는다. 내 논리가 참이라면 먼저 일어나야
  하는 일을 수치화하지 않고 서술로 적는다 (§2.3)
- 시점을 명시하기 때문에, 그 시점이 다가오거나 지나면 앱이 "이 시나리오 재검토 시점입니다"라고
  능동적으로 알릴 수 있다.

### 2.3 반증 가능성 — 결과는 숫자로, 논리는 회고로

"유동성이 풀린다" 같은 가설은 '풀린다'의 기준이 모호해서 나중에 맞았는지 틀렸는지 판정할 수
없다. **판정할 수 없는 가설은 복기할 수 없고, 복기가 불가능하면 이 앱은 그냥 일기장이 된다.**

따라서 시나리오를 만들 때 **그것이 맞았는지 확인할 수 있는 조건을 함께 정한다.**

#### 결과는 숫자로 판정하고, 논리는 회고로 검증한다

이 앱이 답해야 할 질문은 사실 두 개이고, 서로 성질이 다르다.

| 질문 | 검증 방법 | 시점 |
|---|---|---|
| **내가 예상한 일이 일어났는가?** | 시나리오의 판정 방법대로 (auto / manual) | 판단 시점 도래 시 |
| **그게 내가 생각한 이유 때문이었는가?** | AI 자료조사 + 사용자 서술 | 판정 후 회고록(§3.6) |

두 번째 질문을 수치로 풀려는 시도는 현실적으로 실패한다. "DRAM 현물가", "HBM 매출 비중"
같은 진짜 중요한 중간 고리들은 유료 산업 데이터라 무료 API로 가져올 수 없다. 억지로
가져올 수 있는 것만 쓰면 결국 주가·지수로 수렴해 동어반복이 된다.

그래서 **자동 판정은 결과 축만 담당하고, 논리 검증은 회고 단계로 넘긴다.**

#### 검증할 수 있는 명제는 전부 시나리오다

`삼성전자가 12월 말까지 95,000원을 넘는다`와 `삼성이 올해 안에 HBM4 공급사로 진입한다`는
성질이 같다. 둘 다 참·거짓이 갈리는 명제이고, 둘 다 반대편이 있다. 다른 것은 **답이
나오는 방식**뿐이다 — 앞은 기계가 확인하고 뒤는 사람이 확인한다.

그래서 수치 조건을 시나리오 아래 딸린 별개의 것으로 두지 않는다. **수치 질문도 갈래가 되고,
그 답도 시나리오가 된다.** 시나리오는 자기가 어떻게 판정되는지를 스스로 갖는다.

| 판정 방식 | 언제 | 예 |
|---|---|---|
| `auto` | 질문 자체가 공개된 수치에 관한 것일 때 | `기준금리가 3.5% 이하로 내려간다` · `WTI가 70달러 아래로 간다` |
| `manual` | 사실이지만 계열로 살 수 없을 때 | `HBM4 공급사로 진입한다` · `공화당이 중간선거에서 이긴다` |
| `complement` | 다른 답들이 모두 아니면 이 답일 때 | `진입하지 못한다` · `그 외 예상 못한 전개` |

이 정리로 두 가지가 사라진다.

- **사건형 지표가 없어진다.** `종전·휴전 합의가 공식 발표된다`를 예/아니오 지표로 두고
  사용자가 표시하게 하던 것은, 확률만 없는 시나리오였다. 같은 것을 두 이름으로 부르고
  있었으므로 하나로 접는다.
- **지표를 AND·OR·N중M으로 묶는 장치가 없어진다.** 한 답에 조건이 둘 이상 필요하다는 것은
  대개 질문이 둘이라는 신호다. 갈래를 나누면 각각에 확률을 매길 수 있게 되고, 회고에서도
  어느 쪽이 맞았는지 따로 드러난다. 불린 조합으로 뭉쳐 두면 그 구분이 사라진다.

#### 관련 없는 수치가 판정하게 두지 않는다

이전 설계는 `진입한다`라는 시나리오 밑에 `삼성전자 95,000원 이상`을 판정 근거로 달았다.
그러나 **주가가 올랐다고 수주를 받은 것이 아니다.** 이 앱은 "결과는 맞았는데 논리가 맞아서였나"를
가리려고 만든 것인데, 관련 없는 수치를 판정에 넣으면 소 뒷걸음질을 잡기는커녕 판정 단계에서
미리 섞어버린다.

그러므로 자동 판정은 **질문이 실제로 그 수치에 관한 것일 때만** 쓴다. 관련은 있지만 답이
아닌 수치는 판정에서 빼고 `지켜보는 수치`로 둔다 — 목표값도 달성 판정도 없이 추이만 보여준다.
차트는 여기 붙는다.

주가가 궁금하면 그것을 별도의 갈래로 세우면 된다. `12월 말까지 95,000원을 넘는가`에
확률을 매겨두면, 판단 시점에 `진입은 못 했는데 주가는 넘었다`가 화면에 그대로 남는다.
소 뒷걸음질의 정확한 모양이다.

#### 시나리오의 판정 조건 구성 요소

```
auto 판정 = 데이터 출처 + 대상 + 비교 방식 + 목표값
예) FRED · 미국 기준금리 · 이하 · 3.5%
    KIS  · 삼성전자      · 이상 · 95,000원
관측 창 = 갈래의 판단 시점 (시나리오가 따로 갖지 않는다)
```

- **비교 방식**: 이상 / 이하 / 범위 안 / 변화율(기준일 대비 ±N%) — 사용자가 고른다.
- **관측 규칙**: **사용자가 고르지 않는다. 시스템이 하나로 고정한다.**
- 한 시나리오의 auto 조건은 **하나뿐이다.** 둘이 필요하면 질문이 둘이다.

#### 관측 규칙은 하나로 못 박는다

> **판단 시점까지 기간 중 한 번이라도 목표에 닿으면 달성. 장중에 스친 것도 인정한다.**

"장중 터치를 인정할지", "종가로 며칠 연속이어야 하는지"를 사용자에게 물으면, 모든 사용자가
조건을 만들 때마다 **자기가 답할 준비가 안 된 질문** 앞에 선다. 대부분은 그 차이를 생각해본
적이 없고, 고민하다 설정 자체를 포기한다.

관대한 쪽으로 고정해도 잃는 것이 없다. **앱은 어차피 판정하지 않고 제안만 하기 때문이다.**
기준이 관대하다는 건 "앱이 더 일찍 묻는다"는 뜻일 뿐이고, 장중에 잠깐 스친 것을 적중으로
볼지는 결과 확인 화면에서 사용자가 정한다. 오히려 엄격한 기준은 **닿았는데도 앱이 아무 말을
안 하는** 상황을 만들어 더 나쁘다.

- 거시 계열에는 장중이라는 개념이 없다. 발표된 값 하나가 그날의 값이고, 같은 규칙이
  그대로 적용된다.
- 이 규칙은 화면에 **설정 항목이 아니라 안내 문장**으로 한 번 적는다.

#### 근거 항목은 여전히 다른 축이다

시나리오가 결과 축이라면 **근거 항목**은 논리 축이다. `내 논리가 참이라면 그 전에 먼저
일어나야 하는 일`을 서술로 적어두는 것이고, 대부분 계열로 살 수 없다.

- **수치로 가져올 수 없어도 반드시 적어둔다.** 자동 추적이 목적이 아니라, "내가 무엇을
  전제로 이 판단을 했는가"를 남기는 것이 목적이다. 시간이 지나면 사람은 자기가 어떤
  논리로 샀는지조차 잊고 결과만 기억한다.
- 근거 항목은 **회고 시 AI 자료조사의 검색 키워드**가 된다. "HBM 매출 비중이 실제로
  올랐는가"를 AI가 뉴스·공시·실적 발표에서 찾아 근거와 함께 정리한다.
- 근거 항목 중 마침 계열로 살 수 있는 것이 있으면 `지켜보는 수치`로 올려 추이를 보여준다.
  판정하지는 않는다 — 근거가 맞았는지는 회고에서 따진다.

#### 자동 판정은 하지 않는다 — 제안까지만

**auto 조건이 달성되어도 앱이 "맞았다"고 확정하지 않는다.** 목표값은 내 논리와 무관한
이유로도 닿을 수 있고, 그걸 앱이 적중으로 처리해버리면 사용자는 틀린 논리를 옳다고 학습한다.
이 앱의 목적과 정면으로 어긋난다.

- 달성 시: "`내려간다`의 조건이 달성됐습니다. 어떻게 보시겠습니까?" → 사용자가 판단
- 기한 경과 + 미달성 시: 자동 실패 처리가 아니라 `결과 확인 필요` 상태로 전환
- 결과 확인 선택지는 세 가지다.
  `그대로 되었다` / `틀렸다` / `방향은 맞지만 시기를 다시 본다`

  여기서 묻는 것은 **"예상한 일이 일어났는가"뿐이다.** "그게 내 논리 때문이었는가"는
  자료를 조사해봐야 알 수 있으므로 이 자리에서 물으면 사용자가 답할 수 없다.
  그 질문은 회고록(§3.6)이 담당한다.

#### 목표값을 나중에 고치면 이력이 남는다

목표값을 사후에 유리하게 낮추면 이 기능 전체가 무의미해진다. 수정 자체는 허용하되,
**"처음엔 3,200이었는데 2,900으로 낮춤" 같은 변경 이력이 복기 화면에 반드시 남는다.**
원본 대화를 고치지 않는 원칙(§3.1)의 연장이다.

### 2.4 AI의 역할

AI는 판단에 필요한 정보를 모으고 정리해서 사용자가 더 나은 판단을 하도록 돕는
보조자이면서, 동시에 **적극적으로 의견을 개진하는 어드바이저**이기도 하다.

- **리서치 보조**: 노트/가설/시나리오와 관련된 최신 뉴스, 공시, 데이터를 조사해서 읽기 쉽게 요약.
- **관련성 판단**: 수집한 정보가 어떤 시나리오를 뒷받침하는지, 어긋나는지 표시.
- **리마인드 큐레이션**: 언제, 어떤 노트를, 어떤 맥락과 함께 다시 보여줄지 결정.
- **재평가 유도**: 새 정보를 답별로 갈라 보여주고 다시 배분하도록 이끈다.
  확률 숫자 자체는 제안하지 않는다 — 사용자가 낸 것 하나만 확률이다(§3.4).
- **소크라테스식 질문**: 사용자가 놓친 반대 시나리오나 리스크를 질문 형태로 환기.
- **가설 후보 제안 (Phase 2)**: 보유 종목(§3.9)에서 출발해 노트 작성 대화의 진입점을 제안.
  단, 완성된 가설 문장이 아니라 **질문까지만** — 가설은 항상 사용자의 입에서 나와야 한다.
- **직접적인 매수/매도 의견 제시**: AI 프롬프트 단에서는 매수/매도 추천, 목표가, 타이밍 의견 등을
  자유롭게 낼 수 있도록 제한을 두지 않는다. "투자 판단과 그 책임은 전적으로 사용자 본인에게
  있다"는 고지를 UI 레벨(예: 앱 전역 푸터, 리서치/추천 카드마다, 온보딩 등)에서 상시 노출하는
  것으로 책임 소재를 명확히 하고, 그 대신 AI는 판단을 흐리지 않고 소신 있게 의견을 낸다.
  즉 **면책은 UI의 책임, 유용하고 직접적인 조언은 AI의 책임**으로 역할을 분리한다.

## 3. 핵심 기능 명세

### 3.1 투자 노트 작성 — AI와의 대화 기반

노트는 폼 입력이 아니라 **AI와의 대화**로 만들어진다. 사용자는 생각나는 대로 말하고,
AI가 대화를 통해 필요한 구조를 끌어낸 뒤 노트를 작성한다. 폼을 강제하면 작성이 귀찮아져
기록 자체가 쌓이지 않고, 기록이 없으면 이 앱의 가치는 0이 되기 때문이다.

#### 작성은 두 단계로 나눈다

한 번의 대화에서 논리와 수치 설정을 모두 받으면 대화가 길어져 사용자가 이탈한다.
시나리오 2개에 목표값까지 물으면 질문이 열 번을 넘고, 이는 **작성 진입장벽을 최소화한다**는
원칙(UX §P6)과 정면으로 충돌한다. 그래서 성질이 다른 두 작업을 분리한다.

> **논리는 대화로, 수치 설정은 폼으로.**
> 대화는 "왜"를 끌어내는 데 강하고, 폼은 "얼마"를 받는 데 강하다.

| | 1단계 — 대화 | 2단계 — 확인 방법 설정 |
|---|---|---|
| 성격 | 사고를 끌어내는 일 | 기계적인 설정 작업 |
| 형식 | AI와의 자유 대화 | AI가 후보를 채워둔 폼 |
| 필수 여부 | 필수 | 건너뛸 수 있음 |
| 다루는 것 | 대상, 가설, 갈래의 질문과 시나리오, 판단 시점, 근거 항목 | auto 판정의 목표값과 비교 방식 |

#### 1단계 — 대화에서 확보할 항목

| 항목 | 필수 | 비고 |
|---|---|---|
| 투자 대상(티커/자산/테마) | 필수 | |
| 핵심 가설 | 필수 | |
| 갈래의 **질문** | 필수 | 시나리오들이 무엇을 놓고 갈리는지. `올해 안에 엔비디아 공급사로 진입하는가?` |
| 시나리오 2개 이상 | 필수 | 그 질문에 대한 답. 긍정/부정 등 대칭적 사고 유도 |
| 갈래의 **판단 시점** | 필수 | 특정 날짜 또는 범위 ("2026 Q4까지"). 갈래마다 하나 |
| 각 시나리오의 **근거 항목** | 필수 | 내 논리의 중간 고리. 수치화하지 않는다 |
| 반증 조건 | 권장 | |
| 근거 자료 | 선택 | 사용자가 링크를 붙이면 수집 |

- AI는 **판단 시점과 근거 항목**에 대해서만 끈질기게 확보를 시도한다. 시점이 없으면
  리마인드가 불가능하고, 근거 항목이 없으면 회고 때 검증할 대상이 없어진다.
  강요하지는 않고 막연하면 범위로라도 받아낸다.
- **근거 항목은 반드시 1단계에 남긴다.** 2단계로 미루면 안 된다. 논리는 사용자가
  자기 생각을 말하는 흐름 속에서 받아야 진짜가 나온다. 나중에 폼으로 따로 물으면
  이미 정리된 결론에 맞춰 사후 합리화된 답만 돌아온다.
  숫자를 묻지 않으므로 한 턴이면 끝나 대화 길이에도 부담이 적다.
- 근거 항목을 끌어내는 질문: "그렇게 되려면 그 전에 무슨 일이 먼저 일어나야 할까요?"
  **수치나 데이터 출처는 묻지 않는다.** 사용자가 말로 설명한 그대로 받는다.
  ("HBM 공급이 계속 부족해야 하고, 삼성이 퀄 통과를 해야 하고")
- 대화 종료 시 AI가 노트 초안을 생성 → 사용자가 미리보기에서 확인·수정 후 저장
  (무엇을 어떻게 채우는지는 아래 '노트 생성 계약' 참조)
- **원본 대화 전문은 노트에 영구 첨부되며 수정·삭제할 수 없다.** AI가 노트를 쓰는 구조에서
  "과거의 나의 관점"이 AI의 문장이 되는 문제를 방지하는 장치로, 사용자는 언제든
  자신이 실제로 무슨 말을 했는지 원문으로 확인할 수 있다.


#### 노트 생성 계약 — AI는 자유 형식으로 쓰지 않는다

AI는 빈 문서에 글을 쓰는 것이 아니라 **정해진 스키마의 칸을 채운다.**

완전 자유 형식이면 이 앱의 나머지가 전부 무너진다. 프로그램이 시나리오를 읽지 못하면
판단 시점 리마인드도, 계열 연결도, 확률 조정도, 회고 자동 조사도 불가능하다.
반대로 문장까지 템플릿으로 고정하면 AI가 할 일이 없다. 그래서 이렇게 나눈다.

> **구조는 스키마가 강제하고, 문장은 AI가 쓴다.**

**출력 형식**: AI는 산문이 아니라 아래 구조를 반환한다. 화면 렌더링은 클라이언트가 한다.

| 칸 | 누가 채우나 | 규칙 |
|---|---|---|
| `target` | AI | 대화에서 종목·자산·테마를 뽑아 정규화 (`삼성전자` / `005930`) |
| `thesis_summary` | AI | **한 문장.** 목록·검색·알림에 쓰이므로 40자 내외로 압축 |
| `thesis_detail` | AI | 사용자의 논리를 재구성. 3~5문장 |
| 대표 인용 | **사용자 발화 그대로** | 대화에서 가장 핵심적인 한 마디를 원문 그대로 1개. `[사용자]` 표기 |
| `scenario.name` | AI | 한 문장. 무엇이 일어나는지가 드러나게 |
| `scenario.description` | AI | 2~3문장 |
| `scenario.target_timeframe` | AI가 파싱 | "올해 안" → `2026-12-31`. **해석한 결과를 사용자에게 보여주고 확인받는다** |
| `premise.statement` | **사용자 말 그대로** | 다듬지 않는다. 이건 나중에 검증할 대상이므로 원형이 중요하다 |
| `probability` | 사용자 | AI는 **사용자보다 먼저 숫자를 내지 않는다.** 대화에서 나온 표현(`반반쯤`)은 옮겨도 되고, 안 나왔으면 비운다 (§3.4) |

#### 지켜야 할 것 넷

1. **대화에 없는 내용을 쓰지 않는다.** 이게 가장 중요하다. AI가 그럴듯한 근거를 지어내
   채워 넣으면, 사용자가 몇 달 뒤 되돌아볼 "과거의 나"가 **하지도 않은 생각**이 된다.
   이 앱의 존재 이유가 통째로 무너진다. 빈 칸은 빈 채로 두고 미완성으로 표시한다.
2. **근거 항목은 사용자의 말에 가장 가깝게 둔다.** 시나리오 이름은 AI가 다듬어도 되지만,
   논리의 고리는 사용자 것이어야 한다. 회고 때 "내가 이렇게 생각했었나"에서 어긋나면 안 된다.
3. **해석한 것은 보여주고 확인받는다.** "내년 상반기" → `2027-06-30`처럼 AI가 판단한
   값은 미리보기에서 그대로 드러내고, 사용자가 고칠 수 있게 한다.
4. **저장 후에는 재생성하지 않는다.** 미리보기 단계에서만 `다시 만들기`를 허용하고,
   그때도 사용자가 이미 손댄 블록은 보존한다. 저장된 노트를 다시 생성하면 과거 기록이
   바뀌는 것이므로 금지다.

#### 노트 검증 — AI에게 묻지 않고 코드가 검사한다

"반대 시나리오가 없다", "확률 합이 100이 아니다" 같은 판단을 **LLM에게 시키면 안 된다.**
비결정적이고, 통과했다고 환각할 수 있고, 단위 테스트를 쓸 수 없다.

> **AI는 칸을 채우고, 규칙은 결정론적 코드가 검사한다.**

##### 검사는 세 층으로 나뉜다

| 층 | 검사 대상 | 실패하면 |
|---|---|---|
| **1. 구조** | LLM 출력이 스키마에 맞는가 (필드 타입, 필수 키) | 최대 2회 재시도 → 실패 시 대화로 되돌림. 부분 저장하지 않는다 |
| **2. 출처** | 인용이라고 주장한 문장이 실제 대화에 있는가 | 인용 표시를 떼고 AI 문장으로 강등 |
| **3. 규칙** | 노트가 앱의 조건을 갖췄는가 | 심각도에 따라 처리 (아래) |

**2층이 환각을 잡는 유일한 기계적 방어선이다.** `quoted_from`이 달린 블록과 `premise.statement`는
"사용자가 한 말"이라고 주장하는 것이므로, **원본 대화에서 실제로 그 문자열을 찾아 대조한다.**
못 찾으면 인용이 아니다. AI가 쓴 요약문은 자동 검증이 불가능하므로 **미리보기에서 사람이
보는 것이 최종 방어선**이다. 이 한계를 숨기지 않는다.

##### 어떤 칸을 비운 채로 저장할 수 있나 — 중요도로 가르지 않는다

"중요한 칸"과 "덜 중요한 칸"으로 가르면 기준이 사람마다 달라지고, 기준이 모호하면
사용자는 비워도 되는 칸을 계속 비운다. 그래서 중요도가 아니라 **두 가지 사실**로 가른다.

| 축 | 묻는 것 |
|---|---|
| **부패** | 나중에 채우면 **다른 값**이 들어오는가 |
| **정지** | 이 칸이 없으면 **기능이 멈추는가**, 그리고 나중에 채우면 되살아나는가 |

두 축은 서로 다른 실패를 가리킨다. 정지는 **기능이 안 도는 것**이고, 부패는
**기능은 도는데 값이 가짜인 것**이다. 둘을 한 줄로 묶으면 판단이 흐려진다.

- **부패**: 결과를 본 뒤에 쓴 반대 시나리오는 반대 시나리오가 아니고, 결론을 안 뒤에 쓴
  전제는 사후 합리화다(§3.1 1단계). 나중에 채우면 칸은 차지만 내용은 가짜다.
- **정지**: 판단 시점이 없으면 리마인드가 안 온다. 다만 날짜는 썩지 않으므로
  나중에 채우는 순간 그대로 되살아난다.

| 칸 | 나중에 채우면 | 없을 때 | 처리 |
|---|---|---|---|
| `target` · `thesis` | — | **노트가 성립하지 않는다** | **저장 차단** |
| `target_timeframe` | 그대로 살아남 | **리마인드 정지 — 홈에서 사라짐** | 저장 전 되묻기 → 건너뛰면 저장 + 상시 고지 |
| 반대 시나리오 | **썩음** | 멈추는 것 없음. 회고의 갈래 비교가 빈약해짐 | 저장 전 되묻기 → 건너뛰면 저장 |
| `premise` | **썩음** | 멈추는 것 없음. 회고의 논리 축이 빔 | 저장 전 되묻기 → 건너뛰면 저장 |
| `probability` | **썩음** | 멈추는 것 없음 | 저장 직후 2단계 폼 (같은 세션 안) |
| auto 조건 | 그대로 살아남 | 자동 제안 정지 — 채우면 **소급 판정된다** | 조용히 비워둔다. 되묻지 않는다 |

**반대 시나리오와 근거 항목은 아무것도 멈추지 않는다.** 반대 시나리오가 없으면 확률 배분이
막히는데, 확률은 없어도 멈추는 것이 없다. 연쇄가 아무것도 아닌 데서 끝난다. 이 둘이 잃는
것은 정지가 아니라 **손상**이다.

##### 왜 손상되는 칸을 차단하지 않는가

> **부패하는 칸은 차단해도 얻을 수 없다.**

차단은 *"값을 받는다"* 를 보장하지 않고 *"무언가 입력됐다"* 만 보장한다. 반대 시나리오는
사용자가 실제로 생각해야 나오는 것이라, 막고 강요하면 `"그냥 떨어질 수도 있고"` 같은 것이
들어온다. **지어낸 전제는 사후 합리화와 똑같이 가짜다.** 빈 칸이 거짓말로 바뀔 뿐 품질은
오르지 않고, 대신 나중에 회고할 때 그 거짓말을 진짜 자기 생각으로 착각하게 된다.
빈 칸은 비었다는 것이 보이지만, 지어낸 답은 그것이 지어낸 것인지 알 수 없다.

그래서 이 칸들에 쓰는 도구는 차단이 아니라 **되묻기**다. 한 번 붙잡아 기회를 주되,
답이 없으면 없는 채로 둔다.

##### 되묻기는 부패하거나 정지하는 칸에만 건다

되묻기가 다섯 개면 사용자는 다섯 개를 다 무시하고, 그러면 정작 부패하는 칸의 되묻기까지
같이 무시된다. **되묻기의 신뢰는 개수에 반비례한다.**

- **되묻기 화면은 저장당 1회다.** 대상이 셋(판단 시점·반대 시나리오·근거 항목)이지만
  각각 따로 띄우지 않고 **한 화면에서 함께 묻는다.** 세 번 물으면 세 번 다 무시당한다.
- **`비운 채로 저장`은 같은 크기의 선택지로 둔다.** 작게 숨기면 사실상 차단이고,
  차단하면 사용자는 답을 지어낸다. 지어낸 반대 시나리오는 없느니만 못하다.
- 그 버튼 옆에 **무엇을 포기하는 것인지 정확히 적는다.** 문구는 남은 빈 칸에 따라 다르다.
  - 판단 시점이 있으면 → `비워 두어도 저장되고 판단 시점에 리마인드가 옵니다`
  - 판단 시점까지 비었으면 → `비워 두면 저장은 되지만 리마인드가 오지 않습니다`
    (거짓말을 하지 않는다. 이 경우는 실제로 잃는 것이 있다)
- **auto 조건은 되묻지 않는다.** 자동 제안이 멈추긴 하지만, 나중에 채우면 과거 가격으로
  **소급 판정된다.** 되살아나는 정지이면서 값도 썩지 않으므로 지금 받을 이유가 없다.
  수치 설정은 저장 직후 2단계 폼이 이미 담당한다(§3.1 2단계).

##### 판단 시점 — 유일하게 진짜로 멈추는 칸

판단 시점은 부패하지 않는다(날짜는 나중에 정해도 같은 날짜다). 그러나 없으면
**홈 타임라인에도 리마인드에도 뜨지 않는다.** 사용자가 스스로 찾아 열지 않으면 그 노트는
없는 것과 같고, 그건 메멘토가 메멘토를 못 하는 상태다.

그래서 **부패하지 않는데도 되묻기 대상이다.** 되묻기 발동 조건은 둘 중 하나면 된다 —
**나중에 채우면 썩거나, 없으면 제품이 멈추거나.**

- 그래도 차단하지는 않는다. 값이 썩지 않으므로 나중에 채우면 리마인드가 **그대로
  되살아난다.** 되살아나는 정지를 이유로 저장을 막을 필요는 없다.
- 대신 이 칸만은 노트 상단에 `판단 시점을 정하면 리마인드가 시작됩니다`를 상시 노출한다.
  다른 빈 칸의 안내는 한 번 보이고 조용해지지만, 이건 계속 남는다.
- 이것은 독촉이 아니라 **기능이 꺼져 있다는 고지**다. 며칠 됐는지 세지 않는다(§P5).
- 대화 단계에서 AI가 가장 끈질기게 묻는 칸이기도 하다. 막연하면 범위(`올해 안`,
  `다음 실적 발표쯤`)로라도 받아낸다(UX 문서 §3.2).

##### 규칙은 심각도로 나눈다 — 대부분은 차단하지 않는다

```
type Issue = {
  code:     'NO_DEADLINE' | 'SINGLE_SCENARIO' | ...
  severity: 'blocking' | 'ask' | 'incomplete' | 'notice'
  field:    string        // 어느 칸인지
  message:  string        // 사용자에게 보일 문장 (무엇이 왜 비었는지)
  fix?:     { label, action }   // "지금 추가하기" 같은 바로가기
}

validateNote(note): Issue[]
```

| code | 심각도 | 결과 |
|---|---|---|
| `NO_TARGET` / `NO_THESIS` | blocking | 저장 불가. 이게 없으면 노트가 아니다 |
| `NO_DEADLINE` | **ask** + incomplete | 되묻고, 건너뛰면 저장. **리마인드 제외** — 노트 상단에 상시 고지 |
| `SINGLE_SCENARIO` | **ask** | 저장 전 1회 되묻고, 건너뛰면 저장. 확률 배분만 막힘 |
| `NO_PREMISE` | **ask** | 저장 전 1회 되묻고, 건너뛰면 저장. 회고에 조사할 대상이 없어짐 |
| `NO_GALAE_QUESTION` | **ask** | 시나리오는 있는데 무엇을 놓고 갈리는지가 없다. 되묻고, 건너뛰면 가설 문장을 질문으로 임시 표시 |
| `NO_AUTO_RESOLUTION` | notice | 정상 동작. 자동 제안만 없고 사용자가 직접 표시한다 |
| `DEADLINE_IN_PAST` | notice | 작성 시점에 이미 지난 날짜. 오타일 가능성 |

판단 시점이 시나리오마다 어긋나는 경우는 **검증 대상이 아니다.** 시나리오에 날짜
필드가 없기 때문에 애초에 만들 수 없다. 대화에서 서로 다른 날짜가 나오면
갈래를 나누는 것이 정답이고, 그 판단은 Thesis Builder가 노트를 조립할 때 내린다
(§7.3). 검사로 잡을 수 있는 오류를 구조로 없애는 쪽을 항상 택한다 — 확률 합
100%를 갈래 단위 원자적 갱신으로 처리한 것과 같은 이유다.

`ask`는 **저장 전 한 번만** 뜨고, 건너뛴 뒤에는 `notice`처럼 노트 안에서 조용히 있는다.
같은 되묻기를 다시 띄우지 않는다 — 반복되면 그것이 곧 독촉이다(§P5).

**blocking은 둘뿐이다.** 나머지는 다 저장된다. 검증기의 목적은 막는 것이 아니라
**무엇이 왜 비었는지 말해주는 것**이다. 문턱을 높이면 기록이 안 쌓이고, 기록이 없으면
이 앱은 가치가 0이다(§P6).

- `message`는 UI가 그대로 쓸 수 있는 완성된 문장이어야 한다. `"필수 항목 누락"` 같은
  코드 번역이 아니라 `"대화에서 이 판단이 틀린 경우를 이야기하지 않아 비워 두었습니다"`처럼.
- 규칙은 **각각 순수 함수 하나**로 만든다. 노트를 받아 `Issue | null`을 반환한다.
  이러면 규칙마다 테스트를 쓸 수 있고, 규칙을 추가해도 기존 것이 안 깨진다.
- **서버가 정본이다.** 미리보기의 즉시 피드백도 서버 검증 API 호출로 받는다 —
  규칙 구현을 서버 한 곳에만 두면 두 곳이 어긋날 길 자체가 없다. 예외적으로 이중
  구현을 허용하는 것은 확률 슬라이더의 재분배뿐이고, 골든 테스트 벡터로 묶는다(§13.3).

##### 확률 합은 검사하지 않는다 — 어긋날 수 없게 만든다

"합이 100%가 아니다"를 **검사 대상으로 두는 순간 이미 진 것이다.** 어긋난 상태가
데이터베이스에 존재할 수 있다는 뜻이고, 그러면 언젠가 어긋난다.

**개별 시나리오의 확률을 따로 수정하는 경로를 아예 열지 않는다.**

```
✗  PATCH /scenarios/{id}  { probability: 65 }      ← 이 API를 만들지 않는다
○  PATCH /galae/{id}/probabilities
       { changed: {scenarioId, value}, lockedIds: [...] }
       → 서버가 나머지를 재분배하고 합이 100인 상태만 기록한다
```

- 쓰기 경로가 **갈래 단위 원자적 갱신 하나뿐**이므로, 합이 100이 아닌 상태를 만들 방법이 없다.
- 5% 단위 스냅과 `그 외 예상 못한 전개` 최소 5%도 이 함수 안에서 함께 지켜진다.
- 반올림 오차는 **최대 잔여법(largest remainder)** 으로 흡수해 합계를 정확히 100으로 맞춘다.
- DB에도 제약을 건다(갈래별 합계 = 100). 코드가 틀려도 잘못된 데이터가 남지 않게 하는
  마지막 방어선이다.

재분배 함수는 네 단계다. (아래 결과는 참조 구현으로 검증했다)

```
redistribute(갈래, 바꾼_시나리오, 새_값, 잠긴_시나리오[])

  1. 새 값을 5단위로 스냅하고, 잠긴 값들과 잔여 슬롯 최소치(5)가 들어갈 자리를 뺀
     상한으로 자른다                          → 100을 입력해도 95로 잘린다
  2. 남은 몫을 나머지 시나리오들의 기존 비율대로 나눈다
  3. 각각 5단위로 내린 뒤, 부족분을 최대 잔여법(largest remainder)으로 채워
     합계를 정확히 100으로 맞춘다
  4. 잔여 슬롯이 5% 미만이면 가장 큰 항목에서 빌려와 채운다

검증한 경우들 (시작: A 65 / B 25 / 그 외 10)
  A→80  →  A 80  B 15  그 외  5
  A→95  →  A 95  B  0  그 외  5      B가 0이 되어도 허용한다
  A→100 →  A 95  B  0  그 외  5      상한에서 잘림
  A→0   →  A  0  B 70  그 외 30      기존 비율 25:10 을 유지
  A→63  →  A 65  B 25  그 외 10      5단위로 스냅
  B 잠금 + A→80 → A 70  B 25  그 외 5  잠긴 값은 움직이지 않는다
```

세 가지가 항상 참이다: **합계 = 100**, **모든 값이 5의 배수**, **잔여 슬롯 ≥ 5%**.
- 시나리오가 하나뿐이면 **갈래가 성립하지 않으므로 확률 자체를 비운다.**
  혼자인 시나리오에 100%를 넣으면 사용자가 표현한 적 없는 확신을 앱이 만들어내는 셈이다.

##### 언제 검사하나

- 노트 저장·수정 시 (서버)
- 미리보기 화면 진입 시 (클라이언트, 즉시 피드백용)
- **주기적 재검사는 하지 않는다.** 시간이 지나 생기는 상태 변화(판단 시점 경과 등)는
  검증기가 아니라 시나리오 상태 전이(§3.4)가 담당한다. 두 곳에서 같은 일을 하면 어긋난다.

#### 2단계 — 확인 방법 설정 (건너뛸 수 있음)

노트 저장 직후 "이어서 확인 방법을 정하시겠어요?"로 자연스럽게 이어지되, **나중에 해도 되고
안 해도 된다.**

이 화면은 **갈래마다 두 가지**를 받는다. 확률을 어떻게 나누는지, 그리고 어느 답이 기계로
확인되는지다. 갈래 단위로 묶어 보여준다 — 하나의 질문에 대해 "어떻게 보시나요"와
"어떻게 확인할까요"는 붙어 있는 것이 자연스럽다. 갈래가 둘이면 이 묶음도 둘이다.

확률을 받을 때 자료를 언제 보여주는지(기저율은 먼저, 남의 답은 나중)는 §3.4에 있다.

확인 방법 쪽은 갈래마다 **어느 답이 auto로 확인되는지**를 정한다. 시나리오 밑에 조건을
여러 개 다는 자리가 아니다 — 답 하나에 auto 조건은 하나뿐이고(§2.3), 여집합인 답과
`그 외 예상 못한 전개`는 애초에 `complement`라 조건을 갖지 않으므로 화면에 나타나지 않는다.

- **AI가 후보를 미리 채워둔 폼으로 제시한다.** 빈 폼이 아니다. 갈래의 질문에서 종목·지수·
  거시 계열을 추출해 데이터 소스와 함께 후보로 올리고, 대화에 숫자가 언급됐으면 목표값도
  채워 둔다. 사용자는 확인하고 고치기만 하면 된다.
- 여기서 받는 것: **목표값과 비교 방식(이상/이하/범위/변화율)** 둘뿐이다.
- **질문이 수치에 관한 것이 아니면 auto 후보를 제안하지 않는다.** `HBM4 공급사로 진입하는가`에
  주가를 붙이라고 권하지 않는다. 주가가 올랐다고 수주를 받은 것이 아니기 때문이다(§2.3).
  대신 `지켜보는 수치`로 담을지 묻는다 — 판정하지 않고 추이만 보여준다.
- **관측 규칙은 묻지 않는다.** 시스템이 `한 번이라도 닿으면 달성 · 장중 포함`으로 고정하고,
  화면에는 안내 문장 한 줄만 둔다. 사용자가 답할 준비가 안 된 질문을 폼에 놓으면
  거기서 이탈한다.
- 근거 항목 중 마침 FRED·ECOS로 살 수 있는 것이 있으면 이 화면에서 `지켜보는 수치` 후보로
  올라온다. 판정에는 쓰지 않는다 — 근거가 맞았는지는 회고에서 따진다.

#### 확인 방법이 없는 노트도 정상 동작한다

auto 판정은 필수가 아니므로, 없어도 앱의 핵심 루프는 그대로 돌아간다.

| 빠진 것 | 결과 |
|---|---|
| 판단 시점 | **미완성 노트.** 리마인드 대상에서 제외되고 상단에 안내가 붙는다 |
| auto 조건 | 정상 노트. 시점 기반 리마인드·회고록 모두 작동하고, **자동 제안만 없다.** 결과 확인 시 사용자가 직접 표시한다 |

`HBM4 공급사로 진입하는가`처럼 계열로 살 수 없는 질문이 오히려 흔하다. 이때 노트 상세에는
`판단 시점이 오면 여쭙겠습니다`라는 안내가 조용히 붙는다. 차단이 아니라 안내이고,
없는 것을 채우라고 재촉하지 않는다(UX §P5).

> 화면 구성과 인터랙션 상세는 [`ux-design.md`](./ux-design.md) 참조.

### 3.2 리마인드 시스템
- 예약된 리마인드: 노트 작성 후 N일/주/월 후 자동 리마인드 (사용자 설정 가능, 기본값 제공)
- 시점 기반 리마인드: 시나리오의 예상 시점이 임박하거나 도래하면 알림
- 이벤트 기반 리마인드: AI가 수집한 뉴스가 특정 시나리오와 강하게 연관되면 즉시 알림
- 리마인드 화면 구성: "과거의 나는 이렇게 생각했다"(원문 그대로) + "그동안 이런 일이 있었다"(AI 요약)
  + "지금은 어떻게 보시나요?"(다시 판단하도록 유도)

### 3.3 AI 리서치 & 뉴스 모니터링
- 노트/가설/시나리오 단위로 관련 키워드·엔티티 자동 추출
- 주기적으로 (또는 온디맨드로) 관련 뉴스/공시/데이터 검색
- 검색 결과를 다음 기준으로 정리:
  - 어느 노트/시나리오와 관련 있는지
  - 해당 시나리오를 뒷받침하는지 / 어긋나는지 / 관련만 있는지
    (내부 값 `supports` / `contradicts` / `neutral`, 화면 표기는 UX 문서 §9.4 대응표를 따른다)
  - 한 줄 요약 + 원문 링크
- 사용자는 각 리서치 결과에 대해 "반영함/무시" 피드백 → AI 리서치 품질 개선에 활용

#### 다음 점검 일정을 사용자에게 보여준다

AI가 언제 무엇을 볼지 사용자에게 미리 안 보이면, "AI가 알아서 조사해준다"는 약속이
체감되지 않는다. 언제 열어도 그날그날 다른 검색 결과만 나타났다 사라지는 블랙박스로
느껴지면, 사용자는 이 앱에 조사를 맡기고 있다는 감각 없이 그냥 뉴스 피드 하나를 더
구독하는 셈이 된다. 그래서 노트 상세에 **다음에 무엇을 언제 살펴볼지**를 평범한 문장으로
미리 보여준다.

일정의 날짜는 두 군데에서 온다 — 이 둘은 성질이 달라서 내부적으로는 다르게 다뤄야 한다.

| 종류 | 예 | 날짜의 출처 |
|---|---|---|
| **발표 캘린더가 있는 계열** | CPI, 실업률, FOMC 회의 | 발표 기관의 공개 캘린더(FRED가 release_dates를 제공한다). 다음 발표일이 이미 정해져 있다 |
| **발표일이 없는 계열·근거 항목** | WTI 유가, "HBM 매출 비중" 같은 서술형 근거 | 정해진 발표일이 없으므로 예약된 리마인드 주기(§3.2)로 다음 재확인 시점을 잡는다 |

**화면에 나가는 문장은 이 둘을 구분하지 않는다.** 사용자에게 중요한 건 "다음에 언제
다시 보는가" 하나뿐이고, 그 날짜가 발표 캘린더에서 왔는지 재확인 주기에서 왔는지는
내부 사정이다(P8). 예:

```
8.31 · CPI 발표
  발표되면 이 갈래의 전제와 맞는지 확인합니다
9.13 · WTI 유가
  지켜보는 수치를 다시 확인합니다
```

**이건 약속이 아니라 예정이다.** "그날 반드시 알림이 온다"고 하면, 특이사항이 없는
대부분의 점검일에 사용자가 "왜 알림이 안 왔지"라고 느끼게 된다. 그래서 문구는 항상
`확인합니다`까지만 적고 `알려드립니다`라고 적지 않는다. 실제로 리마인드가 뜨는 기준은
기존 이벤트 기반 리마인드 규칙(연관성이 강할 때만, §3.2) 그대로다 — 이 일정은 **AI가
지켜보고 있다는 사실**을 보여주는 것이지, 점검일마다 리마인드를 예약하는 것이 아니다.
점검이 끝나면 항목은 조용히 다음 예정일로 갱신된다. "봤는데 별일 없었다"는 따로
보고하지 않는다 — 그 자체가 소음이다(P5).

화면 위치는 노트 상세로 한정한다. 홈 세로 타임라인은 "내가 결론 내야 하는 날"(판단
시점)만 다루는 축으로 이미 자리를 잡았고(§3.1), 여기에 "AI가 대신 보는 날"까지 섞으면
성격이 다른 두 종류의 날짜가 한 축에 뒤섞여 정작 사용자가 뭔가 해야 하는 날의 신호가
흐려진다. 화면 상세는 [`ux-design.md`](./ux-design.md) §3.4 참조.

### 3.4 시나리오 트래킹 보드
- 노트별로 시나리오들을 보드 형태로 시각화, 홈에서는 전체 노트의 판단 시점을 세로 타임라인으로 표시
  (축 하나에 판단 시점을 점으로 찍고 카드를 연결한다. 항목이 늘어도 스크롤로 감당된다)
- 시간 경과에 따른 확률 변화 이력
- 시나리오 상태 (화면 표기 / 내부 값): 지켜보는 중 `active` / 결과 확인 필요 `pending_judgment` /
  그대로 됨 `confirmed` / 틀렸음 `rejected`
  - **앱이 알아서 "틀렸다"고 정리하는 경우는 없다.** 시점이 지나면 `결과 확인 필요`가 되어
    리마인드가 뜨고, 결론은 반드시 사용자가 낸다.
  - 선택지는 세 가지: `그대로 되었다` / `틀렸다` / `방향은 맞지만 시기를 다시 본다`
    - 여기서 묻는 것은 **"예상한 일이 일어났는가"뿐이다.** "내 논리 때문이었는가"는
      자료를 조사해봐야 알 수 있으므로 회고록(§3.6)에서 따로 묻는다.
    - 세 번째를 같은 비중으로 두는 이유: 현실에서 가장 흔한 경우가 "방향은 맞았는데 시기를
      잘못 봤다"인데, 틀렸다만 고를 수 있게 하면 사용자가 확인 자체를 피하고 방치하게 된다.
    - 시점 재설정 시 `active`로 복귀하며, 재설정 이력은 회고용으로 보존한다.
  - `그대로 됨` 또는 `틀렸음`으로 확정되면 **회고록이 열린다**(§3.6). 여기서 비로소
    "제대로 맞춘 것인가, 소 뒷걸음질인가"를 가린다.
  - auto 판정 시나리오의 카드에는 **목표까지의 거리**가 함께 표시된다
    (예: `95,000원까지 · 지금 92,800`). 부분 진행은 그 자체로 강한 신호이므로 최종 판정
    전에도 계속 보여준다. manual·complement 시나리오에는 표시할 것이 없다.
  - 결과를 정할 때 이유를 한 줄 남기도록 권한다(선택). 이것이 가장 값진 회고 자료가 된다.
- **갈래는 하나의 질문이다.** 시나리오는 그 질문에 대한 배타적인 답들이다.
  질문을 명시적으로 저장하고 화면에도 항상 함께 적는다. 질문 없이 시나리오만 나열하면
  무엇을 놓고 갈리는지 알 수 없고, `그 외 예상 못한 전개`가 무엇의 여집합인지도
  정해지지 않는다.
- **판단 시점은 갈래에 하나뿐이다.** 배타적인 답들이 서로 다른 날 판가름 난다는 것은
  성립하지 않는다. 날짜가 다르다면 한 갈래가 아니라 별개의 질문 둘이므로 갈래를 나눈다.
  시나리오에는 판단 시점 필드를 두지 않아 구조적으로 막는다.
- **한 노트는 갈래를 여럿 가질 수 있다.** 노트는 하나의 믿음이고, 하나의 믿음은 시점이
  다른 여러 질문으로 검증될 수 있기 때문이다. 가설과 근거 항목은 노트에 한 벌 있고
  갈래마다 되풀이되지 않는다. 갈래를 1:1로 묶어 노트를 쪼개면 같은 가설과 같은 논리
  사슬이 노트 수만큼 복사되고, 회고에서 "내 논리가 맞았나"를 물을 단위가 사라진다.
- **갈래는 사용자가 실제로 말한 질문마다 하나다.** 답이 나오는 날이 다르면 반드시
  나눠야 하고, 같은 날이어도 다른 질문이면 나눈다 — `공급사로 진입하는가`와
  `12월 말까지 주가가 95,000원을 넘는가`는 같은 날 답이 나오지만 다른 질문이다.
  오히려 이 둘을 나눠 두어야 회고에서 `진입은 못 했는데 주가는 넘었다`가 드러난다.
- **그러나 AI가 나오지 않은 질문을 지어내지 않는다.** 갈래 하나는 질문 하나, 답 둘 이상,
  합이 100인 확률, 날짜 하나를 요구한다 — 지어내면 사용자가 채우지 않는 빈 칸만
  늘어난다. 사용자가 목표 가격을 말했으면 갈래로 세울지 묻고, 말하지 않았으면 묻지 않는다.
- **노트는 모든 갈래가 판정되면 끝난다.** 갈래마다 판정일이 다르므로 회고록도 갈래마다
  열린다. 근거 항목은 노트에 하나뿐이지만 회고가 여러 번 열리므로, 사후 조사 결과는
  덮어쓰지 않고 조사 시점과 함께 쌓는다 — 반년 뒤에 다시 조사하면 답이 달라질 수 있다.
- **시나리오 이름은 답이지 경로가 아니다.** 원인과 결과를 한 문장에 섞으면
  (`증설로 공급이 풀려 기술 격차만 확인`) 다른 시나리오와 축이 어긋나 확률 배분이
  읽히지 않는다. 이름에는 결과만 쓰고 메커니즘은 설명으로 내린다.
- 한 갈래 안의 시나리오들은 **동시에 일어날 수 없는 경우로 보고, 확률 합을 항상 100%로** 맞춘다.
  하나를 올리면 다른 것이 줄어드는 제약이 있어야 트레이드오프 사고가 강제된다.
- 갈래의 구성비는 **도넛**으로 보여준다. 확률 숫자를 만지는 **눈금 막대**는 확률을
  입력·조정하는 화면(2단계 설정, 다시 판단하기)에만 두고, 시나리오 카드에서 지난번
  대비 변화는 막대가 아니라 문장으로 적는다(UX §6).
  조각 경계를 그라데이션으로 그려 확률이 어림임을 형식에 담는다.
- 모든 노트에 지울 수 없는 **`그 외 예상 못한 전개`** 항목을 자동으로 만들고 최소 5%를 남긴다.
  "내가 생각한 경우가 전부"라는 착각을 구조적으로 막기 위함.

#### 확률 배분 — 자료는 답마다 갈라 주고, 숫자는 사용자만 낸다

확률은 **갈래 단위로 배분한다.** 노트 단위가 아니다. 갈래마다 질문이 다르므로 배분도
따로 하고, 갈래가 둘이면 도넛도 둘이다.

##### 확률은 사용자만 낸다

AI가 먼저 "60%로 보입니다"라고 내면 사용자는 그것을 승인하거나 55%로 조금 움직인다.
그러면 노트에 남는 숫자는 **AI의 판단이지 사용자의 판단이 아니다.** 이 앱은 그 지점에서
무너진다.

- 회고의 2×2는 `내 논리가 맞았는가`를 묻는다. 확률이 AI 것이면 평가할 내 것이 없다.
- 캘리브레이션(`내가 70%라 한 것들 중 실제로 70%가 일어났는가`)이 AI 캘리브레이션
  측정으로 바뀐다.
- `과거의 나를 다시 본다`가 전제인데 과거의 나가 사라진다.

##### 남의 의견을 확률로 환산하지 않는다

`증권사 12곳 중 7곳이 연내 진입 가능` 은 자료다. 이것을 **58%로 바꿔 적으면 안 된다.**

- 애널리스트는 확률을 말한 적이 없다. 방향을 말했을 뿐이다.
- 그들의 견해는 서로 베껴서 상관돼 있고, 매도 의견이 구조적으로 적다.
- 표본이 12이고 적중 이력도 없는데, `58%`는 소수점 아래까지 아는 것처럼 보인다.

**AI 자신의 추정치도 같은 이유로 내지 않는다.** LLM이 뱉는 숫자에는 캘리브레이션 기록이
없다. 근거 문장을 붙여도 숫자 자체는 정밀해 보이는 착시만 만든다.

이런 값을 사용자의 확률 옆에 나란히 세우면 셋이 같은 종류의 값처럼 읽힌다. 실제로는
사용자가 낸 것 하나만 확률이고 나머지는 다른 것이다. **비교 열 자체를 만들지 않는다.**

##### 대신, 답마다 그것을 뒷받침하는 자료를 모아 준다

AI가 하는 일은 숫자를 내는 것이 아니라 **읽을거리를 답별로 갈라 놓는 것**이다.
갈래가 질문이고 시나리오가 그 답들이므로, 자료도 어느 답 편인지에 따라 묶인다.
사용자는 양쪽 더미의 무게를 재서 스스로 나눈다.

```
올해 안에 엔비디아 HBM4 공급사로 진입하는가?

  01 진입한다 쪽
   · 엔비디아, 공급사 다변화 검토 착수              5일 전 · 출처 3곳
   · 증권사 12곳 중 7곳이 "연내 진입 가능" 의견       출처 4곳

  02 진입하지 못한다 쪽
   · SK하이닉스 HBM4 양산 일정 단축                2일 전 · 출처 2곳
   · 삼성 퀄 테스트 3차 지연 보도                   3주 전 · 출처 2곳

  어느 쪽도 아닌 것
   · 최근 5년간 신규 공급사 진입이 발표 후 2분기 안에
     확정된 사례 7건 중 3건                        출처 2곳
```

- **`↗ 뒷받침` / `↘ 어긋남` 표시는 노트 상세의 새 정보 서랍(§3.3)과 같은 어휘를 쓴다.**
  같은 것을 두 이름으로 부르지 않는다.
- **기저율은 어느 답의 편도 아니다.** 질문 전체에 대한 빈도이므로 따로 묶는다.
- **시장의 견해는 자료 한 줄로 들어간다.** `증권사 12곳 중 7곳이 연내 진입 가능`은
  사실이고, `58%`는 사실이 아니다.
- **한쪽이 비어도 채우지 않는다.** 찾지 못했으면 `찾은 자료가 없습니다`라고 적는다.
  한쪽만 자료가 쌓이는 것 자체가 사용자에게 정보다.
- 자료는 숫자가 아니므로 **배분하기 전에 보여준다.** 읽고 나서 나누는 것이 자연스럽고,
  시장이 무엇을 알고 있는지 모르는 채로 판단하는 것이 오히려 나쁘다. 확정 뒤에 무언가를
  공개하는 단계는 두지 않는다 — 공개할 숫자가 없다.

##### 실제 시장 가격에서 나온 확률은 예외다

옵션 내재확률처럼 **거래된 가격에서 계산되는 값**은 애널리스트 의견과 다르다. 돈이 걸려
있고 산출식이 공개돼 있다. 이런 값은 자료로 보여줘도 된다. 다만 특정 종목의 가격 질문에만
존재하고 `공급사로 진입하는가` 같은 질문에는 없으므로, MVP에서는 다루지 않는다(§12).

##### 숫자를 직접 묻지 않는다

`65`를 입력하라고 하면 대부분 멈춘다. 눈금 위의 위치로 받고 시스템이 %로 옮긴다.
눈금 아래에는 `희박 · 반반 · 유력`을 적어 감각과 숫자를 잇는다. 5% 단위로만 움직이는 것도
같은 이유다 — 63%와 65%의 차이를 진지하게 고민하게 만들면 안 된다.

**그래도 못 매기겠으면 비워둔다.** AI가 채우는 것보다 빈 고리로 남는 것이 낫다.
빈 칸은 "아직 생각하지 않았다"는 정직한 기록이지만, AI가 채운 값은 하지도 않은 생각이다.

### 3.5 수치 수집 & 평가

수집 대상은 두 가지다. **auto 판정 시나리오의 계열**과 **지켜보는 수치의 계열**이다.
수집 방식은 같고, 쓰임만 다르다 — 앞은 달성 여부를 평가하고, 뒤는 추이만 그린다.

#### 갈래 하나에 판정도 하나

판단 시점이 되면 그 갈래에 대해 **판정 한 번**이 열린다. auto 조건은 어느 답인지에 대한
제안을 만들 뿐이고, 확정은 언제나 사용자가 한다(§3.4).

| auto 조건이 달성된 답 | 앱이 하는 일 |
|---|---|
| 정확히 하나 | 그 답을 제안하고 사용자가 확인한다 |
| 하나도 없고 complement가 있음 | complement를 제안한다 (`내려간다`가 미달이면 `내려가지 않는다`) |
| 둘 이상 | **제안하지 않는다.** "조건이 서로 어긋납니다"와 함께 양쪽 현황을 나란히 보여주고 사용자가 고른다 |
| auto 답이 없음 (전부 manual) | 제안하지 않는다. 사용자가 표시한다 |

둘 이상이 동시에 달성되는 상태를 코드로 막지는 않는다 — 목표값이 의미상 겹치는지는
결정론적으로 판별할 수 없다. 대신 **조용히 틀린 판정을 내리지 않는다.** 앱이 판정하지
않고 제안만 하기 때문에, 어긋남은 잘못된 결론이 아니라 화면에 드러나는 사실이 된다.

한 갈래에서 auto 답이 둘 이상 나오는 것은 대개 `인하`/`동결`/`인상`처럼 한 수치의 구간을
나눠 갖는 경우이고, 그때는 구간이 겹치지 않으므로 어긋남이 생기지 않는다. 여집합 관계인
답에 각각 조건을 다는 것은 애초에 만들 수 없다 — 여집합인 답의 판정 방식은 `complement`다.

- 수집은 **하루 1회 배치**로 돌린다.
- 이 앱은 **실시간 시세가 필요 없다.** 종가·일별 값 기준으로 판정하고, 거시 통계는
  월·분기 단위로 갱신된다. 실시간을 전제하면 비용·라이선스·복잡도가 모두 불필요하게 올라간다.

#### 무엇을 저장하는가 — 종가와 고가·저가

| 데이터 종류 | 저장 값 | 이유 |
|---|---|---|
| 주식·지수 (KIS) | 종가 + 고가 + 저가 | 종가는 판정과 차트의 기준, 고가·저가는 `장중 터치 인정` 규칙 판정과 차트의 띠에 쓰인다 |
| 거시 계열 (FRED·ECOS) | 값 하나 | 장중이라는 개념이 없다. 설정 화면에서 장중 옵션을 노출하지 않는다 |

- **배치는 각 시장 마감 후 실행한다.** 한국장과 미국장은 따로 돈다.
- **아직 마감하지 않은 당일은 저장하지도, 그리지도 않는다.** 차트의 마지막 점은 언제나
  확정된 마지막 종가다. 장중 값을 보여주기 시작하면 그 순간 시세 앱이 되고, 사용자는
  하루에 몇 번씩 앱을 열게 된다 — 이 앱이 막으려는 행동이 정확히 그것이다.
- 해외 계열은 **현지 거래일 기준**으로 찍는다. 한국 시간으로 환산하지 않는다.
- **수집한 값은 사용자별이 아니라 전역으로 캐시한다.** 삼성전자 종가는 모든 사용자에게 같은
  값이므로, 외부 API 호출량은 사용자 수가 아니라 **서로 다른 계열의 개수**에 비례한다.
  auto 판정이든 지켜보는 수치든 같은 캐시를 쓴다.
  노트 10개 내외 × 사용자 수천 명이어도 실제 호출은 수백 건 수준에 머문다.
- 평가 결과는 `SeriesSnapshot`으로 날짜별 보존한다. "그때 실제로 얼마였는지"가 남아야
  나중에 복기가 가능하다. 이 스냅샷이 곧 **추이 차트**의 원천 데이터가 된다.
- auto 판정 시나리오는 **기록 시점 값 · 목표값 · 그 사이 거리 · 오늘까지의 추이 · 남은 기간**을
  한 그림에 담는다. 지켜보는 수치는 목표선 없이 추이만 그린다. 캔들·이동평균·보조지표는 붙이지 않는다. 기술적 분석을 부르는 순간
  이 앱이 막으려던 충동적 판단이 되돌아온다. (UX 문서 §7)
- 기간은 언제나 `기록 시점 → 판단 시점`으로 고정한다. 사용자가 기간을 바꾸기 시작하면
  트레이딩 앱이 된다.
- auto 조건의 달성/미달성이 바뀌는 순간은 리마인드 트리거가 된다 (§3.2의 이벤트 기반 리마인드).
  지켜보는 수치는 트리거가 되지 않는다 — 목표가 없으므로 "바뀌는 순간"이라는 것이 없다.

### 3.6 회고록 — 이 앱의 최종 산출물

시나리오의 결과가 정해지면 **회고록**이 열린다. 여기서 답하는 질문은 하나다.

> **제대로 맞춘 것인가, 소 뒷걸음질 치다 맞춘 것인가.**

결과가 맞았다는 사실만으로는 아무것도 배울 수 없다. 틀린 논리로 운 좋게 맞은 것을
실력으로 착각하면, 다음에 같은 논리로 더 큰 돈을 넣고 크게 잃는다. **이 앱의 존재 이유가
바로 이 구분에 있다.** 판정도, 리마인드도, 원본 대화 보존도 전부 이 순간을 위한 준비다.

#### 결과 × 논리의 2×2

|  | **논리가 맞았다** | **논리가 틀렸다** |
|---|---|---|
| **결과가 맞았다** | 제대로 맞춤 | **소 뒷걸음질** — 가장 위험한 성공 |
| **결과가 틀렸다** | 논리는 옳았으나 시기·경로가 어긋남 — **가장 배울 게 많은 실패** | 완전히 빗나감 |

- 판정(결과)은 §3.4에서, 논리 평가는 회고록에서 정한다. 두 축은 독립이다.
- 오른쪽 위 칸이 이 앱이 잡아내려는 핵심이다. 다른 앱은 이걸 "적중"으로만 기록한다.
- 왼쪽 아래 칸도 중요하다. 논리가 옳았는데 시기를 잘못 봤다면 그 논리는 버릴 게 아니라
  다시 쓸 자산이다.

#### AI가 초안을 먼저 만든다

빈 화면에 "회고를 쓰세요"라고 두면 아무도 쓰지 않는다. **AI가 자료조사를 마친 초안을
먼저 제시하고, 사용자는 거기에 최종 판단을 얹는다.**

AI 회고 리서치의 동작:

1. 노트에 기록된 **근거 항목**들을 꺼낸다 (수치화되지 않은 것 포함)
2. 각 항목이 해당 기간에 실제로 일어났는지 뉴스·공시·실적 발표에서 조사한다
3. 항목별로 `실제로 일어남` / `일어나지 않음` / `확인 불가`로 분류하고 출처를 붙인다
4. 결과가 그대로 됐다면, **그 결과의 실제 원인으로 지목되는 설명들**을 따로 수집한다
   (시장 전체 상승, 다른 재료, 수급 등 — 내 논리와 무관한 원인일 수 있다)
5. 초안 서술을 생성한다

```
AI 회고 초안 예시

  당시 세우신 논리는 이랬습니다.
    HBM 공급 부족 지속 → 삼성전자가 후발주자로 점유율 확보 → 주가 상승

  조사 결과:
    · "HBM 공급 부족 지속"     → 일어나지 않음
      SK하이닉스 HBM4 양산이 앞당겨지며 2026년 하반기부터 공급이 풀렸습니다. (출처 2건)
    · "삼성전자 점유율 확보"   → 확인 불가
      삼성의 HBM 점유율을 공개한 자료를 찾지 못했습니다.
    · 갈래 "12월 말까지 95,000원을 넘는가" → 넘음 (2026.11.18)

  다만 같은 기간 코스피가 18% 올랐고, 반도체 업종 전체가 21% 올랐습니다.
  삼성전자의 상승률은 15%로 업종 평균을 밑돕니다.

  전제였던 공급 부족은 실제로는 해소되었는데 주가는 올랐습니다.
  시장 전체 상승에 따라 움직였을 가능성을 검토해 보시기 바랍니다.
```

- **AI는 초안까지만 쓴다.** "이건 운이었습니다"라고 확정하지 않는다. 판단은 사용자가 한다.
- 위 예시의 마지막 두 문단이 회고 리서치의 핵심이다. **결과를 벤치마크(지수·업종)와
  대비**시키는 것만으로도 "그냥 시장이 올라서 오른 것"을 상당 부분 걸러낼 수 있다.
  이건 무료 API로 충분히 가능하다.

#### 사용자가 쓰는 부분

- 논리 평가: `논리대로 맞았다` / `결과만 맞았다` / `논리는 맞았는데 결과가 안 나왔다` /
  `둘 다 틀렸다`
- 서술: 무엇을 놓쳤는지, 다음에 같은 상황이면 무엇을 다르게 볼 것인지 (자유 서술)
- 이 서술은 `[사용자]` 저작으로 표기되며, 이후 회고 리포트(§3.10)의 원재료가 된다

#### 회고록을 강요하지 않는다

- 판정 직후 자동으로 초안이 생성되지만, **바로 쓰라고 요구하지 않는다.**
- 안 쓴 회고록이 쌓여도 개수를 세거나 배지를 띄우지 않는다. (P5)
- 대신 같은 대상으로 **새 노트를 만들 때** 조용히 꺼내 보여준다.
  "이 종목으로 지난번에 이렇게 판단하셨습니다" — 회고록이 가장 필요한 순간은
  같은 실수를 반복하려는 바로 그때다.
- 회고록이 비어 있어도 AI 초안과 수치 기록은 그대로 남으므로, 나중에 언제든 쓸 수 있다.

### 3.7 AI 어드바이저
- 노트 상세 화면에서 "지금 어떻게 해야 할까?"를 AI에게 직접 물어볼 수 있다.
- AI는 현재 가설, 시나리오별 확률, 최근 수집된 정보를 근거로 **매수/홀드/매도 등 구체적인 스탠스**를
  명확히 제시한다. 애매한 원론적 답변이나 "전문가와 상담하세요" 같은 회피는 하지 않는다.
- 제시된 의견은 노트에 `AdvisorOpinion`으로 기록되어, 이후 리마인드 시점에 "그때 AI는 이렇게 말했고,
  나는 이렇게 판단했다"를 함께 되돌아볼 수 있다. (AI 의견의 적중률도 함께 축적됨)

### 3.9 보유 종목과 매매 기록

사용자의 실제 포지션을 기록하는 축이다. 원본 데이터는 **매매 기록**(날짜·매수/매도·단가·
수량·코멘트)이고, 보유 잔고는 매매 기록에서 파생된다. 매매는 가설에 대한 **행동**이므로
이 앱의 관점 기록과 별개가 아니다 — 코멘트 한 줄이 그 행동의 이유를 남기고, 수익률은
회고의 "결과는 숫자로" 축(§2.3)에 실제 내 성적을 공급한다.

수익률은 종목 단위(평단·평가손익·실현손익)와 포트폴리오 단위(XIRR, 아래) 둘 다
제공한다. 자산 곡선·일별 손익 그래프는 만들지 않는다 — 그건 증권사 앱이 이미 잘하는
일이다.

- **매매 기록 입력**: 종목(티커로 정규화 — `Note.target`과 같은 정규화), 매수/매도,
  날짜, 단가, 수량, 코멘트(선택). 수동 입력이며 증권사 계좌 연동은 하지 않는다(오픈 이슈).
  코멘트는 "그때 왜 샀는가/팔았는가"의 한 줄 기록이다 — 노트만큼 무겁지 않게, 그러나
  기록은 남게.
- **잔고는 파생 값이다.** 보유 수량 = Σ매수 − Σ매도. 별도의 수량 입력 필드를 두지 않아
  매매 기록과 잔고가 어긋날 길을 구조적으로 막는다. 매도 수량이 잔고를 넘으면 저장 전에
  결정론적 검사로 막는다. 앱 도입 전부터 보유하던 종목은 과거 날짜의 매수 기록 하나로
  등록한다 — 당시 단가를 모르면 **비워 둔다.** 그 종목의 수익률 칸은 `단가 없음`으로
  남는다. 지어낸 단가로 계산한 수익률은 하지도 않은 판단이다(§P: 빈 칸 원칙).
- **수익률 계산**: 평균 매수 단가는 이동평균법(매수 시 가중평균, 매도해도 평단 유지 —
  국내 증권사 표준과 같은 방식). 미실현 손익 = (현재가 − 평단) × 잔고,
  실현 손익 = (매도가 − 매도 시점 평단) × 매도 수량으로 종목별 누적.
  거래 수수료는 반영하지 않는다 — 0.01% 수준이라 무시해도 수익률이 왜곡되지 않는다
  (확정). 세금은 반영하지 않는다.
- **배당금 수령도 장부의 한 줄이다.** 주당 배당액 × 수량으로 기록한다(`side: dividend`).
  배당은 잔고 수량과 평단에 영향을 주지 않고, 달러 예수금(아래)과 종목별 배당 누적에만
  더해진다. 시세 차익 수익률에 합산하지 않는다 — 판단(가설)의 성적과 보유의 부산물은
  다른 성격의 숫자다. 배당 기준일 같은 예정 정보는 장부에 넣지 않는다(장부는 일어난
  일의 기록이다).

**외화와 환전 — 손익의 통화를 섞지 않는다**

- **미국 주식 손익은 달러로만 계산한다.** 매수·매도 시점 환율로 원화 환산해 손익을 적는
  증권사 방식은 양도소득세 계산용 장부의 문법이지 판단 검증의 문법이 아니다. 이 앱의
  수익률은 "그 종목 판단이 맞았나"를 재는 숫자이므로, 여기에 환율 변동이 섞이면 종목
  판단과 환율 판단이 뒤섞여 회고가 오염된다. 달러로 산 주식의 손익은 달러로 발생하고,
  원화 손익은 재환전하기 전까지 확정되지 않는다. 세금용 숫자는 증권사 앱이 이미 준다.
- **환전은 달러의 매매로 기록한다.** 원→달러 환전 = 달러 매수(단가 = 환율),
  달러→원 재환전 = 달러 매도. 평균 취득 환율은 주식 평단과 같은 이동평균법이고,
  재환전하는 순간 실현 환차손익 = (재환전 환율 − 평균 취득 환율) × 금액으로 확정된다.
  주식과 완전히 같은 문법이라 사용자가 새로 배울 것이 없고, 계산 코드도 같은 것을 쓴다.
- **달러 예수금은 파생으로 추적한다.** 예수금 = Σ환전(₩→$) + Σ매도 대금 + Σ배당 −
  Σ매수 대금 − Σ재환전($→₩). 배당을 장부로 받고 수수료를 무시하기로 했으므로 이 파생이
  성립한다. 직접 입력 필드는 없다 — 잔고와 마찬가지로 기록에서만 만들어진다.
  단, **정합성 검사로 입력을 막지 않는다.** 기록 누락은 흔한 일이고, 매수를 막으면
  기록 자체가 끊긴다. 예수금이 음수가 되면 숫자 대신 `기록이 맞지 않습니다 — 빠진
  매매나 환전이 있는지 확인해 주세요`를 조용히 보여준다.
- **원화 예수금은 추적하지 않는다.** 달러는 닫힌 계다 — 드나드는 길(환전·매매·배당)이
  전부 장부에 있어 잔고가 공짜로 파생된다. 원화는 열린 계다 — 급여·이체 등 앱 밖의
  경로로 수시로 드나들어, 추적하려면 입금/출금이라는 새 입력 부담이 생기고 하나만
  빠져도 틀린 숫자가 된다. 쓸모도 없다 — 원화 잔고에는 환율 이야기가 없고, "내 돈이
  얼마 있나"는 은행 앱의 일이다. **환전이라는 사건까지가 이 앱의 기록 범위이고,
  원화가 그 전에 어디에 있었는지는 범위 밖이다.**
- **미실현 환차손익은 "환전 원금 잔량" 기준으로 계산한다.** 환전 원금 잔량 =
  Σ환전(₩→$) − Σ재환전($→₩) — 주식 잔고와 같은 문법이다. 미실현 환차손익 =
  (현재 환율 − 평균 취득 환율) × 환전 원금 잔량. 주식 매매로 번 달러와 배당에는
  취득 환율이 없으므로 환차손익을 주장하지 않는다 — 재환전이 원금 잔량을 넘어서는
  부분(달러로 번 돈의 환전)은 환차손익 없이 원화 수령액 그대로 기록된다.
  지어낸 취득 환율로 노출 전체를 곱하는 것보다 좁지만 정직한 숫자다.
- **원화 환산 평가금액은 종목별 참고 표기다.** 현재 환율(조회 시점 표기)로 환산해
  평가금액 아래 작게 붙인다 — "결국 원화로 얼마쯤인가"는 궁금한 게 당연하다.
  다만 이 값은 미실현이며, 합산하지 않는 원칙은 그대로다.
- 환율 시세는 현재가와 같은 경로(시세 API + 전역 캐시 + 조회 시점 표기)로 조회한다.
  환전의 코멘트도 판단 기록이다 — "연준 인하 전에 미리 환전"은 환율에 대한 가설이고,
  재환전으로 실현 환차손익이 확정될 때 회고의 재료가 된다.
- **목록은 국내/미국/환전 세 탭으로 나눈다.** 국내·미국은 통화와 거래 시간대가 달라서,
  환전은 "환전에만 집중해서 보고 싶을 때"가 있어서다(사용자 결정). 환전 탭에는 달러
  요약(예수금·환전 원금 잔량·평균 취득 환율·현재 환율·환차손익 평가/실현)과 환전
  기록이 산다. 종목이 어느 탭인지는 사용자가 고르지 않고 티커 정규화에서 자동으로
  정해진다. 넛지 정렬(노트 없는 종목이 위)은 각 탭 안에서 동일하게 적용된다.
- **매매 기록 목록은 탭을 따라 필터된다.** 국내 탭 = 국내 종목 거래·배당,
  미국 탭 = 미국 종목 거래·배당, 환전 탭 = 환전. 각 탭은 자기 기록만 보여준다.
- **현재가 표시**: 시스템이 시세 API(한국투자증권)로 최신 가격을 조회해 보여준다.
  화면을 열 때 온디맨드 REST 조회이며, 조회 시점을 가격 옆에 함께 표기한다.
  실시간 스트리밍이 아니다 — "실시간 시세 불필요"라는 비용 구조(§6)는 그대로 유지된다.
  - **짧은 전역 캐시(TTL 수 분)를 통과시킨다.** 새로고침 연타나 여러 사용자가 같은
    종목을 보유한 경우의 중복 호출로부터 API 쿼터를 보호한다. Series Service의
    전역 캐시와 같은 원칙이며, "화면을 열 때 조회"의 실체는 "캐시가 TTL보다 묵었으면
    조회"다.
  - **장중/폐장을 판별하는 로직은 두지 않는다.** 실시간을 약속하지 않으므로 분기할
    이유가 없다. 폐장이면 API가 마지막 체결가(=종가)를 돌려주고, 화면은 조회 시점만
    정직하게 표기한다. 가격의 체결 시점까지 표기하지 않는 것도 같은 이유다 — 그걸
    하려면 장 시간 인지가 다시 필요해진다.
  - **조회 실패 시** 가격·평가금액 칸만 `조회 실패 · 다시 시도`로 두고, 목록(종목·수량·
    노트 연결·넛지)은 정상 동작한다. 가격은 이 화면의 부가 정보지 본체가 아니다.
- **종목별 표시 항목**: 잔고 수량, 평균 매수 단가, 현재가, 평가금액(수량×현재가),
  수익률(미실현), 실현 손익. 전부 매매 기록과 현재가에서 그 자리에서 계산하며 저장하지
  않는다.
- **포트폴리오 수익률은 XIRR(금액가중)로 계산한다.** 장부의 모든 흐름을 날짜별로
  나열하고(매수 −, 매도·배당 +, 마지막에 현재 평가금액 +) 연환산 내부수익률을 푼다.
  예수금 잔고는 식에 등장하지 않으므로 원화 예수금을 추적하지 않아도 계산에 어려움이
  없다. 두 개를 둔다 — ① **원화 기준 전체**: 환전 기록의 원화 금액(환율×달러액)을
  흐름으로 쓴다. 달러 세계 내부의 거래는 식에 안 들어가고, 환차손익이 자연히 포함된
  "원화로 잰 총성적"이 나온다. ② **달러 축**: 달러 흐름만으로 계산한다 — 환율을 배제한
  종목 판단의 성적. 단가 없음(null) 기록이 있는 종목은 계산에서 제외하고 제외 사실을
  표기한다. TWR(시간가중, 벤치마크 비교용)은 이후 단계에서 검토한다(오픈 이슈).
- **수익률은 탭별로도 보여준다.** 전체 XIRR은 탭 위에 한 줄(우측 정렬, 큰 숫자),
  각 탭 첫 줄에는 그 탭의
  성적 — 국내 탭: 국내 XIRR(원화)·평가손익 합·실현 손익 합, 미국 탭: 미국 XIRR(달러)·
  평가손익 합(달러), 환전 탭: 환차손익 평가·실현과 취득 환율 대비 변화율. "미국장에서
  얼마 벌었나", "환전으로 얼마 벌었나"를 각자 자리에서 바로 답한다. 탭 안은 단일
  통화이므로 손익 금액 합산이 성립한다.
- **손익 추이 차트 — 스냅샷은 시스템이 찍는다.** 날짜별 누적 손익을 라인차트로
  보여주되, 사용자가 수익 기록을 남기지 않는다. 장부는 임의의 과거 날짜의 잔고·평단을
  재구성할 수 있고, 일별 종가(Series Service)와 일별 환율(ECOS)이 있으므로 과거 전
  구간의 손익 곡선이 계산으로 복원된다. 야간 배치가 하루 한 점씩 적재하고(종가 기준,
  미마감 당일 제외 — 기존 시세 원칙 그대로), 과거 날짜의 매매를 추가·수정하면 해당
  구간을 소급 재계산한다. 축은 탭을 따른다 — 국내: 누적 손익(원), 미국: 누적 손익(달러),
  환전: 환차손익(원). 화면에는 상시 노출하지 않고, 각 탭 수익률 요약 줄의
  `과거 수익률 차트 보기` 버튼으로 여는 우측 시트에 담는다(UX §3.7). 추이선에 색을
  쓰지 않는 기존 문법(UX §7)을 그대로 따른다.
- **만들지 않는 것**: 통화를 섞는 합산(전체 자산 총액과 그 곡선 — 환산 없이는 성립하지
  않는 숫자다), 기간 선택·기술 지표 같은 차트 조작 기능.
- **회고와의 연결**: 갈래가 판정되어 회고록이 열릴 때, 그 종목의 매매 기록이 있으면
  벤치마크 대비 수익률(§7.5)에 지수 수익률뿐 아니라 **실제 내 매매 성적**을 나란히
  놓을 수 있다. "논리는 맞았는데 나는 벌지 못했다"(타이밍 문제)가 처음으로 화면에
  드러난다.

이 목록의 진짜 산출물은 **"보유 중인데 판단 기록이 없는 종목"**이라는 상태다.
보유하고 있다는 것은 이미 판단을 내렸다는 뜻인데 그 판단이 기록돼 있지 않다면,
그게 바로 이 앱이 채워야 할 빈칸이다.

- 보유 종목 목록에서 각 종목은 연결된 노트 개수를 보여주고, 노트가 없는 종목에는
  그 자리에 `+ 노트 추가` 버튼을 세운다. `아직 기록된 판단이 없습니다` 안내는
  버튼 툴팁으로만 띄운다 (UX §3.7).
- 홈 피드에 같은 넛지를 카드로 얹는다. 단, 리마인드 카드보다 항상 아래 순위이고,
  개수를 세어 압박하지 않는다(P5). 노트 만들기를 누르면 해당 종목이 대화의 출발점으로
  넘어간 채 1단계 대화가 시작된다.

**가설 후보 제안(Phase 2)**: 보유 종목을 시드로 AI가 노트 작성 대화의 진입점을 제안한다.
완성된 가설 문장을 주고 수락받는 방식은 금지다 — 그러면 회고에서 검증되는 것이
사용자의 논리가 아니라 AI의 논리가 된다. AI는 "이 종목에 최근 이런 이슈가 있는데,
보유하고 계신 논리와 관련이 있나요?"처럼 **질문까지만** 던지고, 가설 문장은 여전히
1단계 대화에서 사용자에게서 끌어낸다(§3.1). 종목 관련 이슈를 훑는 리서치가 필요하므로
주기적 리서치가 들어오는 Phase 2에 함께 묶는다.

### 3.10 회고 리포트 & 학습 (장기 로드맵)
- 회고록이 쌓이면 개인의 판단 패턴을 분석한다.
- "결과가 맞은 8건 중 3건은 논리가 틀렸다", "나는 늘 6개월 빠르게 예상한다" 같은 인사이트.
- 적중률만 보여주는 것은 금지한다. 적중률은 운을 실력으로 포장하는 지표다.
  **논리 정확도와 결과 정확도를 항상 분리해서 보여준다.**

## 4. 사용자 플로우 (핵심 시나리오)

1. 사용자가 관심 종목에 대해 투자 노트를 작성 — 가설 + 시나리오(시점 포함) 입력
2. AI가 초기 리서치를 수행해 참고할 만한 배경 자료를 정리해서 첨부
3. 시스템이 리마인드 일정을 자동 생성
4. 시간이 지나며 AI가 지속적으로 관련 뉴스를 모니터링, 유의미한 소식은 즉시 카드로 정리해 노트에 첨부
5. 리마인드 시점이 되면 알림 → 사용자는 "과거 나의 관점 + 그동안의 새 정보"를 한 화면에서 확인
6. 사용자는 시나리오 확률을 조정하거나, 시나리오의 결과를 정하거나, 새 시나리오를 추가
7. 필요하면 AI 어드바이저에게 "지금 어떻게 해야 할까?"를 물어 구체적인 매수/홀드/매도 의견과
   근거·철회 조건을 받고, 그 의견을 노트에 기록
8. 판단 시점이 되거나 auto 조건이 달성되면 결과를 확인한다 — 예상한 일이 일어났는가
9. 결과가 확정되면 **회고록**이 열린다. AI가 근거 항목을 사후 조사하고 벤치마크와 대비한
   초안을 만들어 두면, 사용자가 "제대로 맞춘 것인지 소 뒷걸음질인지"를 판단해 서술한다
10. 같은 대상으로 새 노트를 만들 때 과거 회고록이 조용히 소환된다

```
 ├─ exchanges: [Exchange]   (환전 기록 — §3.9. 달러를 자산처럼 다룬다)
 └─ Note (투자 노트)
     ├─ target: { type: ticker|asset|theme, symbol, name }
     ├─ thesis_summary: string
     ├─ thesis_detail: text

     └─ is_complete: boolean  (필수 항목 충족 여부. false면 리마인드 제외)

Trade (매매 기록 — §3.9. 이것이 원본이고 잔고는 파생)
 ├─ target: { type: ticker, symbol, name }   Note.target과 같은 정규화
 ├─ side: buy|sell|dividend   dividend는 배당금 수령 — price에 주당 배당액.
 │                            잔고·평단에 영향 없음. 예수금과 배당 누적에만 더해진다

 ├─ price: number|null      종목 통화 기준. 과거 보유분 등록 시 모르면 null —
 │                          지어내지 않고, 수익률 계산에서 그 종목을 제외한다
 ├─ quantity: number

 ├─ exchanged_at: date
 ├─ rate: number|null       원/달러. 과거 환전분 등록 시 모르면 null —
 │                          지어내지 않고, 환차손익 계산에서 제외한다
 ├─ usd_amount: number
 ├─ comment: text (선택)    왜 지금 환전하는가 — 환율에 대한 판단 한 줄
 └─ created_at
 ※ 평균 취득 환율은 Trade의 평단과 같은 이동평균법. usd_to_krw 시 실현 환차손익이
    확정된다. 미실현 환차손익 = (현재 환율 − 평균 취득 환율) × 환전 원금 잔량
    (Σkrw_to_usd − Σusd_to_krw). 달러 예수금은 Trade·Exchange에서 파생 추적하되
    (§3.9), 정합성 검사로 입력을 막지 않는다 — 음수면 기록 누락 안내만 띄운다.

PnlSnapshot (손익 추이의 파생 캐시 — 야간 배치가 적재. §3.9)
 ├─ date                    종가 기준. 미마감 당일은 만들지 않는다
 ├─ scope: kr|us|fx
 ├─ pnl                     누적 손익 (kr·fx는 원, us는 달러)
 └─ ※ 원본이 아니라 장부×일별 종가×일별 환율에서 언제든 재계산 가능한 캐시다.
      과거 날짜의 매매가 추가·수정되면 해당 구간을 소급 재계산한다.

Conversation (원본 대화 — 수정·삭제 불가)
 ├─ note_id
 └─ messages: [{ role: user|assistant, content, created_at }]

ContentBlock (노트 본문을 구성하는 블록)
 ├─ note_id, section: thesis|scenario|...
 ├─ content: text
 ├─ authorship: ai|user          ← user일 때만 UI에 [사용자] 표기
 ├─ quoted_from: message_id (nullable, 사용자 발화 직접 인용 시)
 └─ derived: boolean             AI가 해석해서 만든 값인지 (예: "내년 상반기" → 날짜)
                                 true면 미리보기에서 확인을 받는다

Galae (하나의 질문과, 그 질문에 대한 배타적인 답들)
 ├─ note_id
 ├─ question: text
 │     예) "올해 안에 엔비디아 HBM4 공급사로 진입하는가?"
 │     시나리오들이 무엇을 놓고 갈리는지 적는 자리. 이 문장이 없으면 화면에서
 │     시나리오 목록이 무엇의 답인지 알 수 없고, `그 외 예상 못한 전개`가
 │     무엇의 여집합인지도 정해지지 않는다. 갈래를 만들 때 함께 받는다.
 ├─ judge_at: { type: date|range, value }
 │     ★ 판단 시점은 갈래에 하나뿐이다. 시나리오마다 따로 두지 않는다.
 │       배타적인 답들이 서로 다른 날 판가름 난다는 것은 성립하지 않는다.
 │       날짜가 다르면 그것은 한 갈래가 아니라 별개의 질문 둘이므로,
 │       갈래를 나눠야 한다. 필드를 아예 두지 않아 구조적으로 막는다.
 ├─ scenarios: [Scenario]   (2개 이상 + is_residual 하나. 확률 합 100%)
 ├─ references: [Reference]   확률을 매길 때 보여준 자료. 그때 무엇을 보고 판단했는지가
 │                            남아야 회고에서 "자료가 있었는데도 틀렸나"를 물을 수 있다
 ├─ status: open|judged
 └─ judge_at_reset_history: [{ from, to, reset_at, reason }]
      (시점을 다시 잡은 기록 — 회고용. 카드나 홈에는 드러내지 않음)

Scenario (갈래 안의 답 하나 — 검증 가능한 명제)
 ├─ galae_id
 ├─ name          그 질문에 대한 답. 결과로 쓴다 — 경로나 이유를 제목에 섞지 않는다
 │                 ○ "엔비디아 공급사로 진입하지 못한다"
 │                 ✗ "증설로 공급이 풀려 기술 격차만 확인"  (원인과 결과가 뒤섞임)
 ├─ description   그렇게 되는 경로와 이유. 메커니즘은 여기 쓴다
 ├─ trigger_conditions: text
 ├─ probability_history: [{ value, updated_at, reason: text }]
 │     전부 사용자의 판단이다 — AI는 확률 숫자를 내지 않으므로(§3.4) 출처 구분이 없다.
 │     최초값도 함께 보존된다 — "나는 자료를 보면 얼마나 흔들리는가"가 회고의 재료가 된다
 ├─ status: active|pending_judgment|confirmed|rejected
 ├─ status_reason (결과를 그렇게 정한 이유)
 ├─ is_residual: boolean  (`그 외 예상 못한 전개`. 삭제 불가, 최소 5%)
 └─ resolution                     이 답이 실현됐는지 어떻게 아는가
      ├─ type: auto|manual|complement
      │
      ├─ auto — 질문 자체가 공개된 수치에 관한 것일 때. 조건은 하나뿐이다.
      │    ├─ series: { provider: fred|ecos|kis, code, label }
      │    │     예) { provider:"fred", code:"DFF",       label:"미국 기준금리" }
      │    │         { provider:"kis",  code:"005930.KS", label:"삼성전자" }
      │    ├─ comparator: gte|lte|between|change_pct
      │    ├─ target_value / target_range / baseline_date
      │    │   ※ 기한 필드는 없다. 관측 창은 갈래의 judge_at 하나뿐이다 (§3.5)
      │    │   ※ 관측 규칙도 필드가 아니다. `기간 중 한 번이라도 닿으면 달성,
      │    │     장중 포함`으로 시스템 전체가 고정이다
      │    ├─ status: not_met|met  /  met_at: date (nullable)
      │    ├─ progress: float      목표까지 얼마나 왔는지 0~1
      │    └─ edit_history: [{ field, from, to, edited_at, reason }]
      │          사후에 목표값을 유리하게 낮추는 것을 막기 위한 이력. 회고 화면에 노출된다
      │
      ├─ manual — 사실이지만 계열로 살 수 없을 때. 사용자가 결과 확인 화면에서 표시한다
      │    └─ marked: happened|did_not_happen|null  /  marked_at
      │
      └─ complement — 다른 답들이 모두 아니면 이 답이다. 조건을 갖지 않는다.
           여집합인 답과 is_residual인 답이 여기 해당한다

Reference (확률을 매길 때 보여준 자료)
 ├─ galae_id
 ├─ scenario_id: (nullable)
 │     어느 답을 뒷받침하는 자료인지. 기저율처럼 어느 편도 아니면 null이다.
 │     화면에서는 이 값으로 자료를 답별 더미로 갈라 놓는다 (§3.4)
 ├─ kind: base_rate | evidence | market_view
 │     ※ 확률값을 담는 종류는 없다. 애널리스트 견해를 %로 환산하거나 AI가 추정치를
 │       내놓지 않는다 — 사용자가 낸 것 하나만 확률이다 (§3.4)
 ├─ headline: text     "엔비디아, 공급사 다변화 검토 착수"
 │                     base_rate는 "최근 5년간 …확정된 사례 7건 중 3건"처럼
 │                     분모와 분자를 문장에 그대로 담는다
 ├─ note: text         한 줄 요약 (nullable)
 ├─ sources: [{ title, url, published_at }]
 └─ fetched_at: date   자료는 시간이 지나면 달라지므로 언제 본 것인지가 중요하다

Watch (지켜보는 수치 — 판정하지 않는다)
 ├─ note_id
 ├─ series: { provider: fred|ecos|kis, code, label }
 └─ 목표값도 달성 판정도 없다. 노트 상세와 리마인드 화면에서 추이 차트로만 보인다.
    관련은 있지만 질문의 답은 아닌 수치가 여기 온다 — 판정에 섞이면 소 뒷걸음질을
    판정 단계에서 미리 만들어내기 때문이다 (§2.3)

Premise (근거 항목 — 내 논리의 중간 고리)
 ├─ note_id
 │     ★ 갈래나 시나리오가 아니라 노트에 붙는다. 회고의 논리 축이 검증하는 것은
 │       가설의 논리이지 답 하나의 논리가 아니다. 한 노트에 갈래가 둘이어도
 │       ("진입하는가", "격차가 좁혀지는가") 밑에 깔린 사슬은 하나다.
 │       반대 시나리오에 붙는 "이렇게 흘러간다면 이런 모습입니다" 목록은
 │       Premise가 아니라 Scenario.description의 확장이다 — 사용자의 논리가
 │       아니라 AI가 조사해 담은 서술이므로 회고의 검증 대상이 아니다.
 ├─ statement: text        사용자가 말한 그대로. 수치화하지 않는다
 │     예) "HBM 공급 부족이 2026년 내내 이어진다"
 ├─ order: int             논리 사슬에서의 순서 (A → B → C)
 ├─ linked_watch_id: (nullable)
 │     마침 계열로 살 수 있으면 지켜보는 수치로 올려 추이를 보여준다. 대부분 null이고,
 │     연결돼 있어도 판정하지 않는다 — 근거가 맞았는지는 회고에서 따진다
 └─ verification: [(회고 시 AI가 채운다. 갈래마다 회고가 열리므로 이력으로 쌓인다)]
      ├─ verdict: happened|did_not_happen|unverifiable
      ├─ summary: text
      ├─ verified_at: date
      └─ sources: [{ title, url, published_at }]

Review (회고록 — 이 앱의 최종 산출물)
 ├─ galae_id
 │     판정은 갈래 단위로 일어난다 — 그 질문의 답이 나온 날 열린다.
 ├─ realized_scenario_id      실제로 일어난 답
 ├─ outcome: confirmed|rejected        §3.4의 판정 결과 (결과 축)
 ├─ logic_verdict: (사용자가 정함 — 논리 축)
 │     logic_held        논리대로 맞았다
 │     outcome_only      결과만 맞았다 (소 뒷걸음질)
 │     logic_only        논리는 맞았는데 결과가 안 나왔다
 │     both_wrong        둘 다 틀렸다
 ├─ ai_draft: text                     AI가 자료조사 후 생성한 초안
 ├─ benchmark_comparison: {            "그냥 시장이 올라서" 여부 판별용
 │     scenario_return, index_return, sector_return, period
 │   }
 ├─ user_narrative: text               [사용자] 저작. 무엇을 놓쳤고 다음엔 무엇을 다르게 볼지
 ├─ drafted_at / written_at (nullable) 초안 생성 시점 / 사용자가 쓴 시점
 └─ status: draft_ready|written        안 쓴 채로 남아 있어도 압박하지 않는다

SeriesSnapshot (일별 관측값 — 전역 캐시)
 ├─ provider, code, date        ← (provider, code, date)가 유니크 키
 ├─ close: number          판정과 차트의 기준
 ├─ high / low: number     (nullable) 장중 터치 판정과 차트의 띠에 쓰임. 거시 계열은 null
 └─ fetched_at
   ※ 사용자별로 저장하지 않는다. 같은 계열은 모든 사용자가 공유한다.

Source (사용자 첨부)
 ├─ type: link|text|file|image
 ├─ content / url
 └─ created_at

ResearchItem (AI 수집)
 ├─ note_id, scenario_id (nullable, 노트 전체와 연관될 수도 있음)
 ├─ title, summary, url, published_at
 ├─ relation: supports|contradicts|neutral
 ├─ relevance_score
 └─ user_feedback: adopted|dismissed|none

AdvisorOpinion (AI의 액션 의견)
 ├─ note_id
 ├─ stance: buy|add|hold|trim|sell
 ├─ rationale: text (근거 요약)
 ├─ referenced_scenarios: [scenario_id]
 ├─ referenced_research: [research_item_id]
 ├─ target_price / target_timeframe (nullable)
 ├─ invalidation_condition: text (이 의견이 틀렸다고 볼 조건)
 ├─ created_at
 └─ user_action: followed|partially_followed|ignored|none  (사후 기록)

ReminderRule
 ├─ type: interval|galae_deadline|pending_judgment|event_triggered
 ├─ config
 ├─ next_trigger_at
 ├─ consecutive_unopened: int  (빈도 자동 조절용 내부 값 — 화면에 절대 노출하지 않음)
 └─ current_interval_weeks: int  (연속 미열람 시 2배씩 증가, 최대 12주)
```

## 6. 시스템 아키텍처 (초안)

```
[Client: Web App / (향후 Mobile)]
        │
        ▼
[Backend API Server]
   ├─ Notes/Scenarios CRUD
   ├─ Note Validator (결정론적 규칙 — LLM 아님)
   │    ├─ 구조 검증 (스키마)
   │    ├─ 출처 대조 (인용·전제가 원본 대화에 실재하는지)
   │    └─ 규칙 검사 → Issue[]
   ├─ 확률 재분배 (갈래 단위 원자적 갱신, 합계 100 불변식)
   ├─ Reminder Scheduler (cron/queue 기반)
   └─ Auth / User
        │
        ├──────────────────────────────┐
        ▼                              ▼
[AI Orchestration Layer]      [Series Service]
   ├─ Research Agent             ├─ 일 1회 배치 수집 (장 마감 후)
   │    ├─ 뉴스/웹 검색           ├─ auto 조건 달성 여부 평가
   │    ├─ 관련성 판단 & 요약      ├─ 전역 스냅샷 캐시
   │    └─ 시나리오 연결          │   (provider, code, date) 유니크
   ├─ Reminder Curation Agent    ├─ 상태 전이 시 리마인드 트리거
   ├─ Thesis Builder Agent       └─ 계열 카탈로그 검색
   │    └─ 질문 → 계열 후보 제안       (사용자 표현 → 실제 계열 코드 매핑)
   ├─ Review Agent
   │    ├─ 근거 항목 사후 조사
   │    └─ 벤치마크 대비 수익률 계산
   └─ Advisor Agent
        │                              │
        ▼                              ▼
[Data Store]
   ├─ RDB (Notes, Galae, Scenarios, Watches, Premises, Reviews, SeriesSnapshot, Users)
   ├─ Vector DB (노트/뉴스 임베딩 → 유사도 기반 관련 뉴스 매칭, 향후)
   └─ Object Storage (첨부 파일/이미지)
        │
        ▼
[External Integrations]
   ├─ 뉴스/검색 API
   ├─ 시세·거시계열 API (FRED / 한국은행 ECOS / 한국투자증권)
   └─ 알림 (Push / Email)
```

**Series Service를 별도 축으로 두는 이유**: AI 리서치와 완전히 다른 성질의 작업이다.
리서치는 비결정적이고 온디맨드이며 비용이 LLM 호출에 비례하지만, 수치 수집은 결정적이고
스케줄 기반이며 비용이 외부 API 쿼터에 걸린다. 실패 시 재시도 전략도 다르다.
(수치는 하루치를 놓쳐도 다음 배치에서 소급 수집하면 되지만, 리서치는 그렇지 않다.)
auto 판정 계열과 지켜보는 수치는 같은 서비스가 같은 캐시로 처리한다 — 다른 것은
평가를 하느냐 마느냐뿐이다.

### 외부 데이터 소스 선정

> 아래 수치는 2026년 8월 기준 확인값이다. 무료 티어 정책은 자주 바뀌므로 착수 시 재확인할 것.

**채택**

| 소스 | 범위 | 조건 | 비고 |
|---|---|---|---|
| **FRED** | 미국·글로벌 거시 (금리, CPI, 실업률, GDP) | 무료, API 키 발급 | 공공 데이터, 상용 이용 제약 없음 |
| **한국은행 ECOS** | 한국 거시 (기준금리, 물가, 환율, 수출입) | 무료, API 키 발급 | 공공 데이터 |
| **한국투자증권 Open API** | 국내·해외 주식 및 지수 시세 | 이용료 없음, 계좌 개설 필요 | REST + WebSocket, 초당 20건 제한, 리눅스 서버에서 동작 |

**배제 — 이유가 각기 다르다**

| 소스 | 배제 사유 |
|---|---|
| **yfinance** | Yahoo의 비공식 엔드포인트를 긁는 방식이고, Yahoo API 약관은 수익을 얻는 용도의 사용을 금지한다. 개인 학습·프로토타입용이며 이 앱이 유료화되는 순간 쓸 수 없다. 엔드포인트가 예고 없이 바뀌어 깨지는 문제도 있다. |
| **Alpha Vantage** | 무료 티어가 **하루 25요청**(분당 5요청)으로 축소되어 실사용이 불가능하다. 계열 수십 개를 매일 수집하는 이 앱의 요구를 충족할 수 없다. |
| **Finnhub** | 무료 티어(분당 60요청)가 **비상업 용도로 제한**된다. 유료화 시 사용 불가라 yfinance와 같은 문제를 안는다. |
| **Polygon.io** | 무료 플랜이 분당 5요청 + 장 마감/15분 지연 데이터로 좁고, 무료 티어 유지 여부에 대한 정보가 엇갈린다. 유료 전환 시 후보로 재검토. |
| **키움증권 Open API** | Windows 32bit COM 객체 방식이라 리눅스 백엔드에서 쓸 수 없다. |

**프로토타입 단계의 예외**: 개발 초기에 `yfinance`로 빠르게 데이터 파이프라인을 검증하는 것은
가능하다. 단 **출시 전 반드시 교체한다는 전제**로만 쓰고, 데이터 소스 인터페이스를 추상화해
교체 비용을 낮춰 둔다. 프로토타입 코드가 그대로 상용에 남는 것이 가장 흔한 사고다.

**설계상 유리한 점**: 이 앱은 **실시간 시세가 필요 없다.** 수치는 종가 기준으로 하루 1회
평가하면 충분하고, 거시 통계는 월·분기 단위로 갱신된다. 실시간 요구가 없으면 위 무료 소스만으로
충분히 상용 서비스를 운영할 수 있다. 이것이 이 기능의 비용 구조를 결정한다.
보유 종목(§3.9)의 현재가 표시도 이 원칙 안에 있다 — 화면을 열 때 온디맨드 REST 조회
(종목당 1건, 초당 20건 제한 내)이지 스트리밍 구독이 아니다.

## 7. AI 기능 상세 설계

### 7.1 Research Agent
- **입력**: 노트의 target, thesis_summary, 각 시나리오의 description/trigger_conditions
- **동작**:
  1. 키워드/엔티티 추출
  2. 웹/뉴스 검색 실행
  3. 검색 결과 중 관련성 높은 것만 필터링 (relevance_score 산출)
  4. 각 결과를 요약하고, 어떤 시나리오를 지지/반박하는지 분류
  5. 노트에 ResearchItem으로 저장, 유의미도가 높으면 즉시 알림 트리거
- **실행 주기**: 기본 주기(예: 매일 1회) + 사용자 온디맨드 요청

### 7.2 Reminder Curation Agent
- 여러 경로에서 발생한 리마인드(정기/시점/새 정보)를 모아 우선순위를 정하고 한 번에 묶어 보내,
  알림이 과도해지지 않게 한다
- 리마인드 시 "과거 관점 요약 + 새 정보 요약 + 재평가 유도 질문" 형태로 콘텐츠 구성

### 7.3 Thesis Builder Agent (대화형 노트 작성)
노트 작성의 보조가 아니라 **작성 수단 그 자체**다. 대화를 통해 필수 항목을 확보하고
노트를 작성한다.

- **대화 단계**: 대상 파악 → 관심 이유 → 핵심 가설 → 반대 시나리오 → 판단 시점 → 확인 방법
- **질문 예시**
  - "반대로 흘러간다면 어떤 모습일까요?"
  - "이건 언제쯤 판가름 날까요?" (시점 확보 — 가장 집요하게)
  - "그날 무엇이 확인되면 답이 나오는 건가요?" (갈래의 질문 확보)
  - "무엇을 보면 그렇게 되고 있다는 걸 알 수 있을까요?"
  - "이 판단이 틀렸다는 건 뭘로 알 수 있을까요?" (반증 가능성)
- **턴 수 목표: 5~8턴.** 심문처럼 느껴지면 작성을 포기하게 되므로 길이 관리가 중요하다.
- **노트 생성**: 산문이 아니라 **구조화된 객체**를 반환한다. 렌더링은 클라이언트가 한다.
  채우는 칸과 각 칸의 규칙은 §3.1 '노트 생성 계약'에 정의되어 있다.
  - 대화에 없는 내용을 채워 넣지 않는다. 빈 칸은 비운 채로 반환한다.
  - 근거 항목(`premise.statement`)은 사용자의 말을 다듬지 않고 그대로 옮긴다.
  - 시점 문자열("내년 상반기")을 날짜로 해석했으면 해석 결과를 함께 반환해
    미리보기에서 확인받는다.
- **갈래를 나누는 판단은 여기서 한다.** 대화에서 판가름 나는 날짜가 둘 이상 나오면
  시나리오를 한 갈래에 몰아넣지 않고 갈래를 나눠 반환한다. 배타적인 답들이 서로 다른
  날 결판난다는 것은 성립하지 않기 때문이다. 예를 들어 "올해 안에 수주가 나오는가"와
  "2027년까지 기술 격차가 좁혀지는가"는 같은 가설에 대한 별개의 질문이므로
  한 노트 안의 두 갈래가 된다.
- **시나리오 이름에 이유를 섞지 않는다.** 이름은 질문에 대한 답만 담고, "왜 그렇게
  되는가"는 `description`으로 내린다. 이름에 경로가 섞이면 답들끼리 축이 어긋나
  확률 배분이 읽히지 않는다.
- **스키마 위반 처리**: 시나리오가 1개만 나왔거나 시점을 못 뽑았으면 **지어내지 않고**
  해당 칸을 비운 채 반환한다. 미완성 노트로 저장되고 화면에 무엇이 비었는지 표시된다.
- **원본 대화 보존**: 대화 전문을 수정·삭제 불가로 저장. AI가 노트를 쓰는 구조이므로,
  "실제로 내가 한 말"에 대한 접근 경로가 반드시 유지되어야 한다.

### 7.4 Probability Reference Agent (확률 자료 조사)

확률을 **대신 매기는 에이전트가 아니다.** 숫자를 내지 않고, 사용자가 스스로 가늠할
읽을거리를 답별로 갈라 놓는다.

- **출력은 자료 목록이지 확률이 아니다.** 애널리스트 견해를 %로 환산하지 않고,
  자기 추정치도 내지 않는다(§3.4). `증권사 12곳 중 7곳이 "연내 진입 가능"`은 자료 한 줄로
  넣고, 그것을 58%로 바꾸지 않는다.
- **자료마다 어느 답을 뒷받침하는지 판정한다.** `Reference.scenario_id`가 그 값이고,
  어느 편도 아니면 null이다. 이 판정은 새 정보 서랍의 뒷받침/어긋남 판정(§7.1)과 같은
  기준을 쓴다.
- **기저율은 분모와 분자를 그대로 문장에 담는다.** `7건 중 3건`이지 `43%`가 아니다.
  퍼센트로 줄이면 표본이 7건이라는 사실이 사라진다.
- **찾지 못하면 지어내지 않는다.** `찾은 자료가 없습니다`가 정상 응답이다. 한쪽 더미만
  쌓이는 것, 양쪽 다 비는 것 모두 사용자에게는 정보다.
- 결과는 `Reference`로 저장한다. 회고에서 "그때 어떤 자료를 보고 그 숫자를 냈나"를
  되짚을 수 있어야 한다.

### 7.5 Review Agent (회고 초안 작성)

시나리오 결과가 확정되면 실행된다. **이 앱의 최종 산출물을 만드는 에이전트**다.

- **입력**: 노트의 근거 항목(`Premise`) 목록, 갈래의 판정 결과, 대상 종목, 검증 기간
- **동작**:
  1. 각 근거 항목을 검색 질의로 변환해 해당 기간의 뉴스·공시·실적 발표를 조사
  2. 항목별로 `실제로 일어남` / `일어나지 않음` / `확인 불가`로 분류하고 출처를 붙인다
  3. **벤치마크 대비 수익률을 계산**한다 — 대상 종목 / 시장 지수 / 업종 지수를 같은 기간으로
     비교. 종목이 20% 올랐어도 업종이 25% 올랐다면 내 논리와 무관하게 움직인 것이다.
     대상 종목에 매매 기록(§3.9)이 있으면 **실제 내 매매 수익률**도 같은 기간에 나란히
     놓는다 — 종목은 올랐는데 내 성적이 못 미치면 논리가 아니라 타이밍의 문제가 드러난다.
     이 계산만으로도 "그냥 시장이 올라서"를 상당 부분 걸러낼 수 있고, 무료 API로 가능하다.
  4. 결과가 그대로 됐다면 그 결과의 **실제 원인으로 지목되는 다른 설명들**을 수집한다
  5. 초안 서술 생성
- **원칙**: **"이건 운이었습니다"라고 확정하지 않는다.** 사실과 대비만 제시하고 판단은
  사용자에게 넘긴다. AI가 논리의 옳고 그름을 선언하면 사용자는 스스로 생각하지 않게 되고,
  그러면 이 앱은 판단력을 기르는 도구가 아니라 대신 판단해주는 도구가 된다.
- `확인 불가`를 숨기지 않는다. 자료를 못 찾았으면 못 찾았다고 말한다.

### 7.6 Advisor Agent (직접 의견 제시)
- 사용자가 요청하면(또는 리마인드/리서치 결과와 함께) 현재 가설·시나리오·최신 정보를 종합해
  **명확한 액션 의견**을 제시한다.
  - 매수 / 추가매수 / 홀드 / 일부익절 / 전량매도 등 구체적 스탠스
  - 근거가 되는 시나리오와 정보, 목표 가격대·기간(가능한 경우)
  - 이 의견이 틀렸다고 판단할 조건(손절/철회 트리거)
- **프롬프트 원칙**: "투자 조언을 할 수 없다", "전문가와 상담하라" 류의 회피성 문구를 넣지 않는다.
  근거가 부족하면 회피하는 대신 "무엇을 더 알면 판단이 명확해지는지"를 말한다.
- **일관성 체크**: 사용자의 과거 가설과 현재 제시하는 의견이 상충하면 그 사실을 명시적으로 지적한다.
  (메멘토 컨셉의 핵심 — 과거의 나와 지금의 판단을 대조)
- 면책 문구는 AI 응답 본문이 아니라 UI 레이어에서 일괄 처리한다. (AI 출력에 매번 면책을 섞으면
  가독성과 신뢰도가 떨어지므로)

## 8. MVP 범위

투자 판단 보조라는 핵심 가치를 가장 빠르게 검증할 수 있는 범위로 제한한다.

**MVP 포함:**
- 홈: 가까운 미래 판단 시점 타임라인 + 리마인드 피드
- 대화형 노트 작성 (Thesis Builder Agent) → 노트 초안 생성 → 미리보기·수정 → 저장
- 원본 대화 전문 보존 및 열람
- 노트 상세: 좌(나의 관점) / 우(새 정보) 분리 레이아웃, 시나리오 보드
- 갈래별 확률 배분(합 100%, `그 외 예상 못한 전개` 포함) 및 변경 이력 조회(리스트)
- 확률 자료 조사: 답마다 뒷받침 자료를 갈라 제시 (숫자는 내지 않음)
- 시나리오 상태 변화 및 네 가지 선택지
- 확인 방법 설정 (노트 저장 후 2단계 폼, 건너뛰기 가능), 일 1회 수집·평가, 목표까지의 거리 표시
- 지켜보는 수치 (판정하지 않고 추이만) 등록과 차트
- 추이 차트 (노트 상세 축약형 + 결과 확인 전체형)
- 근거 항목 기록 (수치화 없이 서술로)
- 회고록: AI 초안(근거 항목 사후 조사 + 벤치마크 대비) + 사용자 서술
- 수치 데이터 소스: FRED + ECOS + 한국투자증권
- 리마인드 상세 3단 화면 (과거의 나 → 그동안의 일 → 지금은?)
- 기본 주기 리마인드 + 시점 기반 리마인드, 이메일 알림
- AI 리서치: 온디맨드 실행 (노트 상세 화면 "지금 다시 조사하기") — 자동 주기 실행은 이후 단계
- 수집한 정보에 뒷받침/어긋남 표시, 사용자 피드백(반영/무시)
- AI 어드바이저: 온디맨드로 매수/홀드/매도 스탠스와 근거를 받아보고 `AdvisorOpinion`으로 기록
- `[사용자]` 저작 표기
- 보유 종목·매매 기록: 매매 기록(날짜·매수/매도·단가·수량·코멘트) 수동 등록, 잔고 파생
  (국내/미국/환전 탭), 화면을 열 때 현재가 조회 표시(조회 시점 표기), 종목별 평단·평가금액·
  수익률·실현 손익, 배당금 수령 기록, 환전 기록과 실현·미실현(환전 원금 잔량 기준)
  환차손익, 달러 예수금 파생 표시, 포트폴리오 XIRR(전체 + 탭별), 탭별 손익 추이
  라인차트(시스템이 장부×종가로 전 구간 재구성), 미국 주식 원화 환산 참고 표기,
  노트 없는 보유 종목 넛지 (홈 피드 + 보유 종목 목록)
- 면책 고지 UI (온보딩 동의 + 전역 상시 노출)
- 반응형 웹 (데스크톱 전체 → 모바일 리마인드 확인 플로우 순으로 구현)

**MVP 제외 (이후 단계로 이연):**
- 자동 주기적 백그라운드 리서치 크롤링, 이벤트 기반 즉시 알림
- 벡터 검색 기반 정교한 관련성 매칭
- 확률 변화 그래프 시각화 (MVP는 이력 리스트로 대체)
- 회고/패턴 분석 리포트
- PWA 푸시 알림, 네이티브 모바일 앱, 소셜/공유 기능
- 보유 종목 기반 가설 후보 제안 (종목 이슈를 훑는 리서치가 필요해 Phase 2의 주기적 리서치와 묶음)
- 계좌 총액·자산 곡선·일별 손익 등 종목 단위를 넘는 손익 집계 (이연이 아니라 **영구
  제외** — §3.9), 수수료·세금·배당 반영, 환율 환산, 증권사 계좌 연동, 실시간 시세 스트리밍

## 10. 리스크 및 고려사항

- **투자자문 규제 리스크**: AI 프롬프트 자체는 매수/매도 의견을 자유롭게 낼 수 있도록 열어두는 대신,
  "최종 투자 판단과 그 책임은 사용자 본인에게 있다"는 면책 고지를 UI 전반(온보딩, 노트/리서치
  화면, 추천 카드 등)에 상시 노출한다. 다만 이는 제품 방향에 대한 결정이며, 실제 서비스 지역/약관에
  따라 투자자문업 관련 법적 리스크가 있을 수 있으므로 정식 출시 전 법률 검토가 필요하다.
- **정보 신뢰성**: AI가 수집한 뉴스/요약의 출처를 항상 함께 제공하여 사용자가 검증 가능하게 함.
- **알림 피로 / 죄책감**: 리마인드가 과도하거나 부채감을 주면 앱 자체를 안 열게 된다.
  미룬 횟수·달성률·스트릭·배지 카운트 같은 압박 장치는 제품 차원에서 금지하고, 반복해서 열리지
  않는 리마인드는 벌 대신 노출 빈도를 자동으로 낮춘다. (UX 설계 원칙 P5)
- **데이터 프라이버시**: 개인의 투자 관점/포지션은 민감 정보이므로 저장/전송 시 보안 설계 필요.
- **AI 비용**: 리서치 에이전트의 실행 빈도가 늘어날수록 API 비용 증가 → 사용자별/노트별 실행 정책 필요.
- **수치 데이터 소스 의존**: 무료 API의 티어 정책은 예고 없이 축소된다(Alpha Vantage가 하루
  500요청에서 25요청으로 줄어든 것이 실례다). 데이터 소스를 추상화 계층 뒤에 두어 교체 가능하게
  설계하고, 특정 제공자에 종속되는 코드를 만들지 않는다.
- **회고 리서치의 품질**: 근거 항목이 산업 특화 내용일수록 AI가 자료를 못 찾을 가능성이 높다.
  `확인 불가`가 대부분인 회고록은 가치가 없다. 벤치마크 대비 수익률은 언제나 계산 가능하므로,
  최소한 그것만이라도 항상 제공되도록 설계한다.
- **근거 항목이 비는 문제**: 사용자가 논리 없이 "느낌"으로 산 경우 근거 항목을 못 적는다.
  이 경우 회고할 대상 자체가 없다. AI가 대화에서 이를 확보하지 못하면 회고 기능 전체가
  형식만 남는다. 대화 설계의 품질이 곧 이 기능의 품질이다.
- **2단계 확인 방법 설정의 이탈률**: 건너뛸 수 있게 만든 대가로 대부분의 사용자가 이를 영영
  설정하지 않을 수 있다. 그래도 앱은 동작하지만 자동 판정이라는 차별점이 사라진다.
  2단계 진입률과 완료율을 초기 계측값으로 측정하고, 낮으면 1단계 말미에 최소 1개만 받는
  절충안을 검토한다.
- **목표값 사후 조작**: 나중에 유리하게 낮추면 복기가 무의미해진다. 수정 이력을 반드시
  보존하고 복기 화면에 노출한다.

## 11. 확정된 결정 사항

UX 설계 과정에서 확정된 항목들. 상세 근거는 [`ux-design.md`](./ux-design.md) 참조.

| 항목 | 결정 |
|---|---|
| 플랫폼 | 반응형 웹. 데스크톱 전체 → 모바일 리마인드 확인 플로우 순으로 구현 |
| 홈 화면 | 리마인드 피드(우선순위 순) 위, 세로 타임라인(시간 순) 아래. 노트 목록은 별도 탭 |
| 노트 상세 | 본문은 나의 사고. 새 정보는 오른쪽 책갈피로 여닫는 서랍. 데스크톱·모바일 동일 구조 |
| 타임라인 축 | 데스크톱·모바일 모두 세로. 화면 폭에 따라 여백만 달라진다 |
| 노트 작성 | AI와의 대화 → AI가 노트 작성. 폼 입력 방식은 쓰지 않음 |
| 동시 관리 노트 수 | 10개 내외 전제. 폴더/태그 없이 단순 리스트 + 검색 |
| 리마인드 강제성 | 없음. 미룸 횟수 기록·노출 금지, 스트릭/달성률 금지 |
| 누가 쓴 글인지 | AI가 쓴 글은 표시 없음, 사용자가 쓴 부분에만 `[사용자]` 표기 |
| 내 사고 ↔ 외부 정보 | 공간적으로 분리. 리마인드 화면에서만 의도적으로 대비 |
| 포지션 입력 | **매매 기록**(날짜·매수/매도·단가·수량·코멘트)을 원본으로 받고, 잔고·평단·수익률은 전부 파생 계산한다. 수익률은 종목 단위(평단·평가손익·실현손익), 탭 단위(XIRR·손익 합·손익 추이 차트), 전체(XIRR %)로 제공한다. 손익 추이는 사용자가 스냅샷을 찍지 않고 장부×일별 종가로 시스템이 전 구간을 재구성한다. 통화를 섞는 총자산 합산·곡선만 만들지 않는다. 현재가는 화면을 열 때 조회(전역 캐시 통과)해 조회 시점과 함께 표시한다 |
| 외화 손익 | 미국 주식 손익은 **달러로만** 계산한다 — 매매 시점 환율 환산(증권사 방식)은 세금 장부의 문법이지 판단 검증의 문법이 아니다. 환전은 달러의 매매로 기록한다(원→달러 = 매수, 달러→원 = 매도, 평단은 이동평균). 실현 환차손익은 재환전 시 확정, 미실현 환차손익은 **환전 원금 잔량** 기준으로만 계산한다 — 주식으로 번 달러와 배당에는 취득 환율이 없으므로 환차손익을 주장하지 않는다 |
| 장부의 범위 | 매수/매도/배당금 수령/환전이 하나의 시간순 장부에 흐른다. 달러 예수금은 장부에서 파생 추적하되(닫힌 계라 공짜) 정합성 검사로 입력을 막지 않는다(음수면 누락 안내만). **원화 예수금은 추적하지 않는다** — 열린 계라 입출금 기록 부담이 생기고, 환율 이야기도 없다. 환전이라는 사건까지가 기록 범위다. 거래 수수료는 무시(확정), 세금은 반영하지 않음, 배당 기준일 같은 예정 정보는 장부에 넣지 않는다 |
| 가설 후보 제안 | 보유 종목을 시드로 AI가 제안하되 **질문까지만.** 완성된 가설을 주고 수락받으면 회고에서 검증되는 것이 AI의 논리가 된다. 가설 문장은 항상 1단계 대화에서 사용자에게서 나온다 (Phase 2) |
| 확률 표현 | 갈래 안에서 합 100%, 5% 단위로만 조정. 구성비는 도넛, 조정용 눈금 막대는 입력 화면에만, 카드의 변화 표시는 문장 |
| 확률을 누가 매기나 | **사용자.** AI는 사용자보다 먼저 숫자를 내지 않는다. 앵커링이 걸리면 노트에 남는 것이 내 판단이 아니라 AI의 판단이 되고, 회고의 논리 축과 캘리브레이션이 통째로 무의미해진다 |
| 확률 자료 | AI는 숫자를 내지 않는다. 답마다 그것을 뒷받침하는 자료를 갈라 모아 주고, 사용자가 양쪽 무게를 재서 나눈다. 애널리스트 견해를 %로 환산하지 않는다 — `12곳 중 7곳`은 사실이지만 `58%`는 아니다 |
| 못 매기겠으면 | 비워둔다. 빈 고리는 "아직 생각하지 않았다"는 정직한 기록이지만, AI가 채운 값은 하지도 않은 생각이다 |
| AI 의견 강도 | "적극 제안" 고정. 매수/매도 의견에 제약 없음 |
| 갈래 | 하나의 질문과 그 답들. 질문과 판단 시점은 갈래에 하나씩 붙고, 시나리오에는 붙지 않는다 |
| 반증 가능성 | 판단 시점은 모든 갈래에 붙인다. auto 판정은 필수가 아니다 — 없으면 사용자가 직접 표시한다 |
| 결과 vs 논리 | 결과는 시나리오의 판정 방법대로(auto/manual), 논리는 회고록에서 AI 조사 + 사용자 서술로 검증 |
| 근거 항목 | 수치화 불가해도 서술로 반드시 기록. 회고 때 AI 조사의 대상이 된다 |
| 회고록 | 판정 확정 시 AI 초안 자동 생성. 작성 강요·미작성 카운트 없음 |
| 작성 단계 | 1단계 대화(논리) + 2단계 폼(수치 설정)으로 분리. 2단계는 건너뛸 수 있음 |
| 근거 항목 수집 시점 | 반드시 1단계 대화 중. 나중에 물으면 사후 합리화된 답만 나온다 |
| 검증 가능한 명제 | 전부 시나리오다. 수치 조건은 시나리오 밑에 딸린 별개의 것이 아니라 시나리오의 판정 방법이다. 사건형 지표와 AND/OR 결합은 폐기 |
| 판정에 쓰지 않는 수치 | `지켜보는 수치`로 분리. 관련은 있지만 답이 아닌 수치가 판정에 섞이면 소 뒷걸음질을 판정 단계에서 만들어낸다 |
| 판정 | 앱은 제안만 한다. 자동으로 적중/실패를 확정하지 않는다. 조건이 서로 어긋나면 제안 자체를 하지 않는다 |
| 운/실력 구분 | AI는 사실과 벤치마크 대비만 제시하고, 운이었는지는 사용자가 판단한다 |
| 시세 데이터 | 실시간 불필요. 일 1회 종가 기준 배치 + 전역 캐시. 미마감 당일은 저장·표시 안 함 |
| 수치 시각화 | 기록선·목표선·그 사이 띠·추이·남은 기간을 한 그림에. 지켜보는 수치는 목표선 없이 추이만. 기간 고정, 기술 지표 없음 |
| 관측 규칙 | 사용자가 고르지 않음. `한 번이라도 닿으면 달성 · 장중 포함`으로 시스템 고정 |
| 노트 검증 | LLM이 아니라 결정론적 코드가 검사. blocking은 대상·가설 둘뿐 |
| 빈 칸 허용 기준 | 중요도가 아니라 **부패 여부**로 가른다. 나중에 채우면 값이 달라지는 칸(반대 시나리오·근거 항목·확률)만 저장 전에 1회 되묻고, 같은 값이 나오는 칸(auto 조건)은 되묻지 않는다 |
| 확률 무결성 | 검사하지 않고 불변식으로 보장. 개별 시나리오 확률 수정 API를 만들지 않는다 |

## 12. 오픈 이슈 (추후 논의 필요)

- 어떤 자산군까지 지원할지 (주식/코인/부동산/거시경제 테마 등)
- **기저율을 찾을 수 있는 갈래가 얼마나 될지.** `엔비디아 공급사로 진입하는가`처럼
  전례가 적은 질문에는 쓸 만한 표본이 없다. 대부분 "찾지 못했습니다"가 나온다면 이 기능이
  화면 자리만 차지하게 된다. 초기에는 몇 %의 갈래에서 기저율이 나오는지 측정할 것.
- **옵션 내재확률을 언제 넣을지.** 거래된 가격에서 나온 값이라 애널리스트 견해와 달리
  자료로 쓸 만하지만, 특정 종목의 가격 질문에만 존재한다. 넣는다면 다른 자료와 어떻게
  구분해 보여줄지 검토 필요.
- **한쪽 더미만 쌓이는 경우.** 뒷받침 자료가 한쪽에만 모이면 그것 자체가 신호지만,
  단순히 그쪽 뉴스가 많았을 뿐일 수도 있다. 자료 개수를 세어 보여줄지 말지 검토 필요.
- 계열 카탈로그를 어디까지 미리 등록할지. 사용자가 말한 표현("유동성")을 실제 계열로 매핑하는
  일이 이 기능의 사용성을 좌우하는데, 전부 AI에 맡길지 사전 사전(辭典)을 만들지 미정
- 암호화폐 계열을 넣을 경우의 데이터 소스 (현재 채택한 셋으로는 커버되지 않음)
- 매매 기록의 증권사 계좌 연동. MVP는 수동 입력이지만, 매매를 빠뜨리면 잔고가 실제와
  어긋난 채 방치될 수 있다. 연동하면 정확해지는 대신 "자산 관리 앱이 아니다"라는
  선이 흐려질 위험이 있어 신중히 검토
- 보유 종목 현재가의 해외 주식·암호화폐 커버리지 (한국투자증권 API가 닿지 않는 자산의 표시 방식)
- 세금(양도세·배당소득세) 반영 여부 — 수수료는 무시, 배당은 기록으로 확정됐고 세금만 남음
- TWR(시간가중수익률) 도입 여부 — 입출금 타이밍 효과를 제거한 "운용 실력" 지표로,
  회고의 벤치마크 비교와 궁합이 맞다. 구간 경계마다 포트폴리오 평가액이 필요해
  일별 종가 데이터 위에서 계산해야 한다
- 세금 신고 참고용 수치(매매 시점 환율 기준 양도손익) 제공 여부. 판단 검증 축과는
  별개의 계산이라 넣는다면 완전히 분리된 화면이어야 한다
- 달러 외 통화(엔·유로 등) 지원 시점. 현재 설계는 원/달러 한 쌍 전제
- 주식 분할·병합 처리. 분할이 일어나면 과거 매매 기록의 단가·수량 보정이 필요한데,
  자동 감지할지 사용자에게 맡길지 미정
- auto 조건 달성 알림을 이벤트 기반 즉시 알림으로 볼지, 일일 배칭에 포함할지
- 벤치마크를 무엇으로 잡을지 (코스피/코스닥/S&P500은 쉬우나 업종 지수는 매핑이 필요)
- 회고록을 안 쓴 채로 오래 두면 AI 초안의 자료 링크가 만료될 수 있다. 초안 생성 시점에
  본문을 스냅샷으로 보관할지 검토
- 뉴스/데이터 소스 API 선정
- 무료/유료 정책 (AI 리서치 실행 횟수 제한 등)
- 노트 작성 대화의 적정 턴 수 (목표 5~8턴, 실측 필요)
- 인용 대조(검증 2층)의 매칭 관대함 — 공백·개행 정규화 후 완전 일치로 시작하되,
  LLM이 조사·어미를 미세하게 바꿔 강등이 잦으면 허용 편집 거리 도입 검토
- 타임라인 구간 경계값(`이번 주 / ~1개월 / ~3개월 / ~6개월 / 그 이후`)의 실사용 적합성
- 노트 간 거시 변수 연결을 언제 도입할지 (가치는 크나 내비게이션 단순성과 충돌)
- AI 의견 강도를 사용자가 조절 가능하게 할지

## 13. 구현 마스터플랜

프로토타입(`prototype-mvp.html`)을 실제 동작하는 앱으로 만드는 실행 계획이다.
**이 절이 구현의 진입점이고, 분야별 상세는 하위 문서(§13.4)가 담당한다.**
기획·기능 명세(§1~§12)와 어긋나는 내용이 하위 문서에서 발견되면 이 문서가 우선한다.

### 13.1 확정 스택 요약

§6의 확정 표가 정본이다. 한 줄로 줄이면 —

> **Next.js(웹) + FastAPI(API·워커) + Supabase(Postgres·Auth·Storage) + Claude API,
> 처음부터 멀티유저.**

클라이언트는 FastAPI만 호출한다(로그인만 Supabase Auth SDK). 배치는 워커 프로세스의
APScheduler 크론, 온디맨드 AI 작업은 Postgres jobs 테이블 폴링으로 처리한다 —
MVP 규모에서 Redis·메시지 큐는 두지 않는다.

### 13.2 리포 구조 (모노레포)

```
invest_memento/
 ├─ apps/
 │   ├─ web/        Next.js (App Router, TypeScript)
 │   └─ api/        FastAPI — API 서버 · 워커 · AI 에이전트 · Series Service
 ├─ supabase/       마이그레이션(DDL 정본) · 시드
 ├─ fixtures/       골든 테스트 벡터 (확률 재분배 등 — Python·TS 양쪽 CI가 검증)
 └─ docs/           기획·설계 문서 (본 문서 포함)
```

### 13.3 검증 규칙 공유 방침 — Python 백엔드에 맞춘 조정

§3.1은 "클라이언트와 서버가 같은 검증 규칙을 한 패키지로 공유"를 요구했다. 이는
백엔드가 TypeScript일 때의 구현 수단이었고, FastAPI 확정으로 수단을 조정한다.
**원칙(두 곳이 어긋나지 않는다)은 유지하고, 공유 방법만 바꾼다.**

| 규칙 | 정본 | 클라이언트 즉시 피드백 | 어긋남 방지 |
|---|---|---|---|
| 노트 검증기 (3층·Issue) | 서버 Python 단일 구현 | `validate` API 호출 (미리보기 진입 시·디바운스). 클라이언트 재구현 없음 | 구현이 한 곳뿐이므로 어긋날 수 없다 |
| 확률 재분배 (스냅·잠금·최대 잔여법) | 서버 Python 구현 | 슬라이더 조작감을 위해 **TS 미러 구현 허용** (유일한 이중 구현) | `fixtures/`의 골든 테스트 벡터(§3.1의 검증 사례 포함)를 Python·TS 테스트가 모두 통과해야 CI가 초록 |
| 장부 파생 계산 (잔고·평단·XIRR 등) | 서버 Python 단일 구현 | API 응답 값 표시만 | 구현이 한 곳뿐 |

### 13.6 마일스톤 횡단 규칙

- **도메인 규칙은 전부 순수 함수 + 단위 테스트.** 검증기·재분배·장부 계산·auto 평가가
  대상이다. 화면 없이 테스트로 먼저 맞춘다.
- **계측 훅은 해당 기능과 같은 마일스톤에 심는다.** 2단계 진입·완료율은 M4, 대화
  턴 수는 M3. 나중에 붙이면 초기 데이터가 사라진다(§10).
- **yfinance는 M4 개발 중 파이프라인 검증에만** 쓴다. provider 어댑터 뒤에 격리하고
  출시 전 제거를 M9 체크리스트에 넣는다(§6).
- **마이그레이션 먼저, 코드 나중.** 배포 순서로 스키마-코드 불일치를 만들지 않는다.
- 각 마일스톤의 DoD에는 항상 **프로토타입 해당 화면과의 대조**가 포함된다 —
  `prototype-mvp.html`이 화면의 수용 기준이다.
