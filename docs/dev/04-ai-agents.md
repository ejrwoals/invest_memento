# AI 에이전트 — Claude API 기반 설계

> 상위 문서: [`development-plan.md`](../development-plan.md) §2.4(AI의 역할)·§7(AI 기능 상세)·§13(구현 마스터플랜).
> 인접 문서: [`01-db-schema.md`](./01-db-schema.md)(출력이 저장되는 테이블),
> [`02-backend.md`](./02-backend.md)(jobs 워커·API 경계), [`ux-design.md`](../ux-design.md) §3.2·§9(화면과 문구).
>
> 이 문서는 `apps/api/agents/` 모듈의 정본이다. 에이전트별 프롬프트 전문은 코드
> (`agents/prompts/`)에 두고, 여기에는 **요지와 계약**만 적는다. 프롬프트 문장을
> 바꾸는 것은 자유지만, 이 문서의 계약(출력 스키마·검증·원칙)을 바꾸려면 문서를 먼저 고친다.

## 1. 전제

- **LLM은 Claude API**다. Anthropic SDK for Python으로 FastAPI 백엔드에서 호출한다.
  에이전트는 별도 서비스가 아니라 `apps/api/agents/` 모듈이다.
- 기본 모델은 `claude-sonnet-5`. 품질 민감 작업(대화·회고·어드바이저)은 상위 모델
  (`claude-opus-5`)을 A/B로 검토한다 (§7 모델 표).
- 웹 검색은 Claude API의 **web search server tool**(`web_search_20260209`)을 쓴다.
  검색 실행·출처 수집이 서버 측에서 일어나므로 크롤러를 직접 만들지 않는다.
- **동기는 Thesis Builder 대화뿐이다.** 사용자가 화면에서 기다리는 유일한 호출이라
  스트리밍으로 응답한다. 나머지 온디맨드 작업(리서치·확률 자료·회고 초안·어드바이저)은
  Postgres `jobs` 테이블에 넣고 워커가 폴링해 실행한다 — 큐·워커의 정의는
  [`02-backend.md`](./02-backend.md)가 정본이다.

## 2. 프롬프트 헌법 — 다섯 원칙

모든 에이전트의 시스템 프롬프트가 공유하는 원칙이다. 각 원칙은 상위 문서의 결정을
프롬프트 층에 옮긴 것이므로, 여기서 어기면 제품 설계가 무너진다.

| # | 원칙 | 근거 | 어느 에이전트에 어떻게 걸리나 |
|---|---|---|---|
| 1 | **대화에 없는 내용을 쓰지 않는다.** 빈 칸은 비운 채 반환한다 | §3.1 | Thesis Builder 전반. 시나리오가 1개뿐이면 지어내지 않고 비운다. 나오지 않은 갈래(질문)를 만들지 않는다(§3.4). Review Agent도 같은 원칙의 변형 — 조사에서 확인 못 한 것을 서술로 메우지 않는다 |
| 2 | **가설은 사용자의 입에서 나온다.** AI는 질문까지만 | §2.4 | Thesis Builder는 가설 문장을 제안하지 않고 끌어낸다. `premise.statement`는 다듬지 않고 원문 그대로. Phase 2 가설 후보 제안도 질문까지만(§3.9) |
| 3 | **AI는 확률 숫자를 내지 않는다.** 사용자보다 먼저 어떤 %도 출력하지 않는다 | §3.4 | Probability Reference Agent의 존재 이유 — 자료를 가르되 환산하지 않는다. 기저율은 분모·분자 그대로. Thesis Builder는 대화에 나온 표현(`반반쯤`)만 옮긴다. Advisor Agent도 시나리오 확률을 대신 매기지 않는다(스탠스는 내되 확률은 안 낸다) |
| 4 | **면책은 UI의 책임이다.** 프롬프트에 회피·면책 지시를 넣지 않는다 | §2.4·§3.8 | Advisor Agent가 핵심 — "전문가와 상담하세요" 류 문구 금지, 소신 있는 스탠스 요구. 다른 에이전트도 출력에 면책 문장을 섞지 않는다(카드마다 UI가 붙인다) |
| 5 | **찾지 못하면 `찾은 자료가 없습니다`가 정상 응답이다.** 빈 결과를 그럴듯한 내용으로 메우지 않는다 | §3.4·§7.4·§7.5 | Probability Reference(한쪽 더미가 비는 것 자체가 정보), Research(관련성 낮으면 0건 반환), Review(`확인 불가`를 숨기지 않는다) |

이 다섯 줄은 공통 프리앰블로 한 파일(`agents/prompts/constitution.md`)에 두고
모든 시스템 프롬프트 앞에 붙인다. 에이전트별 프롬프트는 그 뒤에 온다 —
프리앰블이 안정적이어야 프롬프트 캐시 프리픽스가 산다(§7).

## 3. 공통 인프라

### 3.1 호출 래퍼 (`agents/client.py`)

Anthropic SDK 클라이언트를 얇게 감싼 단일 진입점. 모든 에이전트가 이걸 통해 호출한다.

- **재시도·타임아웃**: SDK 기본 재시도(429·5xx 지수 백오프, `max_retries=2`)를 그대로
  쓰고, 타임아웃은 작업별로 지정한다(대화 스트리밍은 짧게, 웹 검색 동반 작업은 길게).
  같은 일을 래퍼에서 다시 구현하지 않는다.
- **토큰 로깅**: 호출마다 `usage`(input/output/cache_read/cache_creation)와
  `_request_id`, 에이전트 이름, 프롬프트 버전을 구조화 로그로 남긴다. 비용 가드(§3.5)와
  계측(§6)의 원천 데이터다.
- **모델 선택은 호출부가 아니라 설정이 한다.** `agents/config.py`의 작업→모델 표
  하나로 관리해 A/B와 모델 교체가 코드 수정 없이 되게 한다.

### 3.2 구조화 출력 — tool 강제 + 코드 검증

노트 생성 계약(§3.1)의 구현 패턴이다. 산문을 파싱하지 않는다.

```
1. 출력 스키마를 tool 정의(input_schema)로 선언하고 strict: true를 켠다
2. tool_choice = {type: "tool", name: "<출력 tool>"}로 강제한다
   → 모델은 반드시 그 스키마의 JSON을 반환한다
3. 반환값을 서버에서 Pydantic 모델로 다시 검증한다 (strict가 보장하지 않는
   의미 규칙 — 예: judge_end가 날짜 문자열로 해석되는가)
4. 실패 시 검증 오류를 붙여 최대 2회 재시도
5. 그래도 실패하면 부분 저장하지 않고 대화(또는 작업 실패 상태)로 되돌린다
```

§3.1 검증 3층 중 **1층(구조)**이 여기까지다. 2층(출처 대조)·3층(규칙)은 LLM 밖의
결정론적 코드가 한다(§5, 02-backend.md의 Note Validator). 되돌릴 때 사용자에게
보이는 문구는 UX §9.3 규칙을 따른다 — 내부 사정("스키마 검증 실패")을 화면에 내보내지 않는다.

### 3.3 웹 검색

- `tools`에 `{type: "web_search_20260209", name: "web_search"}`를 선언하고
  `max_uses`로 작업별 상한을 건다(리서치 5, 회고 조사 항목당 2 정도에서 시작해 계측으로 조정).
- 검색 결과 블록에 출처 URL·제목이 들어오므로, 에이전트 출력 스키마의
  `sources[{title, url, published_at}]`는 이 블록에서 옮겨 적게 한다. **본문에 없는
  URL을 만들어 적지 않는다** — 후처리에서 응답에 실재한 URL인지 대조한다.

### 3.4 프롬프트 버저닝

- 프롬프트는 `agents/prompts/` 아래 파일로 두고, 파일마다 `PROMPT_VERSION` 상수를 올린다.
- AI 산출물을 저장할 때 실행 기록(jobs.payload 또는 로그)에 `agent, prompt_version,
  model`을 함께 남긴다. "이 회고 초안은 어느 프롬프트가 만든 것인가"를 되짚을 수
  있어야 품질 회귀를 원인까지 추적할 수 있다. DB 산출물 테이블에는 칼럼을 추가하지
  않는다 — 산출물의 정본은 내용이고, 계보는 실행 기록의 일이다.

### 3.5 실행 정책·비용 가드 (§10)

AI 비용은 실행 빈도에 비례하므로 **사용자별·노트별 정책**을 jobs 생성 시점에 검사한다.
초과 시 jobs를 만들지 않고 대기 시간을 안내한다(문구는 UX §9.3).

| 작업 | 정책 (MVP 초기값 — 계측 후 조정) |
|---|---|
| Thesis Builder 대화 | 대화당 턴 상한 30 (5~8턴 목표의 안전판). 사용자당 동시 draft 대화 3개 |
| 온디맨드 리서치 | 노트당 1시간 1회, 사용자당 하루 20회 |
| 확률 자료 조사 | 갈래당 1시간 1회 (2단계 폼 진입 시 자동 1회 포함) |
| 회고 초안 | 갈래 판정당 1회 자동. 재생성은 사용자 요청 시 하루 3회 |
| 어드바이저 | 노트당 1시간 1회, 사용자당 하루 10회 |

## 4. 에이전트별 상세

### 4.1 Thesis Builder (§7.3) — 대화와 노트 생성

노트 작성 수단 그 자체다. 내부적으로 두 호출로 나뉜다: **(a) 대화 진행**(스트리밍,
자유 텍스트)과 **(b) 노트 조립**(구조화 출력). 같은 시스템 프롬프트 계열을 쓰되
(b)는 §3.2 패턴으로 tool을 강제한다.

- **트리거**: (a) 사용자 메시지마다 동기 호출·스트리밍. (b) `여기까지 정리하기` 또는
  AI가 필수 항목 확보를 판단해 제안했을 때.
- **입력**: 대화 전문(`conversation_messages`), 오늘 날짜(날짜 해석용 — 캐시 보호를
  위해 시스템 프롬프트가 아니라 **첫 사용자 메시지 쪽에 주입**한다, §7), 진행 상태
  패널용 확보 현황(`conversations.draft_note`).
- **시스템 프롬프트 골자** (대화):
  - 대화 목표는 UX §3.2의 확보 항목 표 순서 — 대상 → 가설 → 갈래의 질문 → 시나리오
    2개 이상 → 판단 시점 → 근거 항목.
  - **턴 수 5~8을 목표로, 한 턴에 질문 하나.** 심문처럼 몰아붙이지 않는다. 사용자의
    말에 반응한 뒤 다음 항목으로 자연스럽게 넘어간다.
  - **판단 시점과 근거 항목만 끈질기게.** 막연하면 범위(`올해 안`)로라도 받아낸다.
    나머지는 한 번 묻고 넘어간다.
  - 근거 항목 질문은 "그렇게 되려면 그 전에 무슨 일이 먼저 일어나야 할까요?" —
    수치·데이터 출처를 되묻지 않고, "나중에 제가 찾아 정리하겠다"는 약속을 명시한다.
  - 확인 방법(목표값·비교 방식)은 묻지 않는다. 대화 중 나온 숫자는 기억만 해 둔다.
  - 반증 질문("이 판단이 틀렸다는 건 뭘로 알 수 있을까요?")은 여유가 있을 때만.
- **출력 스키마** (b, DB와의 정합 — [`01-db-schema.md`](./01-db-schema.md)):

```
build_note = {
  target:   { type: ticker|asset|theme, symbol?, name },       → notes
  thesis_summary: string(한 문장·40자 내외), thesis_detail: string, → notes
  quote:    { text: 사용자 발화 원문 그대로 },                   → content_blocks(thesis_quote, quoted_from)
  galae: [{ question, judge: {kind: date|range, start?, end?, derived: bool,
            source_text: "올해 안" },                            → galae (+ derived → content_blocks.derived)
            scenarios: [{ name(답만, 경로 금지), description,
                          is_residual: false }] }],              → scenarios (resolution_type은 2단계에서,
                                                                   여기서는 전부 manual로 초기화. residual은 서버가 생성)
  premises: [{ statement: 사용자 말 그대로, source_text }],      → premises (+quoted_from)
  watch_candidates: [ "환율", "미국 기준금리", ... ],            → 계열 매핑 입력 (아래)
  form_prefill: [{ galae_index, series_expression, mentioned_value?, comparator? }]
                                                                 → 2단계 폼 후보
  incomplete: [ "no_deadline", "single_scenario", ... ]          → 무엇을 못 받았는지 자기 보고 (참고용.
                                                                   정본 판정은 검증기 Issue[]가 한다)
}
```

- **후처리·검증**:
  - `quote.text`·`premises[].statement`를 **원본 대화에서 문자열 대조**(§5). 찾으면
    해당 `conversation_messages.id`를 `quoted_from`에 넣고, 못 찾으면 인용 표시를 떼고
    AI 문장으로 강등한다.
  - `judge.derived=true`인 날짜는 미리보기에서 `"올해 안"을 이렇게 읽었습니다 · 고치기`로
    노출한다(§3.1 규칙 3). 해석 결과와 `source_text`를 함께 반환하게 하는 이유다.
  - **갈래를 나누는 판단은 이 에이전트의 책임이다**(§7.3): 판가름 나는 날짜가 둘이면
    갈래 둘로, 같은 날이라도 질문이 다르면 나눠 반환하라고 프롬프트에 명시한다.
    단, 사용자가 말하지 않은 질문을 지어내 갈래로 세우지 않는다(원칙 1·2).
  - **계열 매핑**: `watch_candidates`·`form_prefill.series_expression`은 표현
    문자열까지만 LLM이 뽑고, `series_catalog`(search_keywords) 검색으로 실제
    `(provider, code)` 후보를 찾는 것은 **코드**가 한다. 질문이 수치에 관한 것이
    아니면 auto 후보를 만들지 않는다(§3.1 2단계) — 이 판정도 프롬프트가 아니라
    "form_prefill은 series_expression이 질문 본문에 있는 갈래에만 허용"이라는
    후처리 규칙으로 이중 방어한다.
  - 확률은 어떤 경우에도 채우지 않는다. 대화에 나온 표현이 있으면 `description`이 아니라
    미리보기 참고 문구로만 옮긴다(원칙 3).
- **실패 모드**: 스키마 실패 2회 → 대화 화면으로 되돌리고 draft 보존. 시나리오 1개·
  시점 없음은 실패가 아니라 **정상 출력**(빈 칸 반환) — 검증기의 ask/notice가 이어받는다.
  스트리밍 중단은 SDK 재시도에 맡기고, 대화 이력은 서버가 정본이므로 유실되지 않는다.

### 4.2 Probability Reference Agent (§7.4) — 자료를 답별로 가른다

확률을 매기는 에이전트가 아니다. 숫자를 내지 않고 읽을거리를 답별 더미로 가른다.

- **트리거**: 2단계 폼(확률 배분 화면) 진입 시 jobs 생성. 갈래 단위.
- **입력**: 갈래의 `question`, 시나리오 이름 목록(+id), 노트 target, 오늘 날짜.
- **시스템 프롬프트 골자**: 질문을 놓고 웹 검색 → 찾은 자료를 ①어느 답을 뒷받침하는지
  (`scenario_id`), ②종류(`base_rate`/`evidence`/`market_view`)로 분류. **기저율은
  분모·분자를 문장에 그대로**(`7건 중 3건`, 43%로 줄이지 않는다). 시장 견해는 자료
  한 줄로(`증권사 12곳 중 7곳이 …` — 58%로 환산 금지). 자기 추정치 금지. 어느 답
  편도 아니면 scenario는 null. 찾지 못한 쪽은 빈 배열이 정답.
- **출력 스키마** (`galae_references`와 1:1):

```
references = [{ scenario_index: int|null, kind: base_rate|evidence|market_view,
                headline, note?, sources: [{title, url, published_at?}] }]
```

- **후처리·검증**: `scenario_index`→`scenario_id` 매핑(범위 밖이면 null로 강등),
  headline에 `%` 패턴이 있는데 kind가 `market_view`·`base_rate`가 아니면 반려 재시도
  (원칙 3의 기계적 방어), sources URL이 검색 결과에 실재하는지 대조. `fetched_at`은
  서버가 찍는다.
- **실패 모드**: 0건 반환은 성공이다 — 화면에 `찾은 자료가 없습니다`가 그대로 나간다.
  기저율이 거의 안 나오면 기능 축소를 검토한다(§12 오픈 이슈 — 발견율을 계측한다, §6).

### 4.3 Research Agent (§7.1) — 온디맨드 리서치

MVP에서는 **온디맨드만** 있다(노트 상세 `지금 다시 조사하기`). 주기 실행은 Phase 2.

- **트리거**: 사용자 버튼 → jobs 생성. 노트 단위.
- **입력**: target, thesis_summary, 갈래 질문과 시나리오 이름·description, 기존
  `research_items`의 URL 목록(중복 수집 방지), 사용자 피드백 이력(`dismissed`가 많은
  출처·주제는 낮춘다).
- **시스템 프롬프트 골자**: ①가설·시나리오에서 검색 키워드·엔티티 추출 → ②웹 검색
  (max_uses 상한) → ③관련성 낮은 결과 버림(억지로 채우지 않는다) → ④남은 것마다
  한 줄 요약과 함께 어느 시나리오를 뒷받침/반박하는지, 관련만 있는지 분류.
- **출력 스키마** (`research_items`와 1:1):

```
items = [{ title, summary(한 줄), url, published_at?,
           scenario_index: int|null,
           relation: supports|contradicts|neutral, relevance_score: 0~1 }]
```

- **후처리·검증**: URL 실재 대조, 기존 URL과 중복 제거, `relevance_score`가 낮은
  항목 컷(임계값은 코드 상수). 화면 표기는 UX §9.4 대응표(뒷받침함/어긋남/관련 있음)를
  따르므로 내부 값만 반환한다. 뒷받침/어긋남 판정 기준은 §7.4의 Reference 분류와
  같은 프롬프트 조각을 공유한다 — 같은 것을 두 이름으로 부르지 않는다(§3.4).
- **실패 모드**: 0건도 성공. 이벤트 기반 즉시 알림은 MVP 제외이므로 "유의미도 높으면
  알림"(§7.1 5단계)은 MVP에서 구현하지 않는다.

### 4.4 Review Agent (§7.5) — 회고 초안

이 앱의 최종 산출물을 만드는 에이전트. **LLM과 코드의 경계가 가장 중요하다.**

| 단계 | 담당 |
|---|---|
| 근거 항목별 사후 조사 (뉴스·공시·실적에서 실제로 일어났는지) | LLM + web search |
| `happened / did_not_happen / unverifiable` 분류 + 출처 | LLM |
| **벤치마크 대비 수익률 계산** (종목/지수/업종/내 매매 성적, 같은 기간) | **코드** — `series_snapshots`·`trades`에서 결정론적으로 계산. LLM은 결과 숫자를 받아 서술에만 쓴다 |
| 결과가 맞았을 때의 다른 설명(시장 전체 상승 등) 수집 | LLM + web search |
| 초안 서술 생성 | LLM |
| 논리 평가(`logic_verdict`) 확정 | **사용자** — AI는 절대 확정하지 않는다 |

- **트리거**: 갈래 판정 확정(`confirmed`/`rejected`) 시 자동 jobs 생성. §3.6.
- **입력**: `premises[]`(statement 원문), 갈래의 question·판정 결과·기간(기록 시점→
  판정일), target, 그리고 **코드가 미리 계산한 benchmark_comparison**(scenario_return,
  index_return, sector_return, my_return?, period).
- **시스템 프롬프트 골자**: 근거 항목마다 해당 기간으로 한정해 조사하고 분류하라.
  확인 못 하면 `unverifiable` — 숨기지 않는다. 초안은 §3.6 예시의 구성(당시 논리 →
  항목별 조사 결과 → 벤치마크 대비 → 검토 권유)을 따르되, **"운이었습니다"라고
  확정하는 문장을 쓰지 않는다.** 마지막은 "~가능성을 검토해 보시기 바랍니다"까지다.
- **출력 스키마**:

```
review_draft = {
  verifications: [{ premise_index, verdict: happened|did_not_happen|unverifiable,
                    summary, sources: [{title, url, published_at?}] }],   → premise_verifications
  alternative_explanations: [{ summary, sources }],   → ai_draft 본문에 편입
  draft: string                                        → reviews.ai_draft
}
```

- **후처리·검증**: verifications를 `premise_verifications`로 저장(리뷰별 이력 — 덮어쓰지
  않는다, §3.4), `benchmark_comparison`은 코드 계산값을 그대로 `reviews`에 저장(LLM 출력
  아님), draft에 "운/실력" 확정 어휘가 있으면 반려 재시도, URL 대조. `drafted_at` 서버 기록.
- **실패 모드**: 전 항목 `unverifiable`이어도 초안은 만든다 — 벤치마크 대비는 언제나
  계산 가능하므로 최소한 그것은 항상 들어간다(§10 리스크 대응). 링크 부패에 대비해
  초안 생성 시점의 headline·summary를 저장한다(원문 스냅샷 여부는 §12 오픈 이슈).

### 4.5 Reminder Curation Agent (§7.2) — MVP에서는 LLM을 쓰지 않는다

§7.2가 요구하는 것은 ①여러 리마인드를 묶어 하루 1통으로, ②"과거 관점 + 새 정보 +
재평가 질문" 구성이다. 검토 결과 **MVP에서는 둘 다 LLM 없이 성립한다**:

- 묶음·우선순위·감쇠는 `reminder_rules`·`notifications` 기반의 결정론적 규칙이다
  (UX §8). LLM이 낄 자리가 없다.
- 리마인드 화면의 "과거의 나"는 원문 그대로(P2 — 요약하면 안 되는 축), "그동안의
  일"은 이미 저장된 `research_items` 요약의 재배치다. 템플릿으로 조립한다.
- 따라서 MVP의 이 에이전트는 **템플릿 + 규칙 모듈**이고, LLM 호출은 0회다. 새 정보가
  많아 요약이 필요해지는 Phase 2(주기 리서치)에서 다이제스트 문단 생성만 LLM으로
  승격하는 것을 재검토한다. 비용·환각 리스크가 없는 축은 끝까지 결정론적으로 남긴다.

### 4.6 Advisor Agent (§7.6) — 명확한 스탠스

- **트리거**: 노트 상세 "지금 어떻게 해야 할까?" → jobs 생성.
- **입력**: 가설(thesis), 갈래·시나리오와 **사용자가 매긴** 확률, 최근 `research_items`,
  auto 조건 진행 현황(목표까지의 거리), 매매 기록 요약(보유·평단), 과거
  `advisor_opinions`(일관성 체크용), 과거 회고록의 logic_verdict.
- **시스템 프롬프트 골자**:
  - **매수/추가매수/홀드/일부익절/전량매도 중 하나를 반드시 고른다.** 원론적 답변,
    "상황에 따라 다릅니다", "전문가와 상담" 금지(원칙 4 — 면책은 UI가 한다).
  - 근거가 부족하면 회피하는 대신 "무엇을 더 알면 판단이 명확해지는지"를 말한다.
  - **철회 조건을 반드시 적는다** — 이 의견이 틀렸다고 볼 조건.
  - **과거와의 상충 지적**: 사용자의 현재 가설·과거 의견과 지금 의견이 어긋나면
    그 사실을 명시적으로 짚는다(메멘토 원칙).
  - 시나리오 확률 숫자를 새로 제안하지 않는다(원칙 3). 스탠스와 확률은 다른 것이다.
- **출력 스키마** (`advisor_opinions`와 1:1):

```
opinion = { stance: buy|add|hold|trim|sell, rationale,
            referenced_scenario_indexes: [int], referenced_research_indexes: [int],
            target_price?, target_timeframe?,
            invalidation_condition: string(필수),
            conflict_note?: string  (과거 가설·의견과의 상충 — 있을 때만) }
```

- **후처리·검증**: index→uuid 매핑, `invalidation_condition` 비면 반려 재시도,
  `user_action`은 `none`으로 초기화(사후에 사용자가 기록). `conflict_note`는
  rationale 앞에 붙여 저장한다.
- **실패 모드**: 참조할 리서치가 없으면 없는 채로 의견을 낸다(입력 부족은 회피 사유가
  아니다). 스탠스 누락은 스키마가 막는다(enum 필수).

## 5. 인용·환각 방어 — 층을 나누고 한계를 숨기지 않는다

§3.1 검증 2층의 구현. **기계적으로 검증 가능한 것과 불가능한 것을 구분한다.**

1. **출처 대조 (코드, 기계적 방어선)** — "사용자가 한 말"이라고 주장하는 모든 출력
   (`quoted_from` 블록, `premise.statement`)은 저장 전에 원본 대화에서 실제 문자열을
   찾는다. 대조는 공백·개행 정규화 후 부분 문자열 일치로 하고, 못 찾으면 인용 표시를
   떼고 AI 저작으로 강등한다(차단이 아니라 강등 — 내용은 남되 `[사용자]`가 안 붙는다).
   웹 출처(`sources[].url`)도 같은 성질 — 검색 결과 블록에 실재한 URL만 통과시킨다.
2. **사람 확인 (최종 방어선)** — AI가 쓴 요약문·서술은 자동 검증이 불가능하다.
   노트는 미리보기, 회고는 초안, 어드바이저는 "AI의 견해" 표기가 그 방어선이다.
   **이 한계를 문서에서도 화면 설계에서도 숨기지 않는다** — 그래서 미리보기 없는
   자동 저장 경로를 만들지 않고, 저장 후 재생성을 금지한다(§3.1 규칙 4).

## 6. 평가·테스트

- **골든 대화 픽스처**: 대표 대화 시나리오(가설이 또렷한 경우 / 느낌만 있는 경우 /
  날짜가 둘 나와 갈래가 갈리는 경우 / 수치 목표가 언급된 경우 / 반대 시나리오를 끝내
  안 말한 경우 등)를 `tests/fixtures/conversations/`에 두고, 각각에 **기대 노트
  구조**를 명세한다. 검증은 LLM 판정이 아니라 결정론적 assert로 한다 — 갈래 수,
  판단 시점 존재 여부, `premise.statement`가 원문의 부분 문자열인가, 확률이 전부
  null인가, residual 생성 여부.
- **프롬프트 회귀 테스트**: `PROMPT_VERSION`이 올라가는 PR은 골든 픽스처 전체를
  실제 모델로 1회 실행해 결과를 비교한다(비용이 드는 테스트이므로 CI 상시가 아니라
  프롬프트 변경 시에만). 문장 스타일 차이는 허용하고 구조적 assert 실패만 회귀로 본다.
- **계측** (§10·§12의 오픈 이슈에 답을 주는 실측):
  - 대화 턴 수 분포 (목표 5~8턴 — §12), 중도 이탈률, 되묻기에서 `비운 채로 저장` 비율
  - 2단계 폼 진입률·완료율 (§10)
  - Probability Reference의 기저율 발견율 (몇 %의 갈래에서 base_rate가 나오는가 — §12)
  - Review의 `unverifiable` 비율 (대부분 확인 불가면 회고 품질 리스크 — §10)
  - 리서치 피드백 반영/무시 비율, 작업별 토큰·비용 (§3.1 로깅에서 집계)

### 프롬프트 캐싱

- 시스템 프롬프트(헌법 + 에이전트별 본문)는 **동결하고** 마지막 블록에
  `cache_control: {type: "ephemeral"}`을 건다. 날짜·사용자명·노트 내용 같은 가변
  값은 시스템 프롬프트에 절대 넣지 않고 사용자 메시지 쪽에 넣는다 — 한 바이트만
  달라져도 프리픽스 캐시가 통째로 깨진다.
- 대화형(Thesis Builder)은 멀티턴 패턴 — 직전 턴 마지막 블록에 브레이크포인트를
  옮겨 가며 대화 누적분을 캐시로 읽는다. 턴이 길어질수록 절감 폭이 커진다.
- sonnet-5의 캐시 최소 프리픽스는 1,024토큰이므로 시스템 프롬프트가 이보다 짧은
  에이전트는 캐시를 걸어도 조용히 무시된다 — `usage.cache_read_input_tokens`로
  적중을 확인하는 로깅(§3.1)이 이를 잡는다.
